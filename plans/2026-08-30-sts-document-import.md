## Формат исходников

Каждый файл - PDF, ровно 2 страницы (перед+зад СТС), качество сканов сильно разное
(53 КБ - 3,3 МБ на файл, от ~150 DPI до ~300 DPI эквивалента). Карточка занимает малую
часть листа А4 - остальное белое поле.

**Важная ловушка, поймана на 2-м пробном образце (тягач Mercedes Actros, файл
"224 Мерседес, БУЛЬДОГ.pdf"):** `doc.extract_image(xref)` (PyMuPDF) отдаёт сырые байты
встроенного изображения БЕЗ трансформации/поворота страницы - для части файлов это
переворачивало картинку на 180°. Правильный метод - ВСЕГДА через `page.get_pixmap()`,
который трансформацию применяет корректно; для попадания в целевое разрешение - серия
рендеров с разным zoom, а не прямое чтение эмбеда. См. `process_all.py` в scratchpad
сессии, функция `render_target()`.

## Обработка изображений

1. Рендер каждой страницы через `get_pixmap()` (см. выше), приведение к целевому
   разрешению (длинная сторона ~1900px - хватает для чёткого чтения текста, проверено
   визуально).
2. Автообрезка по плотности тёмных пикселей (не по одиночным пикселям - иначе пылинки
   скана растягивают bbox на весь лист) - функция `autocrop()`, порог плотности 25
   тёмных пикселей в строке/столбце, отступ от края скана 25px (артефакты крышки
   сканера), паддинг вокруг найденной карточки 20px.
3. Компоновка перед+зад бок о бок на одной странице (выравнивание по высоте, отступ
   30px), сохранение как одностраничный PDF (JPEG quality 85).

Результат - экономия объёма кратна на плохо отсканированных файлах (3,1 МБ -> 175 КБ на
одном из образцов), почти без экономии на уже маленьких файлах - принято Владом как
устраивающий компромисс ("на разрешение экономить не нужно, но чтобы экономно по объёму").

## Сопоставление файлов с записями базы

Имя файла обычно содержит номер без ведущей буквы (тягач: "894 ХМ 797" = "О 894 ХМ 797")
или без 2-буквенного префикса (прицеп: "4928 77" = "ТА 4928 77"). Автоматическое
сопоставление по регулярным выражениям (полный номер тягача: 3 цифры + 2 буквы + регион;
прицепа: 4 цифры + регион) дало 67/103 с первого прохода. Остаток (короткие фрагменты
номера в имени файла) сопоставлен вручную по марке + частичным цифрам, финально
подтверждается визуально при открытии файла на этапе извлечения данных (VIN на
документе - последняя проверка правильности сопоставления).

**Итог сопоставления (зафиксировать после завершения):** из 103 файлов - N сопоставлено,
M дублей (тот же файл под двумя именами, по совпадению размера в байтах), K без пары
(нет соответствующей записи в `sprav_assets` - НЕ трогать, правило Влада "не грузить
лишней информации"), L записей техники вообще без файла СТС в папке.

## Извлечение данных (визуально, не OCR)

Поля из документа: VIN, технически допустимая масса, масса в снаряжённом состоянии,
год выпуска, цвет (`sprav_assets` - характеристики физической машины) + собственник,
лизингодатель (если указан), номер СТС, дата выдачи (`sprav_asset_documents` -
реквизиты КОНКРЕТНОГО документа, при переоформлении СТС меняются, машина - нет).

Параллелизовано через subagent'ы (пачками) - каждый смотрит свою пачку смёрженных
изображений, возвращает структурированный JSON. Финальная запись в базу - централизованно
из этой сессии, не из subagent'ов (контроль корректности продовых записей).

## Запись в базу

`POST /api/sprav/asset` делает ПОЛНЫЙ UPDATE (не патч) при наличии
`expected_updated_at` - обязательно передавать текущие значения ВСЕХ полей (взятых из
свежего `GET /api/sprav/state`), не только новые из СТС, иначе затрутся в NULL значения,
уже занесённые Штаткой (`manufacturer`/`name`/`trailer_type`/...).

`updated_by`/`created_by`/`uploaded_by` = `import:sts-drive-30.08` (тот же принцип, что
`import:shtatka-30.08`) - отличимая метка для будущих сессий.
