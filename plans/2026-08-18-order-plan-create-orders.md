## Карта колонок для записи (подтверждена в этой же сессии по формуле N3 + строкам
заголовков 1/2 живого листа - см. `getOrderPlanView_`/`readOrderPlanDayTab_`)

Пара строк на заказ (нечётная - "верхняя", чётная - "нижняя"):

| Кол. | Верхняя строка (пишем при создании) | Нижняя строка (оставляем пустой) |
|---|---|---|
| A | № п/п (авто, следующий по дню) | статус (пусто до первого выбора) |
| B | менеджер (`access.name`, авто) | логист (пусто) |
| C | тип техники | особенности (необязательно) |
| D | заказчик | ФИО/телефон контакта заказчика |
| E | дата подачи (или пусто - см. ниже) | время подачи |
| F | груз | габарит/негабарит |
| G | (пропускаем - "исполнитель", не наше поле) | какие документы |
| H | адрес погрузки | конт. лицо на погрузке |
| I | адрес выгрузки | конт. лицо на выгрузке |
| J | условия переработки | примечание |
| K | стоимость (необязательно) | статус оплаты (пусто) |
| L,M,O,P,Q,R | пусто - заполняет логист по ходу работы | |

Колонку E (дата) можно не писать явно - в таблице уже есть `onOrderDateAutoFill`
(installable-триггер `masterEditRouter`), который сам подставляет "ДД.ММ.ГГГГ
(день недели)" при любой правке колонки B (менеджер) на дневной вкладке. Наша запись
в B её и вызовет - дата встанет тем же кодом, что и для ручного ввода, без
дублирования логики форматирования.

## Как находим свободную строку

1. `LockService.getScriptLock()` (тот же приём, что уже в `runAll()`) - сериализует
   ОДНОВРЕМЕННЫЕ создания заявок из дашборда между собой.
2. Внутри лока: сканируем дневную вкладку (по дате из формы) с строки 3, шаг 2, ищем
   первую верхнюю строку, где колонка A пустая.
3. Перед записью - повторно читаем именно эту ячейку (на случай, что кто-то успел
   вписать заявку вручную прямо в этот момент) - если уже не пустая, берём следующую.
4. Номер заказа - максимум существующих чисел в колонке A этой вкладки + 1 (не просто
   "первая свободная строка + 1" - в очереди могут быть дыры от удалённых заказов).
5. Пишем обе строки диапазоном (`setRange().setValues()`), не по одной ячейке.

**Почему существующая автоматика (покраска, Telegram, дата) не ломается и не
дублируется:** `masterEditRouter` - installable-триггер, а не simple-триггер - по
документации Google такие триггеры срабатывают и на программные правки ИЗ ДРУГОГО
Apps Script проекта (не только на правки живым человеком). Значит запись из дашборда
пройдёт через ТОТ ЖЕ путь, что и ручной ввод - ничего переписывать не нужно, но это
нужно ОДИН РАЗ проверить вживую перед тем, как доверять фиче (см. Проверка ниже).

## API

`?action=order_plan_create` через `doGet` (тот же паттерн, что уже `calc_save` -
GET с именованными параметрами, не JSON-блобом и не `doPost` - в этом файле нет ни
одного `doPost`, не изобретаем новый механизм ради одной фичи). Параметры - поля
формы (customer, equipType, day, time, cargo, gabarit, loadAddress, loadContact,
unloadAddress, unloadContact, documents, reworkTerms, note, cost, customerContact).
Менеджер/логист - пишут только от своего имени (`access.name`, как везде). admin -
через `&manager=`, как и на чтении (тот же селектор "Смотреть как сотрудник").

Ответ: `{ ok: true, day, orderNumber }` или `{ error: '...' }`.

## Форма на дашборде

- Кнопка "+ Новая заявка" в шапке блока "План задание".
- Поля - как в таблице (см. карту колонок выше). Обязательные: тип техники,
  заказчик, дата подачи, адрес погрузки, адрес выгрузки. Остальное - опционально
  (логист неглавные поля).
- Кнопка "Повторить заказ" на карточке существующего заказа (`buildOrderCard_`) -
  открывает ту же форму, предзаполненную ВСЕМИ полями этого заказа, КРОМЕ даты и
  времени - их менеджер вводит заново (Влад: "остаётся только внести время и дату").
- После успешного создания - закрыть форму, инвалидировать кэш (`orderPlanData =
  null`), перезагрузить вкладку, при возможности - открыть карточку только что
  созданного заказа.

## Проверка перед тем, как доверять фиче

1. Создать ОДНУ тестовую заявку через ручной запуск функции в редакторе Apps Script
   (ещё БЕЗ фронтенда) - открыть реальную таблицу планировки, визуально сверить: та
   ли вкладка, тот ли номер, подставилась ли дата автоматически, не съехали ли
   выпадающие списки/условное форматирование в этой строке.
2. Проверить конкурентность - два "одновременных" тестовых вызова подряд не должны
   попасть в одну и ту же строку (номера должны быть последовательными, не
   задвоенными).
3. Только после этого подключать фронтенд-форму и звать Влада на реальный тест.
4. Удалить тестовую заявку из таблицы вручную после проверки (не оставлять мусор в
   боевых данных).
