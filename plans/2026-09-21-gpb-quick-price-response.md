# План: Быстрые ответы на ценовые запросы ГПБ Комплект

**Дата:** 2026-09-21
**Автор:** Клод
**Статус:** черновик

## Цель

Новая вкладка в дашборде, где по связке «техника + маршрут» (в духе запросов Субботина В.А.
из ГПБ Комплект) менеджер за секунды видит похожие исторические ставки и получает готовый
черновик ответа — вместо того, чтобы вручную рыться в переписке и считать с нуля. Сейчас
много таких запросов остаётся без ответа именно из-за трудозатрат на расчёт.

**Как выглядит «сработало» (критерий MVP):** открываешь вкладку → выбираешь технику (ESDA45,
ESDE240, ...) → вводишь направление текстом (например, «Лесосибирск» или «Забайкальск —
Рязань») → видишь список похожих прошлых рейсов с ценами и датами → жмёшь «скопировать
черновик ответа» → вставляешь в письмо Субботину.

## Контекст

21.09.2026 разобрана вся история работы с ГПБ Комплект (почта с 03.2024, 1С, пакинг-листы
техники) — см. [.business/clients/gpb-komplekt.md](../.business/clients/gpb-komplekt.md).
Ключевая находка: у клиента есть 109 реальных цен в 1С
([gpb-komplekt-1c-priced.csv](../.business/clients/gpb-komplekt-1c-priced.csv)) + около
десятка точных цифр, выловленных вручную из переписки — но всё это сейчас лежит как сырые
файлы, не встроено в дашборд.

**Архитектурное решение (согласовано с Владом 21.09.2026):** это НЕ вкладка «Калькулятор»
(та считает от базы в Домодедово для парка тралов Бульдога, суммы — сотни тысяч ₽).
Перевозки ГПБ — от Забайкальска/Маньчжурии по всей России, суммы в единицы-десятки
**миллионов** ₽, фулфилмент смешанный (свои тралы или субподряд/ж-д — Влад подтвердил «по
ситуации»). Поэтому цена не считается от компонентов затрат, а **подбирается по историческим
рейсам** с похожей техникой/направлением — таблица ставок, не формула.

## Что НЕ делаем в v1 (сознательно отложено)

- Расчёт расстояния/интерполяция цены геометрически (Nominatim/OSRM, как в Калькуляторе) для
  направлений без исторических данных — в v1 просто честно показываем «похожих рейсов не
  найдено».
- Автоматический разбор текста входящего письма (вставил письмо → сам вытащил технику и
  маршрут) — в v1 ручной ввод.
- Показ габаритов/массы техники из пакинг-листов на этой вкладке — пакинг-листы не
  распознаны текстом (сканы), нужен отдельный OCR-конвейер, это отдельная фича.
- Пополнение базы новыми подтверждёнными ценами через UI — в v1 таблица статична (снимок на
  21.09.2026), обновление — вручную пересобрать импорт при следующей выгрузке 1С.
- Прямая интеграция с Mail.ru (черновик ответа сразу в письмо) — в v1 просто кнопка
  «скопировать текст».
- Тонкая настройка доступа по ролям — в v1 видимость как у Калькулятора (админ+менеджеры) или
  сузить до Влада, решить в Фазе 0.

## Риски

- **Цена «полного» плеча — это НЕ вся стоимость доставки клиенту.** Подтверждено на данных
  (Фаза 0): «полное» плечо (граница→точка) и «короткое» плечо (Маньчжурия→граница,
  растаможка) — это ВСЕГДА две отдельные строки одного рейса, и клиенту в переписке
  озвучивается их СУММА (пример: Малмыж = 1.5М короткое + 16.3М полное = 17.8М итого).
  Вкладка в Фазе 1 по умолчанию показывает только `full`, чтобы не путать масштабы цифр в
  списке — но черновик ответа менеджеру должен явно напоминать прибавить короткое плечо
  (типовой диапазон 150К-7.6М в зависимости от модели, см. таблицу short в чистом датасете),
  иначе есть риск озвучить клиенту заниженную на короткое плечо цену.
- Выгрузка 1С «БаТ данных.xlsx» устарела для 2025H2-2026 (проверено 21.09.2026) — таблица
  будет сильно смещена к 2024 году, если не дособрать данные из почты. Не блокирует v1
  (честно показываем, что есть), но снижает полезность для недавних направлений.
- Разброс цен внутри одного направления большой (зависит от модели и количества единиц в
  партии) — медиана может вводить в заблуждение при малом числе совпадений (1-2 рейса).
  Показывать количество найденных совпадений рядом с ценой, чтобы менеджер видел
  уверенность оценки.
- Совпадение по свободному тексту (без геокодирования) может давать ложные срабатывания
  на похожих топонимах — приемлемо для v1 (менеджер видит список и сам решает), не для
  автоматической отправки цены без проверки человеком.

выше (не отдельным списком, а прямо в шаги Фазы 0/1, чтобы не разъезжались):

- 🔴 Короткое и полное плечо (Маньчжурия↔Забайкальск vs полный маршрут) не были разделены в
  выдаче — риск смешать цены на порядок разной величины в одной медиане. Исправлено:
  `leg_type` при импорте + фильтр `full` по умолчанию в поиске.
- 🔴 Кириллические омоглифы в кодах моделей (встречается «ESDА45» с кириллической «А») —
  regex на латинице молча терял бы такие строки. Исправлено: нормализация до парсинга +
  сверка count по модели с досье.
- 🔴 Эндпоинт с реальными коммерческими ставками был описан без auth — прямой повтор класса
  ошибки `YARD_API_KEY` из истории проекта. Исправлено: явный пункт на `session_token`.
- 🟡 Дубли строк (одна сделка = несколько бухгалтерских строк) завышали бы счётчик «N
  рейсов», который план сам использует как индикатор доверия к медиане. Исправлено: дедуп
  по (дата, модель/VIN, маршрут) в Фазе 0.
- 🟡 Смешение НДС 0% и с НДС в одной медиане. Исправлено: `vat_note` сохраняется и
  показывается в выдаче, не сворачивается молча.

Архитектура (данные → таблица → API → вкладка) признана здоровой, переписывать не
потребовалось — только донастройка Фаз 0/1.
