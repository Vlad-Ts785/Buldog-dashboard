# Адреса контрагентов - аудит кода (26.09.2026)

Только чтение. Сайт - рабочая копия `files/` (ветка `claude/manager-actions-analytics-204adc`).
Сервер - боевой код на VPS `/root/yard-dashboard` (коммит `10591ea`), читался через grep/sed,
запросов к базе не было. Цифры по данным (сколько дублей, сколько заявок без координат) в этом
аудите НЕ считались - только то, что видно из кода. Где вывод, а не прямой факт кода - помечено

## 0. Короткая схема

```
ВВОД (4 разных места)                  ПОДСКАЗКИ                          СОХРАНЕНИЕ                        ПЕРЕИСПОЛЬЗОВАНИЕ
-------------------------------        -----------------------------      ----------------------------      ------------------------------
Задание ПК (order-plan-v2.js)   ---->  1) «Точки этого заказчика»   --->  plan_orders:                ---> /orders/customer_history
Задание телефон (orders-m.html) ---->     (/orders/customer_history,       load_address / unload_address       (по ТЕКСТУ названия заказчика,
CRM-сделка (index.html)         ---->      по тексту названия)             load_lat/lon, unload_lat/lon        последние 200 заявок, топ-8)
Планировка (plan-m / index)     ---->  2) «Адреса» DaData                  *_contact_name/phone           ---> «Повторить», «Перенести»
                                          (/geocoder/suggest)              *_confirmed (никто не пишет)        (копия полей)
                                       3) ссылка/координаты в тексте       customer (текст) +             ---> Задание водителю, договор,
                                          (/geocoder/resolve_link)         customer_entity_id (необяз.)        навигация, оценка цены
                                       4) «База»/«По месту»
                                                                     копии: plan_segs.route_from/to (200 симв.),
                                                                     crm_deals.route_from/to (200 симв., без координат),
                                                                     nav_geo_cache (свой кэш точек), contract_versions.snapshot
```

Главное: **отдельного хранилища адресов контрагента нет.** Адрес живёт только внутри каждой
заявки (`plan_orders`), «память по контрагенту» - это выборка из прошлых заявок по точному
тексту названия заказчика, пересчитываемая при каждом открытии формы.

## 1. Форма «Задание» на ПК (`files/order-plan-v2.js`)

### 1.1 Поля
- Разметка полей адреса: `order-plan-v2.js:4903-4918`. `#op2-f-from` (погрузка, плейсхолдер
  «Адрес, ссылка на карту или координаты 55.75, 37.62»), `#op2-f-to` (выгрузка), рядом
  контакты `#op2-f-fromcontact` / `#op2-f-tocontact` («Имя · телефон», одной строкой).
- Под полем - подсказка-«хинт» с координатами (`#op2-f-fromhint`, 4909). У выгрузки хинт при
  открытии всегда пустой (4917), у погрузки показывает сохранённые lat/lon.
- Чипы над полем: у логиста «База» (адрес и координаты базы захардкожены,
  `BASE_ADDRESS_`/`BASE_LAT_`/`BASE_LON_`, 47-48), у менеджера «По месту» (текст «Работа по
  месту» БЕЗ координат, 53) - 4905-4906, 5242-5249.
- Браузерное автозаполнение подавлено (`blockForeignAutofill_`, 34-39): Chrome/Яндекс свою
  историю адресов не подсовывают, только наши подсказки.

### 1.2 Откуда подсказки и в каком порядке
Список под полем состоит из двух независимых под-блоков (`listSubSection_`, 5576-5581):

1. **«Точки этого заказчика»** - `fetchCustomerHistory(name)` (5545-5572) ->
   `GET /orders/customer_history?customer=<текст>`. Один и тот же список кладётся И в погрузку,
   И в выгрузку (5555-5556) - погрузка/выгрузка не различаются. Показывается до 8 штук, со
   счётчиком «сколько раз» (5550-5552). **Не фильтруется по тому, что человек печатает** - это
   статичный блок «топ-8 заказчика».
   Когда вызывается:
   - клик по заказчику в выпадашке (5160-5169), в т.ч. по строке «Новый: «...»»;
   - после «Сохранить в справочник и подставить» по ИНН (5476);
   - при открытии существующей заявки / повтора / заявки из CRM, если `customer` не пуст (5253).
   НЕ вызывается, если название заказчика просто напечатали и ушли из поля без клика по
   подсказке (обработчик `input` у `#op2-f-cust` зовёт только `fetchCustomers`, 5150-5159).
   При перепечатывании заказчика старый блок истории **не очищается** - в списке остаются
   точки предыдущего заказчика, пока не выбрать нового из выпадашки.
2. **«Адреса»** (DaData) - `fetchGeoSuggest(side, q)` (5600-5635) -> `GET /geocoder/suggest`,
   с 3 символов, задержка 400 мс. Подсказки без координат выбрасываются (5609). В поле
   кладётся полный `f.value` DaData (с городом/областью), а не укороченный вид из списка
   (5616-5623). Пустой ответ пишется в журнал трения `empty_search` (5626).

Какой блок выше: тот, чей под-div создан первым. `fetchGeoSuggest` создаёт свой div сразу при
первом вводе символа (5602), история - когда придёт ответ сервера. На практике (заказчика
выбирают раньше адреса, у существующей заявки история грузится при открытии) история стоит
**первой**; если начать печатать адрес до выбора заказчика - первыми будут «Адреса» (вывод).

### 1.3 Что подставляется при клике
- Один обработчик на весь список (5229-5235): `applyAddr_(side, address, lat, lon, 'из истории
  заказчика')` (5216-5223) - текст в поле, координаты в `dataset.lat/lon` поля, хинт.
- **Контакт подставляется вместе с адресом**, если у точки из истории он есть (5232-5234): в поле
  «Контакт на погрузке/выгрузке» той стороны, куда кликнули. Перезаписывает уже введённый
  контакт без вопроса. Контакт берётся из той заявки, где этот адрес встречался последним
  (см. сервер, п. 3.1), независимо от того, был он там погрузкой или выгрузкой.
- Контакт заказчика из истории НЕ подставляется - только текст-подсказка «Из истории: ...» под
  полем (5557-5560).
- Юрлицо-исполнитель «От кого» из последней заявки заказчика подставляется автоматически
  (только в новой заявке) - 5565-5570.

### 1.4 Координаты (`dataset.lat/lon`)
Единственный источник координат для сохранения - `dataset` поля (`collectForm`, 5747-5756).
Кто кладёт координаты в `dataset`:
- клик по подсказке истории/DaData (5218);
- «База» (координаты базы) / «По месту» (очищает, 5245-5246);
- `tryParseAddrPaste_(side)` (5706-5721) - на потере фокуса поля (5227) и при открытии
  существующей заявки без координат (5266-5267). Ищет в тексте: параметры длинной ссылки
  Яндекс.Карт `ll=`/`pt=`/`whatshere[point]=` (порядок долгота,широта, 5665-5671), «голую» пару
  чисел широта,долгота вне ссылки (5672, 5686-5691), короткую ссылку разворачивает сервер
  `/geocoder/resolve_link` (5711-5717). Текст адреса НЕ меняется, ссылка остаётся в нём.
- с 26.09 (фикс `62852cd`) - при открытии заявки на правку сохранённые координаты кладутся в
  `dataset` (5257-5265), иначе любая правка стирала точку (по README сервера восстановлено 82
  погрузки и 63 выгрузки в 97 заявках, `README.md:8810`).

**Чего НЕТ:** ручная правка текста адреса координаты НЕ сбрасывает. Обработчик `input` только
запускает DaData (5228), `dataset.lat/lon` остаётся от прошлого выбора. `tryParseAddrPaste_`
тоже выходит сразу, если координаты уже есть (5708). Следствие (вывод по коду):
- выбрал подсказку, потом дописал/переписал адрес руками - сохранится новый текст со СТАРОЙ
  точкой;
- открыл заявку на правку и вставил в адрес другую ссылку - останется старая точка (после
  фикса 26.09 это стало возможно в режиме правки, раньше там точка просто терялась);
- в «Задании водителю» ссылка «Карта:» поведёт в старое место (driverText, 4079/4084).
Для сравнения: мобильная форма сбрасывает координаты на каждый ввод (п. 2), поле «Компания-
перевозчик» у наёмника сбрасывает привязку к юрлицу на ввод (3862-3864) - у адреса этого нет.

### 1.5 Флаги `load_confirmed` / `unload_confirmed`
- В БД есть (`import/plan-orders-schema.sql:43,49`, «1 = адрес из подсказки/координат, 0 =
  ориентир текстом»), сервер их принимает (`api/lib/plan-orders.js:639-640,780`).
- **Ни один клиент их не отправляет** (`collectForm` 5730-5759, мобильная форма 2013-2025,
  «Повторить» 5911-5923). Сервер сам их не вычисляет. Значит у всех заявок = 0 (DEFAULT).
- Используются только в карточке заявки: у погрузки без координат пишется «адрес не
  подтверждён» (4393). У выгрузки такой пометки нет (4395). То есть фактически это пометка
  «нет координат», и только для погрузки.

### 1.6 Обязательность
- Адреса не обязательны для сохранения (сервер: комментарий `plan-orders.js:632-633`). Пустая
  выгрузка - кнопка жёлтая «есть незаполненные» (`tickState`, 5282); пустая погрузка кнопку даже
  не желтит.
- Для «подтвердить» нужны оба адреса, но достаточно ЛЮБОГО текста - координаты не требуются
  (сервер `confirmReadinessError_`, `plan-orders.js:149-153`; клиент 3301-3302).

## 2. Мобильные формы

### 2.1 Заявка с телефона (`files/orders-m.html`)
- Поля «Откуда»/«Куда» + «Контакт» под каждым: 1693-1699. Тап по слову «Откуда»/«Куда» = «База»
  (логист) / «Работа по месту» (менеджер), `applyBase_` 1781-1789 (адрес базы продублирован
  строкой в коде, 1784).
- Подсказки - те же эндпоинты, что на ПК (1864-1967): заказчик `/orders/customers`, история
  `/orders/customer_history`, DaData `/geocoder/suggest`. Порядок жёсткий: сначала история,
  потом «Адреса» (`renderAddrSugg_`, 1902-1906).
- Отличия от ПК:
  - история приходит **без контактов** - в разметке нет `data-cname/cphone` (1944-1946), контакт
    с адресом не подставляется;
  - история грузится **только** при выборе заказчика из выпадашки (1897); при открытии заявки на
    правку не грузится вообще;
  - **нет разбора ссылок/координат** из текста (`tryParseAddrPaste_`/`resolve_link` на телефоне
    отсутствуют) - вставленная ссылка Яндекса остаётся текстом без точки;
  - координаты сбрасываются при любом ручном вводе (1849-1850) - правильно, в отличие от ПК.
- **Правка заявки с телефона стирает координаты (вывод по коду, на данных не проверено).**
  Объект формы `F` в режиме правки собирается без `load_lat/load_lon/unload_lat/unload_lon`
  (1597-1604), поэтому `draft.load_lat` пуст, и в запрос уходит `load_lat: ''` (2017). Сервер
  превращает `''` в `NULL` (`num()`, `plan-orders.js:80`; `readFields` 779) и пишет в заявку
  (`UPDATE`, 834). Это тот же класс бага, что починили 26.09 на ПК (`order-plan-v2.js:5257-5265`),
  на телефоне фикса нет. Точка сохранится, только если заново выбрать адрес из подсказки.
- Правка с телефона пересобирает текст адреса: при открытии адрес режется по первой запятой
  (`splitAddr`, 573-578; `normalizeOrder` 589), при сохранении, если поле не трогали,
  склеивается обратно через «, » (2015-2016). «Москва,ул. Ленина» станет «Москва, ул. Ленина» -
  строка меняется без участия человека (вывод: ещё один вариант написания в истории).
- Заказчик: при ручном вводе `customer_entity_id` сбрасывается в null (1870), но null не
  отправляется (2031) - сервер оставляет старое юрлицо (см. п. 4).
- «Повторить» с телефона копирует адреса, координаты и юрлицо целиком (1535-1543).

### 2.2 Мобильная Планировка (`files/plan-m.html`)
- Своего ввода адресов заявки нет. У отрезка-рейса есть «Откуда»/«Куда» (`route_from/route_to`
  в `plan_segs`) - выбор из списка `placeItems` (1680, 1723-1728): «У этого заказчика» (до 5
  мест из уже загруженных на ленту отрезков с ТОЧНО таким же текстом заказчика) + захардкоженный
  список 32 городов `PLACES` (566). Ни DaData, ни `/orders/customer_history`, ни координат.
- То же на ПК-Планировке: `datalist` из того же `PLACES` (`index.html:34195`, 36952, 37207).

## 3. Сервер (VPS `/root/yard-dashboard`)

### 3.1 `GET /api/orders/customer_history` (`api/lib/plan-orders.js:1547-1565`)
```sql
SELECT customer_contact_name, customer_contact_phone, load_address, load_lat, load_lon, load_contact_name, load_contact_phone,
       unload_address, unload_lat, unload_lon, unload_contact_name, unload_contact_phone, executor_entity_id, equipment_type
  FROM plan_orders WHERE deleted_at IS NULL AND customer = ? ORDER BY service_date DESC LIMIT 200
```
- **Ключ - текст названия заказчика** (`customer = ?`), НЕ `customer_entity_id`. Сравнение без
  учёта регистра (collation таблицы `utf8mb4_0900_ai_ci`, `plan-orders-schema.sql:70`), но
  «ООО Ромашка», «Ромашка», «ООО «Ромашка»» - три разных заказчика с тремя разными историями.
- Период - нет ограничения по дате, последние 200 заявок по дате подачи.
- Статус не фильтруется: в историю попадают и отменённые (отбой), и внутренние заявки.
  Менеджер не фильтруется: видны точки и телефоны из заявок всех менеджеров.
- Схлопывание (1554-1559): погрузка и выгрузка складываются в ОДНУ общую копилку, ключ -
  **точная строка адреса** (JS `Map`, чувствительна к регистру, пробелам, запятым,
  «ул.»/«ул», ссылке внутри). Координаты и контакт точки берутся из **первого** (самого свежего)
  вхождения строки, более старые не смотрятся - если в свежей заявке точки не было, у подсказки
  её не будет, даже если раньше была.
- Порядок - по частоте (`n` по убыванию), при равенстве - кто свежее; отдаётся топ-8 (1562).
- Служебные тексты («Работа по месту», адрес базы) никак не отсеиваются - попадают в «точки
  заказчика» наравне с реальными (вывод по коду).
- Контакты заказчика - так же, по строке «имя · телефон», топ-8; клиент использует только
  первый как текст-подсказку.

### 3.2 `GET /api/orders/customers` (`plan-orders.js:1469-1482`)
- «Мои»: `GROUP BY customer` (текст) из `plan_orders` за **90 дней** (1477), для менеджера - свои,
  для логиста/админа - все. На клиенте блок подписан «Мои за 30 дней» (`order-plan-v2.js:5392`,
  `orders-m.html:1880`) - подпись не совпадает с кодом.
- `entity_id` у «Моих» = `MAX(customer_entity_id)` по всем заявкам с этим текстом.
- «Все контрагенты»: `sprav_legal_entities`, `name LIKE 'q%'` - поиск только по НАЧАЛУ названия
  (1480); та же префиксная логика у «Моих» (`customer LIKE 'q%'`).
- Отдельно поиск по ИНН (10/12 цифр): `/orders/inn` (1642-1654) - справочник, иначе DaData
  (ЕГРЮЛ) с кнопкой «Сохранить в справочник и подставить» (`/orders/inn_save`, 1774-1791,
  создаёт `le_inn_<ИНН>`).

### 3.3 Геокодер (`api/lib/geocoder.js`, эндпоинты `api/server.js:1874-1910`)
- `/api/geocoder/suggest` - DaData `suggest/address`, 5 подсказок (`server.js:1878`), без
  приоритета региона; наружу - `value`, `lat/lon`, части адреса (`geocoder.js:18-43`).
- `/api/geocoder/reverse` - DaData `geolocate/address` по координате (45-56). Используют
  Калькулятор и CRM, форма «Задание» - нет.
- `/api/geocoder/resolve_link` - разворачивает короткую ссылку Яндекса редиректами, только домены
  yandex.ru/ya.ru/yandex.com, до 6 переходов, 4 с (68-90). Ничего не пишет.

### 3.4 Сохранение заявки `POST /api/orders/save` (`plan-orders.js:787-...`)
- Поля (`EDITABLE`, 637-641): `load_address`/`unload_address` (до 500 символов, 778),
  `load_lat/lon`, `unload_lat/lon` (`num()`, 779: пустая строка -> NULL),
  `load_confirmed/unload_confirmed` (780), контакты (нормализация телефонов на сервере,
  `normalizeOrderContacts`, 784), `customer` (до 255), `customer_entity_id` (до 64).
- Правка: обновляются ТОЛЬКО присланные поля (817, 834). Не прислали поле - старое значение
  остаётся; прислали пустое - затирается.
- В журнал правок координаты пишутся без значений, только факт изменения (`HIST_NO_VALUE_`, 222).

### 3.5 Где адрес ещё хранится/копируется (кроме `plan_orders`)

| `plan_orders_history.snapshot` | полный снимок строки перед правкой | - |
| `sprav_legal_entities.legal_address` | только ЮРИДИЧЕСКИЙ адрес из ЕГРЮЛ, адресов погрузки/выгрузки у юрлица нет | `import/sprav-schema.sql:81-120` |

Отдельной таблицы адресов контрагента (вида `customer_addresses`) нет. В «Партнёрах»
(`api/lib/partner-bridge.js`) адресов нет. В `crm_clients` - только `company` текстом
(`import/crm-schema.sql`, `server.js:4695`).

## 4. Заказчик в заявке и справочник юрлиц

- `plan_orders.customer` - текст (обязателен при создании, `plan-orders.js:856`);
  `customer_entity_id` - ссылка на `sprav_legal_entities.id`, **необязательна**
  (`plan-orders-schema.sql:26-27`). Индекс в файле схемы есть только по тексту (`idx_customer`, 69).
- Как заполняется `customer_entity_id` на ПК: только кликом по подсказке с юрлицом или через
  «Сохранить по ИНН» (`order-plan-v2.js:5166, 5472`), уходит из `dataset.entityId` (5762).
  - При ручном вводе названия **не сбрасывается** - выбрал «А», перепечатал на «Б» -> уйдёт текст
    «Б» с юрлицом «А» (вывод по коду: сравнить с перевозчиком, где сброс есть, 3862-3864).
  - Строка «Новый: «...»» юрлица не несёт, но и старое не стирает.
  - При открытии заявки на правку `dataset.entityId` не заполняется из заявки - поле не
    отправляется, сервер оставляет прежнее. Если при правке перепечатать заказчика без выбора из
    списка - текст сменится, юрлицо останется старое.
  - Внутренний заказчик логиста («Кто заказывает») - юрлицо из этого ряда (5760-5761).
- Сервер не сверяет текст заказчика с юрлицом и сам юрлицо по названию/ИНН не ищет.
- Для чего нужен `customer_entity_id` сейчас: шапка договора-заявки (без него договор не
  выпускается, `order-plan-v2.js:1061`, реквизиты - `/orders/customer_entity`,
  `plan-orders.js:1689-1700`, с ленивым дозаполнением из DaData); сопоставление поступлений
  (`api/lib/receipt-attribution.js:77-80`). **Для истории адресов не используется.**
- Справочник юрлиц - ~17 тыс. записей, почти все импорт из 1С (комментарий
  `plan-orders.js` у `enrichEntityFromDadata_`).

### CRM -> заявка (`CRM.createTask`, `files/index.html:31561-31579`)
- Передаёт: `customer = client_company || client_name` (то есть при пустой компании - **имя
  человека**), `load_address/unload_address = route_from/route_to` (текст), контакт, груз, цену,
  дату, `crm_deal_id`. **Не передаёт** координаты и `customer_entity_id`.
- Пустые компания/маршрут подтягиваются из заказа 1С, если он привязан (31564, 31590-31596).
- В форме (`runPrefill`, `order-plan-v2.js:5985-5992`): история адресов запрашивается по этому
  тексту (5253), координаты - только если в тексте есть ссылка/пара чисел (5266-5267).
- Формат текста адреса в CRM другой: подсказка DaData в CRM кладёт `parts.slice(0,3)`
  («ул Промышленная, д 37, г Домодедово», `index.html:31403`), в «Задании» - полный `value` DaData
  («Московская обл, г Домодедово, мкр Центральный, ул Промышленная, д 37»,
  `order-plan-v2.js:5622`). Одна и та же точка в двух системах - две разные строки (вывод: и две
  разные записи в истории заказчика).
- Правки адреса в заявке обратно в сделку не уходят.

## 5. Калькулятор, договор, задание водителю, цена, навигация

- **Калькулятор** (`index.html:7914-7960`): свои поля погрузки/выгрузки, DaData + обратный
  геокодинг + клик по карте; в поле кладёт `parts.slice(0,3)` (7945, 7957). С заказчиком не
  связан, адресы к контрагенту не сохраняет (в просмотренном коде не найдено).
- **«Посчитать стоимость» в CRM** (`index.html:31473-31517`): заново геокодирует ТЕКСТ поля
  (первая подсказка DaData или «широта, долгота» из текста) и строит OSRM; координаты никуда не
  сохраняются.
- **Оценка цены заявки на сервере** (`api/lib/order-price-estimate.js`): берёт `load_lat/lon`, если
  есть, иначе геокодирует текст сам (приоритет Москвы/МО, «База/ДМД» = база) - 70-84, 130-133;
  найденную точку в заявку не пишет (пишет только `computed_price`, 161).
- **Навигация «Мои заказы»** (`api/lib/nav-orders.js`): свой автопоиск точки по тексту (координаты
  в тексте -> ссылка -> DaData с подрезкой текста), кэш `nav_geo_cache`; в заявку не пишет.
- **Договор-заявка**: адрес - текст без ссылки Яндекса (`contractAddrText_`, `order-plan-v2.js:
  864-867`, PDF 1316, 1321); координаты не используются; реквизиты заказчика - только через
  `customer_entity_id`.
- **Задание водителю**, два разных текста:
  - «Копировать текст» - `driverText` на клиенте (`order-plan-v2.js:4063-4090`): адрес +
    строка «Карта: https://yandex.ru/maps/?pt=lon,lat» (4079, 4084), только если есть lat/lon;
  - «Отправить в Max» - текст собирает сервер (`api/lib/logist-long-bot.js:124-150`): адрес и
    контакт, **без ссылки «Карта:» и без координат** (если ссылки нет в самом тексте адреса).
    В окне показывается первый вариант, водителю ботом уходит второй.
- **Приложение водителя** (`files/driver.html:508-510`, сервер `server.js:12401-12406`): «Откуда/
  Куда» из `plan_segs.route_from/to` - копия на момент назначения, без координат.

## 6. Где теряется или дублируется (факты кода; выводы помечены)

1. **Нет «карточки адресов» контрагента.** Память - это пересчёт последних 200 заявок по
   точному тексту названия при каждом открытии формы (п. 3.1). Нельзя закрепить «основную
   точку», переименовать, объединить, добавить комментарий «въезд с северной проходной».
2. **История привязана к тексту названия, не к юрлицу.** Другое написание заказчика - другая
   (часто пустая) история. `customer_entity_id` есть, но для подсказок не используется.
3. **Историю видно не всегда:** на ПК - только после клика по заказчику в выпадашке (ручной ввод
   названия без клика - без истории); на телефоне - ещё и не грузится при правке заявки. При
   смене заказчика вводом в списке остаются точки ПРЕДЫДУЩЕГО заказчика.
4. **Дубли одного места.** Ключ схлопывания - точная строка. Разные источники дают разные строки
   одной точки: полный `value` DaData (Задание), `улица, дом, город` (CRM, Калькулятор), ручной
   текст, текст со ссылкой, пересборка через «, » на телефоне. Нормализации (по координатам,
   по ФИАС-коду, по тексту) нет. Погрузка и выгрузка смешаны в одном списке, лимит 8 - частые
   дубли вытесняют редкие реальные точки (вывод).
5. **Координаты в истории - только из самой свежей заявки с этой строкой.** Нет - значит нет, даже
   если в старых заявках точка была.
6. **ПК: координаты не сбрасываются при ручной правке текста** (п. 1.4) - риск «новый адрес со
   старой точкой», и ссылка «Карта:» водителю ведёт не туда. Новая ссылка поверх старой
   точки не разбирается (`tryParseAddrPaste_` выходит, 5708).
7. **Телефон: правка заявки стирает координаты** (п. 2.1, вывод по коду, класс бага 26.09).
8. **Флаги `load_confirmed/unload_confirmed` мёртвые** - никто не пишет, всегда 0; пометка
   «адрес не подтверждён» фактически значит «нет координат» и только у погрузки.
9. **Юрлицо заказчика может разъехаться с текстом** (не сбрасывается при вводе на ПК; на телефоне
   сбрасывается, но не отправляется; сервер не сверяет). Из CRM заявка приходит вообще без
   юрлица и иногда с именем человека вместо компании.
10. **Координаты, найденные сервером, выбрасываются.** Оценка цены и навигация каждая сама ищет
    точку по тексту (разными правилами - цена с приоритетом Москвы, навигация с подрезкой
    текста), ни одна не возвращает её в заявку и в историю. Одна строка может дать разные точки
    в цене и на карте (вывод).
11. **Копии адреса расходятся:** `plan_segs.route_from/to` (лента, приложение водителя) не
    обновляется при правке заявки и обрезан до 200 символов (в заявке 500); CRM-сделка не
    получает правок из заявки.
12. **Задание водителю через Max - без ссылки «Карта:»**, в отличие от скопированного текста.
13. **Подсказки DaData:** 5 штук, без приоритета региона, варианты без координат отброшены;
    на телефоне нет разбора ссылок/координат вообще.
14. **Мелочи:** подпись «Мои за 30 дней» при фактических 90 днях (и у логиста/админа это все
    заявки, не «мои»); поиск заказчика и юрлица только по началу названия (`LIKE 'q%'`);
    служебные «Работа по месту»/адрес базы попадают в «точки заказчика»; отменённые заявки тоже;
    на Планировке «Откуда/Куда» - отдельный мир (32 захардкоженных города + текст отрезков).
