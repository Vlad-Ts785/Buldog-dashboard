# План: три роли логистов + фикс задвоения в дропдауне личной страницы

**Дата:** 2026-08-13
**Автор:** Клод
**Статус:** реализовано

## Часть A - фикс задвоения (скриншот Влада)

"В попавшем списке прусс задвоился, нужно это исправить" - Прус-Роскошный появлялся в
дропдауне личной страницы ДВАЖДЫ (обычной строкой и строкой "· логист").

**Причина:** ростер дропдауна (`entries`) собирался конкатенацией `D.orders.by_manager` +
`D.orders.by_logist` в двух местах (`myPageCurrentEntry_()`, `renderMyPage()`) БЕЗ дедупа.
Прус попадает в оба массива - часть его сделок в 1С помечена в поле "Менеджер по продажам"
= он же (артефакт данных), хотя его реальная роль - логист.

**Фикс:** `dedupeMyPageEntries_(rawEntries)` - при коллизии имени побеждает запись с
`type:'logist'` (реальная роль по фиксированному списку логистов, см. `.business/`).
Применена в обоих местах сборки `entries`.

## Часть B - три роли логистов

Влад: "Нужно логистов разделить на три роли:
- Логист по длинномерам: Васин. Упор от валовой прибыли.
- Логист по наёмной технике: Прус и Суркова. Упор от маржи по наёмной технике.
- Логисты своего парка тралов: Сильчев, Кан, Махура. Упор от своего парка по тралам.

Основной каркас должен быть похож (размер полоски, блок расчёта зарплаты - один формат),
но показатель на полоске - разный по флейвору. Возможно смешение ролей (форс-мажор,
подмены) - это редкое исключение, классификацию под него НЕ подстраивать."

Уточнено (AskUserQuestion, 2 раунда):
1. Формула ЗП (`calcLogist`) НЕ меняется ни для кого - меняется только показатель на
   полоске/в задачах ИИ. ЗП считается как считалась.
2. Ростер: длинномеры = Васин (уже отдельная страница/формула - вне скоупа этой задачи);
   наёмная техника = Прус + Суркова (уже `renderMyPageLogist`, без изменений); свой парк
   тралов = Сильчев + Кан + Махура (новый вариант в этой задаче).
3. "Цель" (100%) на полоске "ВП своего парка тралов" - фиксированного плана/порога в
   данных нет (в отличие от Пруса, где порог 1М маржи уже есть в `calcLogist`) - выбрано
   сравнение с прошлым месяцем (не ручной план, не полоска без %).

### Архитектура

**Бэкенд** (`scripts/full_script_final.js`):
- `logistMap` (`aggregateOrdersRows`, "── По логисту ──") - добавлены `own_profit_tral`/
  `own_profit_long`: та же логика, что `managerMap.own_profit` (прибыль 1С по НЕ наёмным
  заказам), разбита по типу техники. `by_logist` в ответе API уже сериализует весь объект
  без allowlist - новые поля попадают в JSON автоматически.
- `isOwnTralLogistName_(name)` - фиксированный список по фамилии (Сильчев/Кан/Махура), не
  data-driven - зеркало `isVasinName_`.
- `prevMonthKeyOf_(monthKey)` - чистая функция 'YYYY-MM' предыдущего месяца.
- `getOwnTralPrevMonthProfit_(ss, logistName, monthKeyOrPeriod)` - читает архивный лист
  заказов за предыдущий месяц (`getOrdersDataForPeriod`), достаёт `own_profit_tral` этого
  логиста. Тихо 0 при ошибке/отсутствии архива (первый месяц работы и т.п.).
- `buildLogistView_` - для own-tral логиста при самостоятельном входе добавляет
  `own_profit_tral_prev_month` в ответ "бесплатно" (без лишнего round-trip).
- `doGet action=own_tral_prev_month` - лёгкий lazy-fetch для admin-предпросмотра (который
  НЕ проходит через `buildLogistView_` - у него полный company-wide payload). Роль logist
  форсит своё имя (на случай ручной проверки), admin передаёт `logist` параметром.

**Фронтенд** (`files/index.html`):
- `isOwnTralLogistSur_(sur)` - зеркало бэкендового классификатора.
- `planProgressBar(...)` - новый опциональный параметр `targetLabel` (по умолчанию 'План'),
  чтобы own-tral полоска могла подписать цель "Прошлый месяц" вместо "План". Оба
  существующих вызова (менеджер, наёмная маржа логиста) не тронуты - используют дефолт.
- `ownTralPrevCache`/`loadOwnTralPrevIfNeeded_` - тот же lazy-fetch паттерн, что
  `mgrLostCache` (AI-задачи, "Пропавшие клиенты") - кэш в памяти на 'ФИО::период', не
  дёргает API повторно.
- `renderMyPageLogist` - блок полоски разветвлён по `isOwnTralLogistSur_(sur)`:
  - own-tral: факт = `lRow.own_profit_tral` (текущий месяц), прогноз = факт × paceRatio,
    "план" = `own_profit_tral_prev_month` (self-login - готово в `D.orders`; admin-
    предпросмотр - лениво из `ownTralPrevCache`, с явным "Загрузка…" пока не пришло).
    Рекомендация "сколько добирать в день, чтобы сравняться с прошлым месяцем" / "прошлый
    месяц уже превзойдён ✅" / "нет данных для сравнения" (первый месяц работы).
  - наёмная техника (Прус/Суркова) - без изменений, старая полоска "Маржа найма к премии
    &gt;1М".
  - **Расчёт зарплаты (`calcLogist`), KPI-грид, вкладки поставщики/документы/сделки - общие
    для всех логистов, без изменений** (единый каркас, как просил Влад).

## Осознанно не сделано

- AI-задачи (`buildLogistAiContext_`/`buildLogistAiTasksPrompt_`) - НЕ дифференцированы по
  флейвору в этом проходе. Не было явного запроса, а смешение ролей означает, что контекст
  наёмной техники иногда всё равно актуален для Сильчева/Кана/Махуры. Если Влад попросит
  отдельный промпт под "свой парк тралов" - отдельная небольшая задача.
- Живой вызов `action=own_tral_prev_month` не проверен вживую (нет доступа к живому Apps
  Script в этой сессии) - проверено синтетикой (см. ниже), реальную первую загрузку у
  Сильчева/Кана/Махуры стоит один раз посмотреть после деплоя.

## Проверено (синтетика, Browser preview)

- Дедуп: 5 сырых записей -> 4 после дедупа, Прус остаётся один раз с `type:'logist'`.
- Own-tral (admin-предпросмотр, Сильчев): полоска "ВП своего парка тралов", подпись цели
  "Прошлый месяц", состояние "Загрузка данных за прошлый месяц…" до резолва кэша; после
  ручной подстановки в `ownTralPrevCache` - оба сценария (отставание с рекомендацией
  "сколько в день добрать", "прошлый месяц уже превзойдён ✅") и сценарий ошибки сети.
- Own-tral (self-login, Кан, `own_profit_tral_prev_month` уже в `D.orders`): полоска и
  рекомендация рендерятся сразу, без "Загрузка…" - как задумано.
- Регрессия: Прус (наёмная техника) - полоска "Маржа найма к премии &gt;1М" и подпись
  "План: 1.0 млн ₽" не изменились. Менеджер - страница рендерится штатно.
- `node --check` бэкенда, синтаксический разбор фронтенда (`new Function` над извлечённым
  `<script>`) - оба чистые.
