**Дата:** 2026-08-27
**Статус:** архитектура v2, пишется ДО кода (Влад: "не принимай текущий UI за основу
- это прототип, а не дизайн-система").

РАБОТАЕТ, и адаптируем под то, что мы возим (негабарит: тралы/длинномеры/спецтехника).

## Аудит того, что уже есть (что оставляем, что переделываем)

Построено за 27.08 (`plans/2026-08-26-own-crm-replace-bitrix.md`,
`plans/2026-08-27-crm-product-redesign.md`):

**Оставляем как фундамент (не костыль, рабочая часть):**
- `crm_clients`, `crm_deals`, `crm_calls`, `crm_messages`, `crm_employees` - схема в
  целом верная, точечно расширяется ниже (не переписывается).
- Приём звонков Mango (`POST /api/mango/events/call`) - работает на реальных
  данных, НЕ трогаем.
- Приём сообщений Авито (`POST /api/avito/webhook/:secret`) - работает на реальных
  данных (сегодняшнее реальное сообщение подтвердило), НЕ трогаем механизм приёма,
  расширяем то, что происходит ПОСЛЕ приёма.
- Отправка сообщений (`POST /api/crm/avito/send`) - рабочий путь, переиспользуется.
- Ключевой принцип "один клиент = одна запись с одним ответственным" - это то, ради
  чего вообще уходили с Битрикса (там баг из-за разъезда контакт/сделка). НЕ трогаем.
- Push-уведомления (Service Worker, VAPID) - решают задачу "уведомление дошло, даже
  если вкладка закрыта". Дополняются внутристраничными тостами (см. ниже), не
  заменяются.

**Переделывается (было временным решением, не продукт):**
- Двухпанельный мессенджер (`crmShowView`/`loadCrmChats`/`openCrmChatThread` в
  `files/index.html`) - список чатов почти без метаданных, нет контекстной панели,
  нет статусов/фильтров/непрочитанных. Логика запросов (`/api/crm/chats`,
  `/api/crm/chat`, `/api/crm/avito/send`) остаётся, вокруг неё строится настоящий
  рабочий экран.
- Карточка сделки на канбане - `avito:467952731 / 0 ₽ / 1 зв.` - минимум
  информации. Модель данных для этого уже частично есть (client_name, amount), не
  хватает груза/маршрута/веса/даты/техники - это НОВЫЕ поля, не переделка старых.
- `crm_deals.responsible_extension` НЕ хранится - это специально (см. принцип выше),
  но у клиента (`crm_clients.responsible_extension`) хранится и readable через join
  - остаётся так же.

## Сущности

```
Client ──1:*── Deal (повторный бизнес - несколько сделок за время)
   │
   ├──1:*── Message (переписка = все сообщения client_key+channel по порядку)
   │
   └──1:*── Call (телефония Mango)

Deal.ответственный ЧИТАЕТСЯ через Client.responsible_extension, не хранится в Deal
(тот самый принцип, который убрал битриксовский баг разъезда - сохраняем).
```

### Client (`crm_clients`)
Один человек/компания, с кем когда-либо была связь. Ключ идентичности - реальный
телефон (звонки) ИЛИ `avito:<author_id>` (синтетический ключ для канала без номера).

Новые поля (Фаза 1 реализации):
- `company` VARCHAR(200) - название компании, если известно (звонок сам не даёт,
  Авито-профиль иногда даёт, менеджер может вписать вручную).

### Conversation - НЕ отдельная таблица (осознанное решение, не забытая деталь)

Влад просил архитектуру `Client → Conversation → Request → Deal`. Разбираем, что из
этого реально нужно СЕЙЧАС:

"Conversation" (переписка) уже полностью представлена как `crm_messages`,
отфильтрованные по `(client_key, channel)`. Отдельная таблица `crm_conversations`
добавила бы смысл ТОЛЬКО если бы у одного клиента одновременно было НЕСКОЛЬКО
независимых нитей на одном канале, либо нужно было бы хранить состояние переписки
отдельно от факта сообщений (например статус "закрыта вручную"). Сегодня у клиента
максимум одна активная переписка на канал - выделять сущность рано, это
переименование без новой возможности. **Помечено на Фазу 2**: если появится
необходимость закрывать/архивировать переписку независимо от сделки, или один клиент
заведёт два параллельных диалога на одном канале - тогда `crm_conversations`
оправдана, не раньше.

### Request/Lead (обращение) - тоже НЕ отдельная таблица (осознанное решение)

Роль "необращение, которое нужно разобрать - сделка или нет" сегодня уже исполняет
`crm_deals.stage = 'new'` ("Новые заявки"). Разделять на `crm_requests` +
`crm_deals` сейчас означало бы завести вторую сущность без новой функции - у "заявки"
и "сделки на стадии new" пока абсолютно одинаковый набор данных и поведения.
**Условие для выделения в Фазу 2**: если понадобится фильтровать спам/нецелевые ДО
того, как они попадут в воронку продаж (сейчас такое отклоняется уже ВНУТРИ воронки,
через стадию "Отказ" + причина) - тогда обращение и сделка разойдутся по смыслу.

### Deal (`crm_deals`)
Реальная возможность продажи: груз + маршрут + цена + стадия. У клиента может быть
несколько сделок за время (повторный бизнес), но НЕ БОЛЕЕ ОДНОЙ открытой
(нетерминальной стадии) одновременно.

Новые поля (Фаза 1 реализации) - "бриф груза", извлечённый из переписки или введённый
менеджером вручную:
- `cargo_type` VARCHAR(100) - тип груза (экскаватор, кран, трактор, спецтехника...)
- `cargo_weight_tons` DECIMAL(8,2) - вес в тоннах
- `route_from` VARCHAR(200), `route_to` VARCHAR(200) - маршрут
- `wanted_date` DATE - желаемая дата перевозки
- `vehicle_hint` VARCHAR(50) - предполагаемая техника (трал/длинномер), подбирается
  по весу/типу груза (та же логика, что уже есть в Калькуляторе - переиспользуем
  категории, не изобретаем новые)
- `brief_source` ENUM('auto','manual') - показывает менеджеру, извлечено
  автоматически или он ввёл сам (см. "Автоизвлечение" ниже) - автоматическое НИКОГДА
  молча не перезаписывает то, что менеджер поправил руками.

**Правило создания новой сделки** (закрывает найденный сегодня пробел - повторный
клиент терял сделку):
```
новый контакт (звонок Connected ИЛИ входящее сообщение Авито) от клиента:
  если клиента нет вообще            → создать клиента + сделку (stage=new)
  если клиент есть, ОТКРЫТОЙ сделки НЕТ → создать НОВУЮ сделку (stage=new) - повторный бизнес
  если у клиента ЕСТЬ открытая сделка   → ничего не создавать, это продолжение диалога по ней
```
"Открытая" = стадия НЕ в (`won`, `lost`).

### Message (`crm_messages`)
Новое поле (Фаза 1 реализации):
- `is_read` TINYINT(1) DEFAULT 0 - непрочитанное. Входящее (`direction='in'`) при
  создании = 0. Исходящее = 1 (мы сами его написали - прочитано по определению).
  Проставляется в 1 при открытии переписки менеджером.

### Call (`crm_calls`) - без изменений схемы.

### Employee (`crm_employees`) - без изменений схемы.

## API - существующее и новое

**Существующее (переиспользуется как есть):**
`GET/POST /api/mango/events/*`, `POST /api/avito/webhook/:secret`,
`GET /api/crm/deals`, `POST /api/crm/deals/stage`, `GET /api/crm/deal_detail`,
`POST /api/crm/deals/update`, `GET /api/crm/avito/chat_id`,
`POST /api/crm/avito/send`, `GET /api/crm/chats`, `GET /api/crm/chat`,
push-эндпоинты (`/api/crm/push/*`).

**Новое (Фаза 1 реализации):**
- `GET /api/crm/summary` - сводка воронки (уже реализуется параллельно с этим
  документом) - суммы по стадиям, топ причин отказа, недозвоны за сегодня.
- `POST /api/crm/messages/read` - пометить переписку клиента прочитанной
  (`client_key`) - вызывается при открытии треда.
- `GET /api/crm/unread_count` - общее число непрочитанных диалогов, для бейджа в
  сайдбаре/вкладке "Чаты" - лёгкий отдельный запрос, чтобы не тянуть весь список
  чатов ради одной цифры.
- Расширение `GET /api/crm/chats` - добавить `unread_count` на диалог, `channel`,
  `stage` связанной сделки (для статус-бейджа в списке).
- Расширение `GET /api/crm/chat` и `deal_detail` - отдать новые поля брифа груза.
- Расширение `POST /api/crm/deals/update` - принимать поля брифа
  (cargo_type/cargo_weight_tons/route_from/route_to/wanted_date/vehicle_hint) с
  проставлением `brief_source='manual'` при ручном сохранении.

## Realtime и непрочитанные

**v1 (эта реализация):** короткий опрос (10-15 сек) списка чатов, ПОКА открыт режим
"Чаты" - не вся страница, не постоянно, только пока менеджер реально там. Новое
сообщение поднимает диалог наверх списка, зажигает бейдж непрочитанного, обновляет
счётчик во вкладке. Открытие треда - `POST /api/crm/messages/read`, снимает
непрочитанное. Это НЕ WebSocket - честно назвать вещи своими именами: частый опрос,
не push. Работает, не требует новой инфраструктуры на сервере.

**v2 (документировано, не в этой реализации):** WebSocket/SSE - у нас уже есть
момент, когда сервер ТОЧНО знает о новом сообщении (сам обработчик вебхука Авито) -
можно было бы держать открытое соединение с браузером и толкать событие немедленно.
Не делается сейчас, потому что: (а) сервер сегодня без сессионного WebSocket-слоя,
это реальная инфраструктурная работа, не 15 минут; (б) до проверки на реальном
объёме сообщений непонятно, оправдан ли этот вес. Опрос 10-15 сек для текущего
объёма (единицы сообщений в день) практически неотличим от push на глаз.

## Автоизвлечение груза/маршрута/веса из текста сообщения

**v1 (эта реализация):** эвристика на регулярных выражениях по входящему тексту
Авито-сообщения при получении:
- вес: `\d+\s*(т|тонн|тонны)` 
- маршрут: паттерны "из X в Y", "X - Y", "X → Y" (первые заглавные слова после
  предлогов)
- дата: "N месяц" (русские названия месяцев) и "ДД.ММ"
- тип груза: словарь ключевых слов (экскаватор, кран, манипулятор, трактор,
  бульдозer, спецтехника...) → подсказка техники (трал/длинномер) по той же
  логике категорий, что в Калькуляторе.

Результат пишется в `crm_deals` с `brief_source='auto'`, ПОКАЗЫВАЕТСЯ менеджеру как
предположение (не факт), редактируется вручную - при ручном сохранении
`brief_source` становится `manual` и автоизвлечение по этому полю больше не
перезаписывает его.

**v2 (документировано, НЕ в этой реализации без отдельного "да" от Влада):**
LLM-извлечение через `kie.ai` (ключ уже есть в `.env`, `reference_kie_ai` в памяти
проекта - "мозг проекта", ИИ-агрегатор). Реально надёжнее регулярок (понимает
"тридцать две тонны" словами, разговорные формулировки маршрута), но добавляет
задержку и стоимость НА КАЖДОЕ сообщение живого вебхука - решение подключать это к
горячему пути принимает Влад, не молчаливое расширение бюджета.

## Данные и состояния (для UX-документа)

Статусы чата (для фильтров "Чаты"), выводятся из уже существующих полей, НЕ новая
таблица статусов:
- **Новый** = у сделки клиента `stage='new'` и ещё не было исходящего сообщения.
- **Ждёт ответа** = последнее сообщение в переписке - входящее (`direction='in'`).
- **Отвечено** = последнее сообщение - исходящее.
- **Без ответственного** = `crm_clients.responsible_extension IS NULL`.
- **Просрочен** = входящее сообщение без ответа дольше 2 часов (рабочее время) -
  тот же принцип, что SLA-бейдж "зависло" у сделок, другой порог (часы, не дни -
  чат обязан отвечать быстрее, чем двигаться по воронке).
- **Закрыт** = связанная сделка в терминальной стадии (`won`/`lost`).

## Границы этой реализации (честно, не по умолчанию "всё сделано")

Не делается в этом заходе (см. `plans/2026-08-27-crm-product-redesign.md` и раздел
"v2" по каждому пункту выше): List-представление (таблица), Аналитика как отдельный
режим, WebSocket-реалтайм, LLM-извлечение, задачи/документы/КП внутри карточки
сделки, разграничение по ролям. Каждое - реальный, но отдельный кусок работы, не
влезающий в один заход без риска сделать всё сразу плохо.
