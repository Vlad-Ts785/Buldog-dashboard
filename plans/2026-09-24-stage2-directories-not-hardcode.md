## Зачем

Одна правда живёт в 3-6 копиях: списки менеджеров отдела (сервер, Apps Script, сайт), внутренние
клиенты (расчёт, импорт, Apps Script + флаг в Справочниках), госномера спецтралов (3 версии),
ставки и пороги. Каждый новый сотрудник = правка кода в нескольких местах; забыли одно место -
тихо неправильные деньги (Гуцу/Кимличенко 22.09, Ратников в планах 04.09, Суркова в TRAL_LOGISTS).
Цель: Влад добавляет/переводит человека, клиента, машину в Справочниках - код не трогается.

## Как это сделал бы профессиональный архитектор

**Один механизм вместо десяти таблиц: «признаки с датами».** Почти все зашитые списки - это
признак объекта, действующий с какой-то даты: «сделки этого менеджера - отдел тралов», «ведёт план
продаж», «ЗП по формуле Васина», «внутригрупповой клиент», «спецтрал». Уже дважды сделано по одной
схеме (effective dating): команды продаж (`sprav_people_team_history`) и отдел машины
(`sprav_asset_department_history`). Дальше не плодим по таблице на список, а делаем:
- **каталог признаков в коде** (`api/lib/person-attrs.js`): ключ, название для экрана, описание,
  «влияет на зарплату» (такие правки - с подтверждением и эталонами);
- **одна таблица значений** `sprav_person_attrs (person_id, attr, valid_from, valid_to, value)`;
- **одна чистая функция** «список на месяц» (с тестами) и **один эндпоинт** для Apps Script и сайта;
- **один блок в карточке сотрудника** в Справочниках - «Признаки» с датами.

Варианты, которые рассматривались: (1) колонки в `sprav_people` - просто, но колонка на каждый
признак, без дат, миграция на каждый новый; (2) по таблице на список - та же болезнь, только в базе;
(3) каталог + одна таблица с датами - выбран: новый признак = строка в каталоге, история не
переписывается задним числом, один экран.

**Переезд каждого списка - «теневым режимом» (shadow mode / parallel run):** таблица засевается
ТОЧНОЙ копией константы -> код читает из базы, константа остаётся запасной -> при каждой загрузке
сервер сравнивает базу с константой и пишет расхождения в журнал -> эталоны 72/72 и
`verifyServerOrdersCalc` = 0 -> неделя без расхождений -> константа удаляется. Засев «всегда»
(valid_from 2000-01-01) даёт байт-в-байт прежние цифры: даты начинают работать только с первой
правки в Справочниках.

**Чего профессионал здесь не поставил бы:** новый список «на время» в коде; снимок значения вместо
чтения через функцию (класс бага `project_commercial_head_teams_snapshot_vs_getter_bug`); правку
закрытых месяцев без решения Влада; три копии правила сопоставления имён.

## Расхождения, которые решает Влад (меняют цифры закрытых месяцев)

Внутренние клиенты - три классификатора на реальных заказах (январь-сентябрь):
- **СТРОЙТРАНС ООО** - в Справочниках «свой» (и в юрлицах ДЗ «03. СТРОЙТРАНС ООО»), заказы считают
  клиентом: 7 строк, 353 тыс. выручки (январь-март, июнь). Свой с какой даты?
- **Панасюк Роман Викторович** - заказы: внутренний (11 строк, 509 тыс., авг-сен), Справочники не
  знают (физлицо, флаг только у юрлиц) - его поступления идут как от клиента.
- **БАЗА ДМД** - заказы: исключается целиком (56 тыс.), в Справочниках записана «База» (имена не
  сопоставляются).
Спецтралы: 3 номера (бонус Рыщанова) против 4 (Файмонвиль, «супертралы» в отчёте собственнику) -
**решено Владом 24.09:** разные понятия; бонус Рыщанова по 3 машинам - по приказу, приказ не действует,
август посчитан верно - историческое правило, в Справочники НЕ переносим, уходит при разборе зарплаты (2.6).
«Файмонвили» (4) - признак машины (2.4).

**Решения Влада 24.09 по внутренним клиентам:** сравнивать по ИНН, не по названию («СТРОЙТРАНС» - название
десятка компаний). В отчётах 1С (заказы 102 колонки, поступления, ДЗ) ИНН заказчика НЕТ - нужна колонка
«ИНН заказчика» в отчёте заказов на стороне 1С (просьба к тому, кто настраивал выгрузку); до неё 2.3 не
делаем. Панасюк - свой (внутренний): отметка «свой» будет и для физлиц.

## Риски и как проверим
- Засев не совпал с константой (опечатка, «ё») - теневое сравнение при старте + эталоны до/после.
- Подстрочное сопоставление имён (`ordInList`: 'Кан' внутри любого имени) - сохраняем как есть,
  менять семантику - отдельным шагом с решением Влада.
- Импорт и расчёт должны видеть одинаковые списки - одна функция загрузки, один модуль.
- Apps Script до 2.1б считает по своим константам - пока списки в базе не менялись, цифры совпадают;
  первая правка признака в Справочниках - только после 2.1б.
