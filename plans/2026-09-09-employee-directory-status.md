# Справочник сотрудников - статус занятости (работает/уволен)

**Дата:** 2026-09-09
**Статус:** MVP сделан и задеплоен. Полная интеграция (зарплата/планы продаж по
Апп-скрипту) - сознательно не в этом заходе, см. низ файла.

## Зачем

Живой повод: Влад увидел, что уволенная Дербенцева попала в список «Ответственный» в
CRM (после фикса пробела в `crm_employees` этим же днём). Его требование - не точечный
патч, а фундамент: «отметь менеджерами всех менеджеров... статус работает или уволен,
с датой увольнения, что бы логика функций дашборда шла через справочник».

**Как выглядит успех MVP:** уволенный сотрудник, помеченный в Справочниках, перестаёт
предлагаться на назначение в CRM И не всплывает новой строкой в Планах продаж - через
ОДНО поле в ОДНОМ месте, не разбросанные списки по каждой функции отдельно.

## Что нашли при разборе

`Справочники -> Люди` (`sprav_people` + `sprav_people_roles`) УЖЕ существовал как
канонический реестр людей с ролями (driver/manager/mechanic/logist) - Планы продаж
(`plansBuildRows_`) уже читали его для ростера менеджеров. Не хватало ровно одного:
явного статуса занятости. Заодно вскрылось: Филипчук и Ратников в этом справочнике
отсутствовали ПОЛНОСТЬЮ (не просто без роли) - добавлены.

## Что НЕ делаем в v1

- НЕ переводим зарплатную логику (`DEPT_CFG`, `COMMERCIAL_HEAD_TEAMS_` в Apps Script,
  `ACTIVE_PLAN_KEYS`/`CRM_HEAD_TEAMS_` в orders-calc.js/server.js) на чтение статуса из
  справочника - это финансовый расчёт, по правилу проекта трогается МЕДЛЕННО, с
  построчной сверкой (`plans/2026-08-18-payroll-logic-server-port.md`), не наспех вслед
  за живым багом. Отдельная задача, если Влад подтвердит объём.
- НЕ удаляем уволенного из `crm_employees`/истории сделок - его старые сделки должны
  оставаться читаемыми с его именем, меняется только его ДОСТУПНОСТЬ для НОВОГО
  назначения.
- НЕ переиспользуем `deleted_at` (мягкое удаление записи) под смысл «уволен» - это разные
  вещи (случайная правка карточки vs реальное HR-событие с датой), развели по полям.

## Сделано (09.09)

- [x] `sprav_people`: `employment_status ENUM('active','fired') DEFAULT 'active'`,
      `fired_date DATE NULL`.
- [x] `/api/sprav/state` отдаёт оба поля (только admin-срез, как остальные ПДн-поля).
- [x] `/api/sprav/person` (POST) сохраняет статус/дату, `fired_date` обнуляется, если
      статус вернули на `active` (форма не может оставить дату висеть на действующем).
- [x] Форма `Справочники -> Люди` (`drv-reg-drawer`): селект «Статус», поле «Дата
      увольнения» показывается только при статусе «Уволен(а)» (`drvRegToggleFiredDate_`,
      тот же приём, что документы водителя). Список - красная пометка «уволен(а) с
      ДД.ММ.ГГГГ» у карточки.
- [x] `GET /api/crm/employees` (список «Ответственный») - не предлагает уволенных
      менеджеров. Сопоставление `crm_employees.name` <-> `sprav_people.full_name` - по
      фамилии (первое слово), тот же приём, что `crmScope_`/`autoMeForManager` (нет
      прямого FK между таблицами). Не найден в справочнике вообще - считаем действующим
      (fail-open), чтобы не спрятать реального менеджера молча.
- [x] `plansBuildRows_` (Планы продаж) - тот же фильтр `employment_status`, уже строил
      ростер из `spravPeople_`, добавилось одно условие.
- [x] Данные: Дербенцева -> `fired` (дата пока не указана - см. открытый вопрос ниже),
      Филипчук и Ратников добавлены в справочник (роль «менеджер», отсутствовали).
- [x] Проверено вживую: карточка Дербенцевой показывает статус «Уволен(а)» в форме и
      бейдж в списке; `/api/crm/employees` её больше не отдаёт (14 из 15 менеджеров).

## Открытый вопрос Владу

Точная дата увольнения Дербенцевой - не нашлась ни в одной таблице (только дата ПРИЁМА,
2026-05-18). Стоит статус `fired` без даты - работает (её нет в списках), но карточка
пока не показывает «с какого числа». Донести дату - через саму форму в Справочниках,
код трогать не нужно.
