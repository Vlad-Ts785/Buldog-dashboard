## 2. Ключевая находка: вторая половина системы уже построена

«Планировка» (`plans/2026-08-29-logistics-planning-board.md`) - уже на сервере и в бою:
`plan_segs` (рейс на машине: госномер, kind, start_hour, length_hours, manager, logist,
route_from/to, customer, trip_mode, needs_data), поллинг 7 с, presence, история
`plan_segs_history`, сцепки `fleet_assignments`, справочники `sprav_*`, десктоп-лента в
`files/index.html` (модуль `LP`) и телефон `files/plan-m.html`. В её Фазе 4 стоит
невыполненный пункт: **«Стыковка с План задание менеджеров: заявка менеджера -> отрезок на
машине»**.

Сегодня рейс на ленте создаёт САМ ЛОГИСТ, вручную перепечатывая заказчика/маршрут/время из
Google-листа менеджера. Новый «План задания» - это недостающая **передняя половина** того же
конвейера, а не третья отдельная система:

```
МЕНЕДЖЕР                      СЕРВЕР (api.yardhub.ru)              ЛОГИСТ
создаёт заявку  ───────────>  plan_orders (новая таблица)  ──────> очередь заявок
(экран «Мои заявки»)                 │ order_id                     в Планировке
                                     ▼                                  │ drag на машину
видит: машина/водитель <─────  plan_segs (уже есть) <───────────────────┘
+ данные на пропуск            + fleet_assignments (уже есть)
+ уведомление Telegram         + sprav_people (водители, уже есть)
```

**Связь = одно поле:** `plan_segs.order_id` (nullable). Заявка - родитель, рейс на машине -
ребёнок. Одна заявка может породить несколько рейсов (несколько машин / несколько
загрузок / наёмник + своя машина). Статус «машина назначена» у заявки - производный от
наличия рейса, не вводится руками.

## 3. Два экрана (принципиальное разделение - Влад)

### 3.1 Менеджер - «Мои заявки»
Что нравится сейчас - сохраняем (Влад: «как видит менеджер, в принципе, как сейчас более-
менее устраивает»): день-вкладки / выбор даты, таблица заявок дня, «+ Новая заявка» в
шторке, «Повторить», редактирование, статус прямо из таблицы, копия данных водителя.
Что меняется: всё мгновенно (сервер, не Sheets API), статус машины/водителя приходит сам
из Планировки, уведомление «водитель назначен» (Telegram + плашка), адрес - только
нормализованный (раздел 5). Видит СВОИ заявки (админ - любого менеджера, как сейчас).

### 3.2 Логист - Планировка + очередь заявок
Влад: «им падают заявки... все логисты должны видеть все заказы... регулярно ставят машины,
могут менять, переставлять, менять местами... живая система... такой же подход, как в
планировке, чтобы можно было удобно и быстро перемещать данные».

- **Панель «Очередь заявок»** прямо в Планировке (десктоп `LP`, потом `plan-m`): карточки
  ещё не поставленных заявок на выбранный день - заказчик, тип техники, маршрут A->Б,
  время подачи, код менеджера. Видят ВСЕ логисты ВСЕ заявки (тралы/длинномеры/наёмка -
  один груз могут отработать разные).
- **Поставить = перетащить карточку на строку машины** - создаётся `plan_seg` с
  `order_id`, предзаполненный заказчиком/маршрутом/менеджером/временем (тот же лист заявки,
  что уже есть, 4.4 плана plan-m - только уже заполненный). Переставить/поменять местами/
  снять - это уже готовые жесты ленты. Снял последний рейс - заявка вернулась в очередь.
- **Таблица «Все заявки»** (день) для логиста - для обзвона/сортировки по типу техники,
  с назначением машины из списка без drag (для тех, кто не на ленте, и для телефона).
- Заявка с несколькими машинами - несколько отрезков, на карточке заявки список госномеров.

### 3.3 Общее для обоих
Карточка заявки (шторка, канон канбана) - одна и та же компонента для менеджера и логиста,
различаются только редактируемые поля по роли. История изменений («Кан изменил 12 мин
назад») - по образцу `plan_segs_history`.

## 4. Модель данных (сервер, MySQL, ручной SQL-скрипт - конвенция сервера)

`plan_orders` - заявка менеджера. Поля - 1:1 из живого Google-листа (колонки A-R, пара
строк на заказ) плюс координаты и служебные:

| Группа | Поля |
|---|---|
| Идентичность | `id` (PK, auto), `service_date` DATE, `day_no` (номер внутри дня - менеджеры так ссылаются: «третья за 5-е»), `created_by`, `created_at`, `updated_by`, `updated_at`, `deleted_at` (мягкое удаление) |
| Менеджер | `manager_name`, `customer` (текст) + `customer_key` (ключ контрагента 1С/CRM, nullable), `customer_contact` (ФИО/телефон - ПДн, только по роли) |
| Груз | `equipment_type` (Трал/Длинномер/Панелевоз/Тент/Любая модификация - строгий список из «Справочника»), `cargo`, `gabarit` (Габарит/Негабарит), `rework_terms`, `documents` (Путевой лист / +ТТН), `note`, `cash` флаг |
| Точки | `load_address`, `load_lat`, `load_lon`, `load_contact`, `unload_address`, `unload_lat`, `unload_lon`, `unload_contact` (нормализованный текст + координаты + id провайдера - раздел 5) |
| Время | `service_time` (TIME, nullable = «уточнить») |
| Деньги | `price` DECIMAL, `payment_status` (список из «Справочника») |
| Статус | `status` ENUM: `new` / `confirmed` (Подтверждено) / `cancelled` (Отбой) / `not_closed` (Не закрыто) - те же три, что в листе; `assigned` - ПРОИЗВОДНЫЙ (есть живой seg) |
| Логист | `hired_company`, `hired_vehicle`, `hired_driver` (наёмная техника - см. вопрос 2), `invoice_issued` и остальные галочки логиста из колонок O-R листа (значения уточнить у логистов при переносе, не гадать) |

`plan_orders_history` - полный снимок строки перед любым overwrite/delete (тот же приём,
что спас заявку «894» 30.08).

`plan_segs` - добавить `order_id` (nullable, индекс). Ничего существующего не менять -
контракт `/api/plan/segs` потребляют два клиента (память
`project_plan_segs_fleet_state_shared_contract`), поле только добавляется.

## 5. Умный ввод адресов (Влад: «не от балды... нормальные адреса либо координаты»)

Сейчас в калькуляторе - Nominatim (OSM) + OSRM, без ключей. Влад: «в Яндексе адреса ищутся
гораздо лучше... это важно». Решение (вопрос 3 к Владу): провайдер подсказок/геокодинга через
**серверный прокси** `GET /api/geo/suggest?q=` и `/api/geo/geocode` - ключ провайдера лежит в
`.env` сервера, во фронтенд не попадает (та же логика, что закрыла публичный ключ 21.08).
Компонент ввода - один общий для «План задания» И калькулятора (чиним обе точки разом, не
плодим два автокомплита). Поле хранит: текст как выбрал человек + нормализованный адрес +
lat/lon + id объекта провайдера. Ввод координат вручную - допустим (карьеры/поле без адреса).
Кэш повторных адресов на сервере (заказчики ездят по одним точкам).

Задел, который это открывает (Влад, «идеи вслух», НЕ в этом плане): адреса + тип техники +
цена менеджера -> автосверка с прайсом (`.business/products/pricing.md`).

## 9. Решения Влада - нужны до старта агентов

1. **Логист ставит машину ГДЕ:** очередь заявок прямо в Планировке + drag (рекомендую, это
   его же слова «как в планировке») - или отдельный экран-таблица заявок с кнопкой
   «поставить машину»? Или оба (очередь в ленте - главный путь, таблица - запасной)?
2. **Наёмная техника на ленте:** у наёмника нет строки-машины. Варианты: (а) заявка
   помечается «отдана наёмнику: компания/госномер/водитель», без отрезка на ленте;
   (б) виртуальные строки «Наёмная техника» с машинами, заводимыми на лету; (в) оба.
   Как сегодня работают Прус-Роскошный и Суркова?
3. **Провайдер адресов:** Яндекс (Геокодер + Саджест, нужен API-ключ, коммерческое
   использование - платный тариф) / DaData (подсказки, платно, лучший по РФ-адресам) /
   оставить OSM. Ключ и тариф - твоё решение; техника одна и та же (прокси на сервере).
4. **Режим теста 20-30.09:** все менеджеры и логисты переходят сразу (лист - только читать)
   или параллельно ведут оба, а мы сверяем по дням? Параллель безопаснее, но удваивает
   работу людям и размывает тест.
