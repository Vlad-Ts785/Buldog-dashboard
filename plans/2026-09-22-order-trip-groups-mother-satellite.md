# Материнская заявка + сателлиты (группы рейсов)

## Зачем

Одна машина везёт один и тот же груз по одному маршруту несколькими рейсами подряд в один
день (Влад: «не редкость - даже часто бывает»). Сейчас менеджер руками копирует строку -
источник ошибок, а на Планировке отрезки (`plan_segs`) одной машины у копий совпадают по
времени и ложатся друг на друга - ложное наложение там, где на деле последовательные рейсы.
Реальный кейс сегодня: заявки №25/№26, СЗ РЕНОВАЦИЯ ООО, один груз/маршрут/цена, разное
время - руками заведены как две несвязанные строки.

## Как выглядит успех MVP

Менеджер при создании заявки указывает количество рейсов (1/2/3/4). При N>1 система сама
создаёт материнскую заявку + (N-1) сателлитов, связанных друг с другом, с расставленным
встык временем и своей ценой на каждый рейс. Постановка машины на материнскую - одним
действием проставляет её на все сателлиты (с возможностью переназначить на отдельном
рейсе). Подтверждение/отбой материнской каскадируется на группу; отбой сателлита - не
каскадируется вверх. Тип техники синхронизирован с материнской и не редактируется на
сателлитах. Все N строк в «Задании» остаются полноценными отдельными заявками (не
сворачиваются), связь читается по строке-ссылке под «Машина · водитель» - клоном уже
существующего приёма `transferSubHtml_`/«←перенос с №X».

Все развилки замысла уже прошли Ревизора и получили ответ Влада (время 6ч/2 рейса,
5ч/3+ рейса, встык; деньги - явные поля на каждый рейс при создании; статусы - каскад вниз
от материнской, не вверх от сателлита; удаление - вне скоупа, ручная admin-функция; тип
техники - только на материнской; визуал - строка-ссылка, вариант 2 из трёх превью
https://claude.ai/artifact/57CqEHRNDRmP5MGsLM42p9). Этот план их РЕАЛИЗУЕТ, не пересматривает.

## Что НЕ делаем в v1

- Изменение состава уже созданной группы (добавить/убрать рейс постфактум) - сейчас вручную:
  обычная заявка без связи, или отбой лишнего сателлита.
- Единый договор-заявка на всю группу - Влад явно отложил («по договору пока давай
  отложим»). `contract_versions`/`contract_stale` не трогаем - каждая заявка группы получает
  свой договор по отдельности, как сейчас у любой обычной заявки.
- Настраиваемая длина/интервал рейса - сейчас жёстко 6ч (2 рейса) / 5ч (3+), без поля ввода.
- Перенос (`transfer`) ВСЕЙ группы на другой день одним действием - каждый рейс переносится
  по отдельности, как обычная заявка (существующий `/orders/transfer` не меняем).
- Любая работа над самой лентой Планировки (`files/index.html`) - сервер просто отдаёт
  корректные `start_hour`/`length_hours` через уже существующий механизм `plan_segs`, лента
  ничего не знает и не должна знать про группы.
- Валидация «сумма рейсов адекватна» - менеджер вводит цену на глаз, без проверки.

## Фаза 0 - Подготовка (данные, не код)

      `transferred_from_id` - см. `server/import/plan-orders-schema.sql`, добавление колонки
      через `INFORMATION_SCHEMA`-проверку + `ALTER TABLE ... ADD COLUMN`). У материнской -
      `NULL`, у сателлитов - id материнской.
- [ ] Константа `TRIP_HOURS_BY_COUNT_` - `{2: 6, default: 5}` (3 и более - 5ч), объявить в
      ОБЕИХ копиях (`server/api/lib/plan-orders.js` И `files/order-plan-v2.js` - тот же класс
      гочи, что уже был с `ACTIVE_PLAN_KEYS`, см. CLAUDE.md).
- [ ] Решить верхнюю границу N (чип «1/2/3/4» на превью - предлагаю ограничить сервер N≤8,
      чип с ручным вводом сверх 4 не в v1).

4 вопроса: (1) готовит фундамент, без кода - да; (2) не оверинжиниринг - одна колонка, одна
константа; (3) не усложняет - решение зеркалит `transferred_from_id`; (4) group_id/UUID
выкинут в пользу простого `parent_order_id` (1-к-N через асимметричный FK, как у переноса).

## Фаза 1 - MVP: сервер (`server/api/lib/plan-orders.js`)

- [ ] Новый `POST /orders/create_group` (или флаг `trip_count`+`trip_prices[]` в существующем
      create-пути «Задания») - принимает обычные EDITABLE-поля (заказчик/адреса/груз и т.д.,
      как сегодня) + `trip_count` (2-8) + массив `trip_prices[]` длиной `trip_count`.
      Одной транзакцией: материнская создаётся как сегодня (`price=trip_prices[0]`), затем
      сателлиты - ТЕМ ЖЕ приёмом копирования полей, что уже в `/orders/transfer` (~строка
      495: список `EDITABLE`, retry-safe `day_no` через `SELECT MAX(day_no)+1 ... FOR UPDATE`,
      3 попытки) - но `status` дефолтный (`unconfirmed`, как у обычного создания, НЕ
      `cancelled` как у transfer), `parent_order_id` = id материнской, `price` = свой элемент
      `trip_prices[]`, `service_time` = конец предыдущего рейса группы (start + `TRIP_HOURS_
      BY_COUNT_[trip_count]` часов). Вся группа - ОДНА транзакция, частичный сбой на 2-м из 3
      рейсов не должен оставлять «половину группы» без родителя.
- [ ] `createOwnExecutor()`/`executor_set`: `length_hours` для заявки с `parent_order_id`
      (сателлит) ИЛИ с детьми (материнская группы) берётся из `TRIP_HOURS_BY_COUNT_`, а не из
      `DEFAULT_TRIP_HOURS=8` - обычные одиночные заявки не трогаем.
- [ ] Пропагация машины: в `executor_set`, если у заявки есть дети (`SELECT id FROM
      plan_orders WHERE parent_order_id=?`) - после `createOwnExecutor` для материнской, тем
      же вызовом в цикле проставить ТУ ЖЕ `gos` каждому сателлиту (свой `seg` с уже
      рассчитанным `start_hour`). Если `executor_set` вызван НАПРЯМУЮ на сателлите -
      обычное поведение, без каскада (односторонне - только от материнской вниз).
- [ ] `resolveEquipmentTypeIfUndetermined_()` вызывать в том же цикле пропагации - и для
      материнской, и для каждого сателлита, если тип «Любая модификация».
- [ ] Блокировка типа техники на сателлитах: в `/orders/save`, если `order.parent_order_id`
      не пуст и в payload меняется `equipment_type` - 400 «тип техники меняется только на
      материнской заявке №X». Остальные поля сателлита редактируются как обычно.
- [ ] Каскад статуса (в существующем `POST /orders/status` или аналоге): заявка БЕЗ
      `parent_order_id`, у которой ЕСТЬ дети, при переходе в `confirmed`/`cancelled` -
      применяет тот же статус ко всем детям в той же транзакции. Заявка С `parent_order_id`
      (сателлит) - меняется только сама, без каскада вверх/в стороны.
- [ ] `attachGroupInfo_(orders)` (клон `attachTransferInfo_`) - сателлиту добавляет
      `{parent_day_no, parent_service_date, parent_order_id}`; материнской с детьми -
      `{children: [{day_no, id}, ...]}`. Вписать в `GET /orders` (list) и `GET /orders/one`,
      рядом с `attachTransferInfo_`/`attachContractInfo_`.

4 вопроса: (1) решает и наложение (разные start_hour), и ручное дублирование - да; (2) не
код ради кода - переиспользует retry-safe day_no и копирование EDITABLE из `/orders/
transfer`, не пишет параллельный механизм; (3) минимально для первой версии - один FK,
один эндпоинт, три точки каскада (машина/тип/статус); (4) выкинут `group_id`/UUID в пользу
простого `parent_order_id`, выкинута отдельная таблица «группы».

## Фаза 1 - MVP: клиент (`files/order-plan-v2.js`, `.css`)

- [ ] Форма создания заявки (`renderForm()`): чип «Рейсов» 1/2/3/4 рядом с полем
      «Стоимость» (клон `op2-chip`, дефолт «1» - при «1» форма и `saveForm()` работают

      применяется к `op2-f-price`).
- [ ] `saveForm()`: при N>1 - вызов нового `POST /orders/create_group` с массивом цен вместо

- [ ] `groupSubHtml_(o)` - клон `transferSubHtml_(o)` (та же обёртка `.op2-sub`, тот же
      `jumpToOrder_` для перехода): материнская с детьми → «рейс 1 из N · №X, №Y»
      (day_no сателлитов через запятую); сателлит → «рейс K из N · материнская №X». Вписать
      туда же, где сегодня `mgrVehCell(o) + transferSubHtml_(o)` в ячейке «Машина·водитель»
      (`renderMgr`/`renderLog`), НЕ новый визуальный класс - тот же `.op2-sub`.
- [ ] Замок типа техники на сателлитах: `techCell_(o, clickable)` (сегодняшний параметр уже
      есть от фичи quick-swap) - `clickable=false`, если `o.parent_order_id`, независимо от
      роли (логист тоже не может менять на сателлите).
- [ ] Форма редактирования сателлита: чип «Тип техники» - readonly с подписью «меняется на
      материнской №X» вместо кликабельных чипов.

4 вопроса: (1) закрывает форму создания и отображение - да; (2) клонирует `op2-chip`/
`op2-sub`/`techCell_(o, clickable)`, ни одного нового визуального паттерна; (3) N=1 не
меняет существующий путь вообще - минимальный риск регрессии; (4) выкинут drag-переставить
порядок рейсов в форме, выкинута валидация цен на клиенте (сервер и так примет любое число).

## Куда бить первым

Сервер: `parent_order_id` + `POST /orders/create_group` + три точки каскада (машина/тип/
статус) - без этого фундамента клиентские правки некуда вешать. Честная оценка времени:
миграция + create_group + каскады - НЕ «час», транзакционная осторожность (повтор
retry-safe day_no для N строк подряд, живая проверка на реальных данных) - реалистично 2-3
часа. Клиентская часть (чип рейсов + N полей цены + `groupSubHtml_` + замок типа) - клонирует
существующие паттерны почти один-в-один, около часа.
