**Дата:** 2026-09-23. **Автор запроса:** Влад. **Статус:** анализ готов, реализация не начата.
**Тип документа:** зонтичный план. Он связывает существующие планы в одну последовательность и не заменяет их:
- `plans/2026-08-19-audit-remediation.md` - страховочная сетка и безопасность;
- `plans/2026-09-01-apps-script-elimination.md` - вывод Apps Script;

Анализ делали 4 агента параллельно, только чтение: сайт, сервер VPS, Apps Script с дублированием, инженерные практики. Все цифры ниже посчитаны скриптами, это не оценки на глаз.

## 1. Термины (как это называют программисты)

| По-простому | Профессиональный термин |
|---|---|
| Дом из говна и палок | Монолит с хардкодом, «big ball of mud» |
| Дом по проекту | Модульная архитектура |
| Кирпич, который можно вынуть и заменить | Модуль / компонент |
| Каждая комната для своего | Разделение ответственности (separation of concerns) |
| Имена и пороги в справочнике, а не в коде | Конфигурация вместо хардкода, data-driven |
| Одна правда в одном месте | Единый источник истины (single source of truth) |
| Перестраиваем по комнате, продолжая жить в доме | Паттерн «Душитель» (strangler fig) |
| Проверка, что после переноса цифры те же | Эталонные тесты (golden / snapshot tests), сверка паритета |

## 2. Диагноз в цифрах

### Сайт (`files/`)
- `index.html` - **36 920 строк, 3,78 МБ**. Из них JS 80%, CSS 11%, разметка 9%. Комментариев 14%.
- 819 КБ (22% веса) - шрифты и логотип для PDF в base64. Их скачивает каждый пользователь при каждом открытии.
- ~1 200 глобальных имён (860 функций и 343 переменные) в одной общей области видимости.
- Роутер: одна функция `showPage()` с 26 `if` подряд. Кнопка «Назад» в браузере не работает.
- Встроенного в разметку: 465 `onclick="..."`, 2 277 `style="..."`, 413 сборок HTML строками.
- **Хардкод:** 104 фамилии в строках кода, 112 разрозненных проверок роли, 22 адреса сервера в 7 файлах, ~358 цветов мимо токенов (фирменный зелёный вбит вручную 59 раз).
- **Дубли:** два API-клиента с разным поведением плюс ~15 прямых `fetch`; вход через Google реализован 3 раза; `toast` - 7 копий; экранирование HTML - 16; форматирование чисел и дат - 41.
- Мобильные страницы (`orders-m`, `plan-m`) не копии, а заново переписанная логика. Совпадение с десктопом 2-11%, поэтому копии расходятся незаметно.
- Мёртвый код: старый «План задания» ~765 строк, вызовов 0.
- `index.html` менялся в 877 коммитах, 62 из них за последнюю неделю. Главная причина конфликтов параллельных чатов.

### Сервер (VPS, `/root/yard-dashboard`)
- `server.js` - 11 821 строка, 192 роута в одном файле. Ещё 66 роутов в `lib/`, всего ~258.
- SQL прямо в обработчиках: ~460 вызовов в `server.js` и ~290 в `lib/`. Отдельного слоя работы с базой нет.
- `loopbackFetch_`: сервер 30 раз ходит по HTTP сам к себе, потому что логика заперта в обработчиках.
- 225 ручных try/catch, общего обработчика ошибок нет. В 177 из 185 ответов с кодом 500 клиенту уходит сырой текст ошибки SQL.
- БД: 101 таблица, 0 внешних ключей. У 48 таблиц схема нигде не описана. Миграции не учитываются. Смешаны две кодировки сравнения строк (77 и 23 таблицы).
- Мусор: 59 `.bak` (из них 21 копия `server.js`), 7 копий `.env.bak` с секретами, 27 JSON-дампов в `api/lib`. В git 128 файлов логов и CSV с персональными данными на 22 МБ.
- Расписание разбросано по трём местам: 29 записей cron (без защиты от наложения), 5 таймеров внутри API, отдельный systemd-сервис.

### Apps Script (`scripts/full_script_final.js`)
- 12 798 строк, 339 функций. Около четверти (~3 200 строк) - разовые скрипты и мёртвые зоны: Bitrix 870 строк, «План задание» v1, бэкфиллы.
- 10 разделов сайта до сих пор не имеют серверного аналога.
- Круг зависимостей: сервер → Apps Script → лист → сервер (`month_summary`).

### Инженерные практики
- Тестовой среды нет: push в `main` через минуту уходит в прод (30-38 выкатов в сутки). Локальный просмотр ходит в боевой API.
- Автотестов 0. CI мёртвый: шаблонный workflow от чужого проекта, всегда красный.
- На сервере прямо сейчас работает незакоммиченный код (`server.js`, `owner-report.js`, `logist-long-bot.js`, ~72 строки).
- Бэкапы на том же диске, что и сервер. У git на VPS нет remote. Потеря диска = потеря кода, данных и бэкапов разом.
- Внешнего мониторинга нет. 24.08 приостановку VPS Влад заметил раньше системы.
- Токен сессии в URL: 16 мест в коде, 193 строки в логах nginx, число растёт.
- Правила живут в тексте, а не в коде: «правь в обеих копиях», «не TRUNCATE», «не DATE_FORMAT для времени». Каждое такое правило можно проверять автоматически.

### Что уже сделано хорошо (фундамент, на который опираемся)
- `orders-calc.js` и `debt-calc.js` - чистые функции со сверкой 8/8 месяцев. Образец правильной миграции.
- Вход через HMAC-сессии, общие проверки прав на 148 роутах, параметризованный SQL, API за nginx.
- Токены дизайна (`var(--` 3 576 раз), `DESIGN_SYSTEM.md`, единая точка записи данных `applyData`.
- Калькулятор, ГПБ, CRM, Планировка, `order-plan-v2` уже изолированы. CSS разделён по префиксам - готовые границы файлов.
- Справочники (`sprav_*`, `manager_plans`, `dashboard_settings`) уже есть. Хардкоду есть куда переехать.
- Git на сервере, ежедневный дамп, журнал `import_runs`, сторож свежести, тихие фолбэки.

## 4. Целевая схема («дом по проекту»)

```
Сайт (files/)                       Сервер (api/)                        База
 css/tokens.css (одна копия)          app.js, server.js (только запуск)     migrations/ (нумерованные,
 css/pages/<префикс>.css              config/  (env, роли, константы)       с таблицей учёта)
 js/core/ config · api · auth         middleware/ (вход, права, ошибки)    sprav_* = единственный
         state · router · perms       routes/<домен>.js                     источник фактов о людях,
         org · format · dom           services/ (бизнес-логика)             машинах, контрагентах
 js/pages/<страница>.js               repositories/ (весь SQL)             business_settings,
 js/modules/ calc · crm · planning    calc/ (чистые расчёты = правила)     salary_rules (по месяцам)
 js/lib/kp-fonts.js (по требованию)   jobs/ (cron + запускатель с flock)
 мобильные страницы = тот же core     tests/ (эталоны закрытых месяцев)
Apps Script: только адаптер почты «Отчет парк», потом удаляется
```

**Главный принцип:** факт живёт в одном месте, в БД. Правило живёт в одном месте, в `calc/` на сервере. Сайт только показывает готовые цифры и ничего не считает сам.

## 6. Правила перестройки (инварианты)

1. **Никакого «снести и построить заново».** Только по одной комнате, дашборд работает каждый день.
2. **Коммит переноса не меняет поведение.** Перенос кода и правка логики - всегда разные коммиты.
3. **Эталон до и после.** Каждый шаг проверяется эталонными ответами (1.4). Расхождение = откат.
4. **Старый путь выключен = этап закрыт.** Пока есть две копии, работа не сделана.
5. **Объявлять занятые файлы.** При разборе `index.html` или `server.js` на части другие чаты не правят этот же кусок (координация через `ListAgents`/`SendMessage`), иначе конфликты слияния гарантированы.
6. **Новый код сразу по новым правилам.** Любая новая фича после этапа 4.3 пишется в своём файле и через `core/`, а не дописывается в монолит. Иначе монолит растёт быстрее, чем мы его разбираем.

## 7. Чего сознательно НЕ делаем

- Не переписываем на React/Vue. Фреймворк - это смена всего дома, а проблема в планировке, не в материале (см. `project_crm_ui_target_level`).
- Не вводим сборщик (webpack/vite) и ES-модули на этапе 4: это сломало бы 465 `onclick` и добавило бы шаг, который может упасть при деплое.
- Не дробим сервер на микросервисы. Один процесс с чёткими модулями - правильный размер для команды «директор + ИИ».
- Не удаляем Apps Script целиком, пока «Отчет парк» не переведён на FTP.
