## 3. Обработка вызовов (Битрикс-коннектор)

Подвкладки: `Входящие вызовы` · `Распределение входящих вызовов` · `Исходящие вызовы` · `Ограничения`

### 3.1 Входящие вызовы

| Флаг | Сейчас | Что делает |
|---|---|---|
| Автоматически создавать лид и дело при входящих звонках | ✅ | Звонок с номера, которого нет в CRM, создаёт лид/контакт + дело. В простом режиме CRM (наш, «без лидов») создаётся **контакт**, в остальных режимах - лид. Если выключить - создаётся только дело. |
| └ Указывать источник при входящих звонках | ⬜ | Пишет источник «Звонок на номер: X». Требует заранее заведённых источников в CRM/Настройки/Справочники. |
| └ **Обновлять ответственного при переводах входящих вызовов** ⭐ | ✅ | **Только для новых (автосозданных) объектов.** При **переводе** звонка ответственным становится тот, кто принял звонок **последним**. Срабатывает только при переводе В РАМКАХ одного звонка, не когда клиент перезвонил заново. |
| └ Указать ответственного при пропущенных звонках в группу 🔒 | ⬜ | |
| └ Указать ответственного при пропущенных звонках в IVR 🔒 | ⬜ | |
| Добавлять сообщение о звонке сотруднику в чат 🔒 | ✅ | |
| Отображать карточку входящего звонка | «При поступлении звонка» | Варианты: *При поступлении* / *После начала разговора* / *Не отображать*. |

### 3.2 Распределение входящих вызовов ⭐ 🔒

Правил не настроено (пусто, «Не обрабатывать»). До 10 правил, анализируются сверху
вниз. Источник данных: данные о звонке, коллтрекинг, или **CRM** (поиск по номеру).

**Обязательное предусловие:** в схеме переадресации в начале - звуковое приветствие/
гудок/тишина **не менее 3-5 секунд** + «Ожидать окончания: Да».

**Пример 1 (наш случай):** `Клиент есть в CRM? = да` → **Переадресовать на
ответственного**. Новых клиентов - по обычной схеме.

**⚠️ КРИТИЧНО - правило берёт ответственного за КОНТАКТ/КОМПАНИЮ, а не за сделку.**
Манго ищет контакт/компанию по номеру и шлёт звонок ЕГО ответственному. Если
ответственный за контакт разъехался с тем, кто реально ведёт сделку - правило шлёт
звонок не туда. Подтверждено кейсом **7 999 988-14-56 (22.07)**: звонок принял
Котельников → сделку переназначили на Гуляеву (продала и везёт) → контакт остался на
Котельникове. Одного правила распределения мало, пока это разъезжается.

## 7. ⭐ Как решался баг "клиент звонит повторно и попадает на другого" (в Битриксе)

**Что произошло** (сделка 7 929 504-14-11, 18.07): клиент за 7 минут звонил трижды.
Первый звонок принял один менеджер (стал ответственным), следующие два - другой.
Ответственный не сменился, потому что флаг «Обновлять ответственного при переводах»
работает только при переводе внутри ОДНОГО звонка, а не при повторном наборе номера.

**Решение в рамках Битрикса** было найдено (Пример 1 распределения), но требовало
платного пакета и всё равно ломалось на разъезде контакт/сделка (раздел 3.2).

**ИТОГОВОЕ РЕШЕНИЕ (26.08.2026): не чинить Битрикс, а уйти на свою CRM** - см.
`plans/2026-08-26-own-crm-replace-bitrix.md`. Архитектура своей CRM убирает баг
СТРУКТУРНО: один клиент = одна запись с одним ответственным, нет отдельного
"контакта" и "сделки" с разными хозяевами.

## 9. ⭐⭐⭐ VPBX Integration API - как реально решили и подключили свою CRM (26.08.2026)

**Ложный след - «API: Webhooks» (2100 ₽).** Изначально показалось, что это генерик-
вебхук для приёма событий. ПРОВЕРЕНО и ОТВЕРГНУТО: тултип на вкладке «Работа со
звонками» этой услуги прямо говорит - «можете автоматизировать процесс осуществления
**исходящих** звонков **из внешней системы**». Это направление НАША СИСТЕМА → Манго
(командовать «позвони»), а не наоборот. Деньги не потрачены впустую - проверили до
оплаты.

**Правильный путь - «API коннектор»** (в «Витрине продуктов» → «Для крупных
клиентов», путь в URL буквально содержит `api-vpbx/connector` - подтверждает, что
это вход в VPBX Integration API из документации `MangoOffice_VPBX_API*.pdf`).
Список возможностей на странице совпадает 1-в-1 с нашей задачей: «Всплывающая
карточка клиента и уведомление о входящем звонке», «Умное распределение звонков»,
«Сохранение истории коммуникаций».

**Настройка (ЛК Манго → Интеграции → API коннектор → Настройки API коннектора):**
- «Уникальный код вашей АТС» (= `vpbx_api_key`) и «Ключ для создания подписи»
  (= `vpbx_api_salt`) - генерируются на этой же странице («Сгенерировать новый код и
  ключ»). ЭТО ОБЩИЙ ключ для VPBX API, отдельный от Битрикс-коннектора.
- «Разрешённые IP-адреса»: свободный доступ или ограничение по IP.
- «Версия событий»: 1 или 2. **Подтверждено тултипом в интерфейсе Манго:** «При
  выборе версии 2 убедитесь, что приложение поддерживает версию 2. События
  events/call имеют ТОТ ЖЕ формат данных, что и версия 1, но содержат БОЛЬШЕ
  параметров» - т.е. V2 это надстройка над V1, не другая схема, обратной
  совместимости достаточно для чтения только известных полей.
- Блок **«Внешние системы» → «Добавить систему»** - ЗДЕСЬ регистрируется наш URL:
  - «Адрес внешней системы» - placeholder `https://samplehost:443/path/to/name`.
    **КРИТИЧНО: это БАЗОВЫЙ URL, Манго сам дописывает хвост** (`/events/call`,
    `/events/summary`, `/events/sms`, `/events/dtmf`, `/ping` и т.д.) в зависимости
    от типа события/проверки. Наш итоговый адрес: `https://api.yardhub.ru/api/mango`
    (БЕЗ `/events/call` на конце - изначальная ошибка, исправлена, подтверждена
    логом nginx: реальные хиты с IP Манго 81.88.80.34 на `/api/mango/ping`).
  - SSL-сертификат: «Сертификат выдан удостоверяющей компанией» (у нас настоящий
    Let's Encrypt через certbot, не самоподписной).
  - «Проверить подключение» - **проверяет только базовую TCP/TLS-доступность**, НЕ
    гарантирует, что конкретный путь (`/ping`) реализован на нашей стороне. Ловушка:
    видели зелёное «Соединение установлено успешно», хотя `/ping` реально отдавал 404
    до фикса - не доверять этой галочке буквально, смотреть лог сервера.
  - **«Настроить отправку событий по звонкам»** (чекбокс, разворачивает 2
    подчекбокса): «Не отправлять уведомления о промежуточном состоянии вызова
    (events/call)» и «Не отправлять итоговую информацию по звонку (events/summary)» -
    ОБА нужно оставить НЕ отмеченными (не отмечены = событие ШЛЁТСЯ, это чекбоксы
    "не отправлять", то есть opt-out).
  - Остальные чекбоксы в том же блоке (SIP_Call_ID, DTMF, запись разговора, робот-
    статистика, адресная книга, распознавание тематик, Манго Диалоги, задания ИО) -
    тоже все "не отправлять X" (opt-out), можно оставлять как есть - не влияет на
    events/call.

**Внутренние номера сотрудников (`crm_employees`)** нужны отдельно для сопоставления
- см. раздел 2.2, вкладка «Сотрудники и группы» в ЛК Манго (НЕ тот же список, что на
странице настройки Битрикс-коннектора - это общий список сотрудников аккаунта).

**Общий номер компании для звонков клиентов: `79330918978`** (маршрутизируется в
«Группа тралы» - подтверждено «Историей вызовов» в ЛК Манго, все реальные звонки
клиентов идут именно на этот номер). Звонок МИМО этого номера (например, тест с
личного мобильного на личный мобильный сотрудника) НЕ создаёт событие VPBX API -
подтверждено тестом 26.08.2026.

**Формат события звонка** (сверено по обоим PDF, V1 и V2 совместимы):
```json
POST https://api.yardhub.ru/api/mango/events/call
vpbx_api_key = ..., sign = sha256(key+json+salt), json = {
  "entry_id": "...", "call_id": "...", "timestamp": 1558422128, "seq": 2,
  "call_state": "Connected", "location": "abonent",
  "from": {"number": "79001234567", "taken_from_call_id": "..."},
  "to": {"extension": "13", "number": "sip:...", "line_number": "sip:...", "acd_group": "303"},
  "disconnect_reason": 1131
}
```
`call_state` ∈ Appeared → Connected → OnHold → Disconnected (может пропускать
промежуточные). `disconnect_reason` коды сгруппированы: 11хх нормальное завершение,
2xxx ограничение биллинга, 32хх неверный номер, 42хх недоступен абонент, 5001
перегрузка, 5003 технические проблемы.
