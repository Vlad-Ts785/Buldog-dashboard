# План: аудит и починка UTC/МСК в отображаемых временных полях (VPS)

**Дата:** 2026-09-21
**Автор:** Клод
**Статус:** черновик

## Цель

Найти и починить ВСЕ места на сайте, где человеку показывают абсолютное время
("обновлено HH:MM", "проверено ДД.ММ HH:MM" и т.п.), а оно на самом деле хранится в UTC без
пометки и показывается без пересчёта в МСК - то есть отстаёт от реального московского
времени на 3 часа. Плюс закрепить ОДНО правило на будущее, чтобы новый код не наступал на
те же грабли.

## Контекст

21.09, вечером, Влад разбирал расхождение по контрагенту в "Плане поступлений" (баланс 5000
в дашборде, 0 в 1С - оказалось, актуальные данные уже совпадали, просто открытая вкладка не
обновилась сама). Отвечая на этот вопрос, я (Клод) сам наступил на грабли: прочитал
`import_runs.started_at` (эта таблица ХРАНИТ время уже в МСК, см. `toMysqlDate()` в
`import-log.js` - решение прошлой сессии) и ОШИБОЧНО прибавил к нему ещё +3 часа, решив, что
это UTC. Получил "19:05 МСК" вместо реальных ~16:05 МСК. Влад заметил нестыковку по своим
собственным часам (16:58) и сказал: "мы это уже обсуждали в соседней сессии... нужно это
настроить правильно".

**Уже известно и задокументировано** (`[[project_vps_utc_clock_timestamp_bug]]`, найдено
21.09 утром в другой сессии): VPS и MySQL живут по UTC (`@@global.time_zone`=`SYSTEM`,
подтверждено `date`/`Intl.DateTimeFormat` - оба честно UTC). `NOW()`/
`DEFAULT CURRENT_TIMESTAMP` пишут настоящее UTC-время в колонки, которые весь остальной код
исторически трактовал как уже готовые московские цифры. Прошлая сессия починила ТОЛЬКО
`api/lib/plan-orders.js` (поля `taken_at`/`otboy_ack_at`/`needs_data_sent_at`/
`changed_at`/`requested_at`/`resolved_at` - которые показываются человеку как "когда") и
явно оставила открытым пунктом: "тот же корень вероятно есть в Планировке (plan_segs) и в
других API-подсистемах (CRM/ДЗ/Поступления) - не проверено".

**Сегодня, живой проверкой (не догадка), подтверждено:**
- Системные часы VPS и `NOW()` MySQL - честный UTC, сейчас (21.09, ~14:00 UTC) = 17:00 МСК,
  всё сходится с реальностью. Часы НЕ сломаны.
- Проблема - не в часах, а в том, КАК приложение читает/показывает то, что в них лежит.
  Ровно 76 колонок в базе имеют `DEFAULT`/`ON UPDATE CURRENT_TIMESTAMP` (полный список
  получен через `information_schema.COLUMNS`, см. ниже) - все они хранят настоящий UTC.
- Часть кода ВОЗВРАЩАЕТ эти поля через `DATE_FORMAT(col, '%Y-%m-%d %H:%i...')` - это даёт
  ГОЛУЮ строку без всякой пометки часового пояса. Если фронтенд показывает такую строку как
  есть (или режет её `slice()`) - человек видит настоящее UTC-время, подписанное как
  московское, то есть на 3 часа МЕНЬШЕ реального. Это ПРОТИВОПОЛОЖНОЕ направление ошибки от
  моей сегодняшней (я НЕ ХВАТИЛО +3 часа для этих полей, а не наоборот).
- Другая часть кода отдаёт поле СЫРЫМ (`SELECT col` без `DATE_FORMAT`) - `mysql2` возвращает
  JS `Date`, `JSON.stringify` сам сериализует её в правильный ISO с `Z` (настоящий UTC,
  честно помеченный), и если фронтенд парсит через `new Date(iso)` + `toLocaleString('ru-RU',
  ...)` - браузер сам переводит в московское время автоматически, БЕЗ бага. Этот путь уже
  используется (и работает корректно) для `uploaded_at` (документы сотрудников/техники/
  юрлиц) и `first_visit`/`last_visit` (лог доступа).

**Подтверждённо БЕЗОПАСНО (не трогать, разбирался - работает верно):**
- `uploaded_at` (документы: `sprav_people_documents`/`sprav_asset_documents`/
  `sprav_legal_entity_documents`) - сырой `SELECT`, фронтенд `new Date(...).toLocaleDateString(
  'ru-RU')` - браузер сам переводит в МСК.
- `access_log.first_visit`/`last_visit` - тот же паттерн, `fmtVisit()` в `index.html:13778`.
- `ai_tasks_cache.generated_at` - сырой `SELECT`, фронт использует `Date.parse(...)` для
  относительного сравнения, не для показа абсолютного времени.
- `import_runs.started_at`/`finished_at` - ОСОЗНАННО хранится уже в МСК (`toMysqlDate()` в
  `import-log.js`), НЕ путать с остальными - это ловушка для ЧИТАЮЩЕГО (в т.ч. для меня
  сегодня), не для пользователя (эта таблица нигде не показывается на сайте).
- Поля дат БЕЗ времени (`%Y-%m-%d` без `%H:%i`) - `birth_date`/`hire_date`/`license_expiry`
  и т.п. - трёхчасовой сдвиг на них не действует (только полночный граничный случай, это
  ОТДЕЛЬНЫЙ известный класс багов, см. `[[project_month_boundary_bug_class]]`, здесь не
  разбирается).

**НЕ проверено сегодня (нужно пройти при выполнении плана)** - все остальные `DATE_FORMAT(...,

нужно решить: (а) не показывается человеку - не трогать; (б) показывается, но парсится через
`new Date()` - не трогать; (в) показывается сырой строкой из `DATE_FORMAT` - чинить.

## Риски

- Поле может использоваться ОДНОВРЕМЕННО для показа человеку И для программной логики
  (сравнение строк, сортировка по строке) - смена формата с "готовой строки" на "сырой
  ISO+Z" может сломать такую логику молча. Проверять оба использования каждого поля перед
  правкой, не только видимый текст.
- `plan_segs`/CRM - активно используемые прямо сейчас страницы (Планировка живая, водители
  в моменте кликают там кнопки) - деплоить точечно, не одним большим пушем всех 5 фиксов
  сразу, чтобы легче было найти виновника при регрессии.
- Полей может оказаться больше, чем 76 найденных через `information_schema` - если где-то
  время пишется через `new Date()` из Node (не через `NOW()`/`CURRENT_TIMESTAMP`) в колонку
  без дефолта, `information_schema`-запрос их не покажет. Дополнительно проверить `grep -rn
  "new Date()" api/server.js api/lib/*.js`, отфильтровать по колонкам datetime-типа.
