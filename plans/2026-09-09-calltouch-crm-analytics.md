# Calltouch + сквозная аналитика в CRM

**Дата:** 2026-09-09
**Статус:** MVP-план (навык «Зодчий»). Фаза 1 - можно строить сразу. Фаза 2+ - ждёт
входа трёх экспертных агентов (маркетолог/эргономист/РОП), см. низ файла.

## Зачем

Влад: «полагаю мы так можем отследить трафик что откуда к нам идёт» + «нужно строить
источники звонков в дашборд» + «сделай страницу сквозной аналитики в CRM - третья
вкладка после Чатов - откуда что, кто взял, кто продал, кто не продал и почему».

**Как выглядит успех MVP (Фаза 1):** на CRM-доске виден блок «Откуда звонят» с реальной
разбивкой по источникам ТОЛЬКО нашего бизнеса (негабарит, arenda-tral.ru), без чужих
номеров (экскаваторы/yard-imperial.ru), данные обновляются из Calltouch автоматически,
не руками.

## Что НЕ делаем в v1

- Не считаем стоимость лида/CPL/ROI - расходов на рекламу в системе ещё нет (Влад
  сказал «в будущем добавим затраты»).
- Не связываем звонок Calltouch со сделкой CRM 1:1 (join по телефону) - это лежит в
  основе Фазы 2, но само по себе отдельная работа с граничными случаями (один клиент
  разными номерами и т.д.) - не рискуем сделать её наспех ради Фазы 1.
- Не трогаем заявки с формы сайта - подтверждено, что форма НЕ шлёт данные в Calltouch
  (0 записей за 5+ недель по `orders-diary`). Это отдельная задача (спросить у того, кто
  ставил форму), не часть этого плана.
- Не выносим общий бюджет предупреждений/квоты Calltouch API в мониторинг - подключение
  новое, простой polling с кэшем в БД достаточен, не отдельный сервис.

### Что показываем (маркетолог + РОП, пересечение мнений)

**Первый экран - 5 метрик, не больше:**
1. Воронка по стадиям, когортно по дате СОЗДАНИЯ сделки (не снапшот текущей доски) -
   `count(stage_N)/count(stage_N-1)` для сделок, у которых `created_at` попадает в
   выбранный месяц. Существующий `/api/crm/summary.by_stage` считает снапшот, не когорту -
   нужен НОВЫЙ запрос с фильтром по `created_at`, не переиспользование as-is.
2. Win rate по когорте создания: `won / (won + lost)` среди сделок этого месяца создания -
   НЕ путать с `won_month`/`lost_month` из `/crm/summary` (те считают по дате ЗАКРЫТИЯ).
3. Средний срок жизни сделки (velocity), отдельно `won` и `lost`: `AVG(closed_at -
   created_at)` в днях. Нужна дата закрытия - есть (`closed_at`).
4. Топ причин отказа (переиспользуем `/crm/summary.loss_reasons`, уже готово) - но
   визуально выделить «Нет свободной техники» и «Дорого» отдельно от остальных
   (операционно значимые, не просто «плохой лид»).
5. Заявки без ответственного старше 1 рабочего дня (НОВАЯ метрика, которой нет ни в
   `/crm/summary`, ни в этом плане до сих пор) - `COUNT(client WHERE
   responsible_extension IS NULL AND created_at < NOW() - INTERVAL 1 DAY)`.

**Разбивки (2-3, не больше):**
- По каналу (Авито-чат / Авито-звонок / прямой звонок / звонок с сайта через Calltouch) -
  количество+сумма. Внутри «звонок с сайта» - органика/платное (то, что уже даёт
  Фаза 1), БЕЗ дальнейшей разбивки по UTM/ключевым словам - 30 звонков/мес физически не
  дают статистики глубже.
- По менеджеру/группе - это и есть ростер «взял/продал/слил», см. ниже.
- Причина отказа × стадия, на которой отказ случился (`crm_deals` не хранит историю
  переходов стадий сегодня - см. предостережение ниже, это блокер для точной версии
  этого среза).

**Что НЕ считаем сейчас:** CPL/CPA/ROI (нет бюджета рекламы - явная плашка-заглушка в
интерфейсе, не выдуманные цифры), разбивку Calltouch глубже source/medium, среднюю
сумму сделки как headline (волатильна при малом `won`), донат-диаграммы, тепловые
карты по часам/дням, ML-прогнозы, лид-скоринг, NPS-опросники, геймификацию.

### Ростер «Кто взял / кто продал / кто слил» (РОП + эргономист, единое решение)

Не таблица - список карточек-строк по менеджеру, отсортирован по «продал» по убыванию,
менеджеры без движения за период не рисуются вообще (не строки с нулями):

```
[ЕФ]  Ефремова   Взял ▬▬▬▬▬▬▬▬ 9   Продал ▬▬▬▬ 4   Слил ▬▬ 2   · чаще: «Дорого» (1)
```

- Аватар - `.kb-ava`/`AVATAR_PALETTE_` (уже есть, 2.12) - тот же цвет менеджера, что в
  канбане.
- Три bar-per-row метрики от общей левой базы, а НЕ три сегмента одной суммы (осознанное
  исключение из правила «один цвет на серию» - здесь цвет несёт семантику: «Взял» -
  нейтральный `--blue` (как и карточка «Откуда звонят», тот же смысл «объём», не оценка),
  «Продал» - `--green`, «Слил» - `--red`.
- Причина - только если «Слил» > 0, ОДНА строка мелким `--red`-текстом (самая частая
  причина этого менеджера за период) - та же анатомия, что причина отказа на карточке
  канбана (текстом под метой, не иконкой).
- Клик по строке - фильтрует таблицу сделок внизу по этому менеджеру (не новая
  сущность).
- Видимость - тот же `crmScopeSql_`, что и везде в CRM: руководителям групп (Ахтамова,
  Гусейнова) видны только их люди + свободные, менеджеру - вообще нет смысла показывать
  чужой ростер (страница по факту только для admin/руководителей групп).

**Это ЕДИНСТВЕННЫЙ реально новый визуальный паттерн на всей странице** (всё остальное -
`.mp-status`, `.kpi-grid`, bar-per-row, спарклайн, `.mp-drawer`, сортируемая таблица -
уже есть в ГОСТе). По разделу 0 п.2 `DESIGN_SYSTEM.md` - **нужно согласие Влада ДО
кода**: показать статичный HTML-мокап ОДНОЙ строки ростера (не всю страницу), дождаться
«да», только потом писать `DESIGN_SYSTEM.md` 2.18 и кодить. Это НЕ формальность - три
предыдущих захода в этой сессии на другие паттерны CRM (полка терминальных стадий)
потребовали переделки именно потому, что решение принималось без превью.

### Структура страницы (эргономист, сверху вниз)

1. Шапка страницы (стандартная анатомия ГОСТа) + переключатель периода на всю страницу
   (один период - все блоки читают из него, без собственных мини-фильтров).
2. `.mp-status` вердикт-строка - конверсия месяца словами + формула словами под ней
   (пороги цвета - согласовать с Владом, не выдумывать самостоятельно).
3. KPI-ряд (5 метрик выше) - `.kpi-grid`, та же плитка 248px, что и везде в CRM (2.14).
4. **Ростер + топ причин отказа** - сразу после KPI, сеткой `1fr/1fr` (это и есть прямой
   ответ на «кто взял/продал/слил», должно быть видно без скролла).
5. Разрез по каналам (bar-per-row) - сюда же позже встанет расход на рекламу третьей
   полосой в той же анатомии (взял/продал/слил доказывает, что формат расширяется без
   переделки).
6. Тренд - 1-2 спарклайна максимум (сделок/выручки по месяцам), не отдельная страница
   графиков.
7. Таблица сделок внизу - сортируемая (канон раздела 4), фильтры по стадии/менеджеру/
   каналу, клик по строке - `.mp-drawer` (карточка сделки уже есть, переиспользуется).

Звук - регистр `soundsD` («деликатный»), не `sounds5` - это BI-экран для просмотра, не
CRM-действие вроде переноса сделки (решение эргономиста, проговорить с Владом одной
строкой при сдаче, не «новый паттерн»).

### Известный блокер перед реализацией (не найден экспертами - найден при синтезе)

РОП просит «средняя длительность каждой СТАДИИ по менеджеру» и разрез «причина ×
стадия отказа» - оба требуют **истории переходов стадий с таймстампами**, которой
СЕЙЧАС в `crm_deals` нет (хранится только текущая стадия + `updated_at`). Без неё эти
два конкретных пункта посчитать нельзя - либо заводить `crm_deal_stage_history`
(таблица, `deal_id`, `stage`, `entered_at`) с записью при каждом `POST
/crm/deals/stage`, либо сознательно вычеркнуть эти два пункта из Фазы 2 и оставить в
Фазе 3. Решить это ДО начала кода Фазы 2 - другие метрики (когортная воронка, win rate,
velocity целой сделки, ростер) этой истории не требуют и не блокируются.
