# Перенос показа сайта с GitHub Pages на свой VPS + приватный репозиторий

**Статус:** в работе
**Одобрено:** Влад, 2026-09-13 - продолжение разговора про защиту кода от кражи. Цель - убрать
GitHub как публичную витрину (историю коммитов, Apps Script, документы, планы), при этом не
уронить `yardhub.ru`, которым пользуется вся компания каждый день. Правило сессии - "мягкая
посадка": на боевой домен переключаемся только после того, как всё проверено в обход него.

## Разведка (сделана 13.09, до написания плана)

- **DNS `yardhub.ru`** сейчас указывает на IP-адреса GitHub Pages (`185.199.108/109/110/111.153`),
  отдельного стороннего CDN/прокси перед сайтом нет - кэш 10 минут из CLAUDE.md это встроенный
  CDN самого GitHub Pages (Fastly), не что-то дополнительное.
- **SSL-сертификат** сейчас автоматически выпускает и продлевает GitHub (Let's Encrypt).
- **DNS домена управляется через Beget** (`ns1/ns2.beget.ru`) - тот же провайдер, что держит VPS,
  менять A-запись предстоит в той же панели.
- **На VPS уже стоит и работает Nginx** (слушает 80/443, судя по всему проксирует `api.yardhub.ru`)
  - не нужно ничего ставить с нуля, только добавить новый server-блок.
- **Ресурсы VPS с большим запасом**: 2 CPU (загрузка 0.01-0.05), 3.8 ГБ RAM (2.7 ГБ свободно/в
  кэше), 24 ГБ свободного диска из 38 ГБ. Отдача статики - на порядок легче того, что сервер уже
  держит (MySQL, Node API, cron-импорты).
- **Что реально нужно копировать на сервер** (проверено по факту в репозитории, не по памяти):
  корневой `index.html` (редирект на `files/index.html`), `CNAME`, `.well-known/assetlinks.json`
  (проверка Android-приложения), и весь `files/` - `index.html`, `app.html`, `driver.html`,
  `plan-m.html` + их `*.webmanifest`, `sw.js` (service worker - PWA), `logo.png`, `icon-192.png`,
  `icon-512.png`, `manifest.json`, `order-plan-v2.css`/`.js`, `tshub.apk`. Это больше, чем один
  дашборд - есть мобильные страницы и Android-приложение, все должны переехать вместе.

## Фазы

### Фаза 1. Подготовка сервера - без риска для боевого сайта
- [ ] Сгенерировать отдельный SSH-ключ на VPS для чтения репозитория (`deploy key`, read-only,
      НЕ тот же ключ, что уже используется для SSH-доступа человека на сервер).
- [ ] **Влад добавляет публичную часть ключа** в GitHub - Settings репозитория -> Deploy keys ->
      Add deploy key (без права записи). Это единственный шаг, который нужно сделать руками через
      веб-интерфейс GitHub, не автоматизируется без токена с админ-правами на репозиторий.
- [ ] `git clone` репозитория на VPS в отдельную папку (например `/root/site-yardhub`) через этот
      ключ - разовая проверка, что доступ работает.
- [ ] Добавить в Nginx новый `server` блок для `yardhub.ru`, указывающий `root` на склонированную
      папку - ПОКА без реального DNS и без SSL на этот блок (слушает, но пока никто по-настоящему
      на него не попадёт, кроме явного обращения по IP+заголовку Host).
- [ ] Проверить `curl -H "Host: yardhub.ru" http://<IP-сервера>/` и `.../files/index.html` -
      сравнить с тем, что реально отдаёт текущий `https://yardhub.ru/` (размер, содержимое).

**Откат:** ничего не трогали снаружи, боевой сайт не задет - просто не продолжать дальше.

### Фаза 2. SSL-сертификат ДО переключения DNS (нулевой простой)
- [ ] Получить сертификат Let's Encrypt для `yardhub.ru` через `certbot` в режиме **DNS-01**
      (не HTTP-01) - это НЕ требует, чтобы домен уже указывал на сервер. Certbot покажет
      TXT-запись, которую нужно добавить в DNS.
- [ ] **Влад (или я по его команде) добавляет TXT-запись** в панели Beget - разовое ручное
      действие, у Beget может не быть готового плагина certbot, поэтому вручную надёжнее.
- [ ] Подтвердить в certbot после появления записи - сертификат выпущен, лежит на сервере,
      Nginx настроен использовать его для `server_name yardhub.ru`, но домен ещё указывает на
      GitHub - реального трафика через него пока нет.

**Откат:** сертификат просто лежит неиспользуемым, ничего не сломано.

### Фаза 3. Проверка живьём через домен - БЕЗ публичного DNS (файл hosts)
- [ ] Влад временно правит файл `hosts` на своём компьютере (одна строка, точную инструкцию дам
      в момент действия) - только у него локально `yardhub.ru` начинает указывать на IP VPS,
      для всех остальных в интернете домен по-прежнему идёт на GitHub как раньше.
- [ ] Полная поблочная проверка в браузере на реальном домене: вход через Google, дашборд,
      калькулятор, CRM, Планировка, мобильные страницы (`app.html`/`driver.html`/`plan-m.html`),
      что PWA/service worker не показывает битый кэш.
- [ ] Вернуть `hosts` в исходное состояние после проверки.

**Откат:** правка только на одном компьютере, ничего публичного не менялось.

### Фаза 4. Переключение DNS
- [ ] В панели Beget поменять A-запись `yardhub.ru` с IP GitHub Pages на IP VPS.
- [ ] Дождаться распространения (проверять `nslookup`/`dig` до совпадения).
- [ ] Проверить `curl https://yardhub.ru` с обычного интернет-канала (не с самого сервера) -
      реальные посетители видят новый сервер, HTTPS уже валиден (сертификат готов с Фазы 2).
- [ ] Мониторить 15-30 минут после переключения - errors в логах Nginx, реальный заход кого-то
      из сотрудников.

**Откат:** вернуть A-запись обратно на IP GitHub Pages - GitHub Pages по-прежнему настроен и
работает (мы его не трогали), сайт вернётся на прежнюю схему в течение того же времени
распространения DNS.

### Фаза 5. Обновление кода на сервере при каждом пуше
- [ ] Решить механизм: вебхук GitHub -> скрипт на сервере делает `git pull` автоматически, ИЛИ
      добавить ручной `git pull` на сервере в наш обычный чек-лист после фичей, которые трогают
      `files/`/корневые HTML-страницы (пока не понадобится автоматизация - меньше движущихся
      частей на старте).
- [ ] Проверить на одной реальной правке "конец в конец" - я пушу в `main`, файл обновляется на
      сервере, виден на живом `yardhub.ru`.

### Фаза 6. Приватность репозитория - только после нескольких спокойных дней на новой схеме
- [ ] Переключить видимость репозитория на GitHub с Public на Private.
- [ ] Проверить: мой `git push`/`git pull` по-прежнему работает (личный доступ не теряется при
      приватности - её теряют только посторонние), деплой-ключ сервера по-прежнему может читать,
      сайт продолжает работать (он уже не зависит от GitHub Pages вообще).
- [ ] Сообщить, если есть другие параллельные сессии/сотрудники с доступом к репозиторию -
      приватность может неожиданно закрыть им доступ, если они заходили как посторонние
      (маловероятно, но стоит проверить список коллабораторов перед переключением).

### Фаза 7. Цикл после фичи (обязательно)
- [ ] Security review: кто имеет доступ к деплой-ключу на сервере, права на файлы, не остался ли
      где-то старый публичный ключ/токен от прежней схемы.
- [ ] Проверить `curl yardhub.ru` (та же проверка, что нашла исходную проблему с калькулятором) -
      убедиться, что переезд ничего лишнего не открыл.
- [ ] Ретроспектива.

## Что сознательно НЕ входит в этот план

- Обфускация/минификация клиентского JS - отдельная опциональная задача, обсуждали как низкий
  приоритет (поднимает порог для любопытного, не для решительного).
- Полный переезд самого git с GitHub на свой сервер (Gitea и т.п.) - не обязателен для достижения
  цели "код не гуляет публично", GitHub-приватности достаточно; можно рассмотреть отдельно, если
  Влад позже захочет полной независимости от GitHub как компании.
