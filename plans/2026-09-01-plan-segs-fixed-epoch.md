# Планировка: постоянная (не месяц-относительная) эпоха для `start_hour`

**Статус:** в работе, дедлайн **до 8 сентября 2026** (см. "Срочность" ниже).
**Обнаружено:** параллельной сессией (`debtor-page-dynamics-ddeba7-56`), 01.09.2026,
верификация агентом-исследователем на живом сервере. Независимо подтверждено в этой
сессии (см. "Проверка фактов" ниже).

## Проблема

`plan_segs.start_hour` хранится как **часы от полуночи 1-го числа МЕСЯЦА ЭПОХИ** - но
сама эпоха НИГДЕ не хранится (ни колонки в БД, ни отдельной таблицы). Она вычисляется
ЗАНОВО на КАЖДОЙ загрузке страницы, в браузере, из текущей даты:

```js
// files/index.html, ~19670 (fix от 01.09, этой же сессией, раньше)
var EPOCH_GRACE_DAYS_ = 7;
var EPOCH_ANCHOR_ = new Date(NOW0_.getTime() - EPOCH_GRACE_DAYS_ * 86400000);
var YEAR = EPOCH_ANCHOR_.getFullYear(), MONTH = EPOCH_ANCHOR_.getMonth();
var EPOCH0_ = new Date(YEAR, MONTH, 1);   // "час 0" всей ленты
```

Комментарий в `api/server.js` (~2348) прямо признаёт это осознанным временным решением:
"конверсия эпох при смене месяца входит в план запуска с 1 сентября, следующий шаг" -
шаг не был сделан.

**Ранний сегодняшний фикс (`EPOCH_GRACE_DAYS_=7`) НЕ решает проблему, только откладывает
её на неделю.** До 7 сентября включительно `NOW0_ - 7 дней` остаётся в августе, эпоха =
1 августа. **8 сентября** `NOW0_ - 7 дней` = 1 сентября - эпоха скачком переходит на
сентябрь, и ВСЕ уже сохранённые `start_hour` (посчитанные от 1 августа) реинтерпретируются
как посчитанные от 1 сентября - визуальный сдвиг на 31 день (744 часа) вперёд для КАЖДОЙ
записи. Тот же класс бага, что уже ловили 1 сентября (см. память
`project_month_boundary_bug_class`), просто с недельной отсрочкой.

## Проверка фактов (эта сессия, 01.09, до начала работы)

  реальных данных на 01.09, эпоха = 1 августа 2026).
- `plan_segs_history.action` - только `'overwrite'`/`'delete'`, НЕТ `'create'` (подтверждён
  второй факт из отчёта коллеги) - создание новой записи не оставляет исторического следа,
  ОТДЕЛЬНАЯ проблема (см. "Не входит в эту задачу" ниже).
- Найдена **1 аномальная запись** при проверке: `s1-ab5e6f84` (В 325 МХ 797, kind=repair,
  `start_hour=-1442.00`, `length_hours=2659.50`, `updated_at=2026-08-31 21:56:15`) - это
  ≈ 1-3 июля 2026 (за 60 дней до текущей эпохи) с длительностью ≈110 дней, отредактирована
  ВЧЕРА. Похоже на баг ввода (см. известный пункт полировки UI - "datetime-input
  откладывает сам", `project_logistics_planning_ui_polish_backlog`), не связано с эпохой
  напрямую - **проверить/поправить ДО миграции**, чтобы не тащить мусорное значение в
  постоянную эпоху молча.

## Решение: разделить "нулевую точку часов" и "видимое окно ленты"

Сейчас ОДНА переменная (`EPOCH0_`/`YEAR`/`MONTH`) отвечает СРАЗУ за две разные вещи:
1. Смысл цифры в `start_hour` (должен быть НАВСЕГДА неизменным).
2. Какой месяц(-а) физически рисуются на ленте (должен плавно сдвигаться со временем -
   иначе через год лента будет пытаться отрисовать 12+ месяцев ячеек).

Фикс - развести их:

```js
// НАВСЕГДА фиксировано - выбрано РАВНЫМ текущей живой эпохе (1 августа 2026), поэтому
// МИГРАЦИЯ ДАННЫХ НЕ ТРЕБУЕТСЯ - смысл существующих start_hour не меняется, просто
// перестаёт "уезжать" при следующей смене месяца.
var EPOCH0_ = new Date(2026, 7, 1);   // 1 августа 2026, 00:00 - раз и навсегда
function hourToDate_(h){ return new Date(EPOCH0_.getTime() + Math.round(h * 60) * 60000); }
function dateToHour_(dt){ return (dt.getTime() - EPOCH0_.getTime()) / 3600000; }

// Видимое окно ленты - ПО-ПРЕЖНЕМУ today-relative (та же грация в 7 дней, чтобы не
// дёргать раскладку сетки рывком в полночь 1-го), но это ТЕПЕРЬ только вопрос "что рисуем",
// не "что значит число" - на смысл start_hour больше не влияет.
var VISIBLE_ANCHOR_ = new Date(NOW0_.getTime() - EPOCH_GRACE_DAYS_ * 86400000);
var VISIBLE_YEAR = VISIBLE_ANCHOR_.getFullYear(), VISIBLE_MONTH = VISIBLE_ANCHOR_.getMonth();
var WINDOW_START_H_ = dateToHour_(new Date(VISIBLE_YEAR, VISIBLE_MONTH, 1));  // смещение окна от EPOCH0_
```

Всё, что сейчас рисует сетку/позиционирует плитки по формуле "час 0 = левый край ленты"
(`renderScale()`, hour→pixel в `renderRowsInner_`, создание сегмента через drag/шторку),
нужно провести через `- WINDOW_START_H_`, а не считать, что `EPOCH0_` = начало видимой
области. Это единственная реально трудоёмкая часть - нужен построчный аудит мест,
использующих `HOURS`/`DAYS`/`hourToDate_`/`dateToHour_` (порядка 15-20 мест по прошлой
сессионной сверке).

**Почему миграция БД не нужна:** `EPOCH0_` выбран РАВНЫМ уже действующей сейчас эпохе
(1 августа), т.е. смысл существующих чисел в `plan_segs.start_hour` НЕ МЕНЯЕТСЯ - только
код перестаёт пересчитывать эту точку заново каждую загрузку. Это делает фикс кодовым
рефакторингом, не рискованной миграцией живых данных (в отличие от неудачного захода
"сдвинуть -744 часа" этой же сессией раньше сегодня, который был откачен).

**Часовой пояс:** `new Date(2026, 7, 1)` - локальное время БРАУЗЕРА (Europe/Moscow для
всех реальных пользователей), т.е. 1 августа 2026 00:00 MSK = 31 июля 2026 21:00 UTC.
Любой код на сервере (Node/MySQL, оба в UTC), интерпретирующий `start_hour` независимо от
фронтенда - ОБЯЗАН использовать именно этот сдвиг, не наивную UTC-полночь.

## Не входит в эту задачу (отдельные, менее срочные проблемы)

- `plan_segs_history` не пишет `action='create'` - новые записи без истории до первого
  overwrite/delete. Не блокирует эту задачу, но не забыть отдельным заходом.
- Аномальная запись `s1-ab5e6f84` - разобраться ДО деплоя фикса (см. выше), не блокирует
  сам дизайн, но её значение может исказить первую сверку "ничего не уехало" после деплоя.

## Координация с параллельной работой

`debtor-page-dynamics-ddeba7-56` строит `vehicle_status_daily` (ежедневный снимок статусов
машин из `plan_segs`+`fleet_assignments`) и должен интерпретировать `start_hour` тем же
способом. Т.к. `EPOCH0_` после фикса = 1 августа 2026 00:00 MSK и данные НЕ мигрируют - их
снимок, построенный СЕЙЧАС против текущей (уже верной) эпохи, останется корректным И
ПОСЛЕ деплоя этого фикса без изменений с их стороны. Сообщено им напрямую (SendMessage,
01.09) с точной формулой ДО реализации, по их просьбе.
