# План: ускорение страницы Васина + прогноз выполнения плана ВП

**Дата:** 2026-08-11
**Автор:** Клод
**Статус:** реализовано, ждёт деплоя

## Цель

1. Ускорить загрузку личной страницы Васина - сейчас она делает лишнюю работу.
2. Добавить широкую шкалу "Выполнение плана ВП (длинномеры)" с прогнозом к концу месяца - по
   аналогии с "Выполнение плана продаж" на странице менеджера.

## Контекст

Влад: "Очень долго загружаются его страницы". Диагноз - `renderMyPageVasin` (см.
plans/2026-08-11-vasin-long-haul-page.md) на каждую загрузку делает ВТОРОЙ отдельный запрос
`action=long_haul_detail`, который внутри СНОВА гоняет полный `getOrdersData`/
`getOrdersDataForPeriod` (тяжелейшая функция дашборда - десяток агрегатов по всем строкам
Заказы_данные) - хотя ПЕРВЫЙ запрос (вход как `logist`, `getLogistView_`) уже посчитал ровно
то же самое один раз. Итого: 2 полных прогона агрегации заказов + отдельный HTTP round-trip
(своя цена открытия таблицы + проверки токена) на каждую загрузку страницы.

## Реализация

### Бэкенд - убрать дублирование
- `buildLongHaulBundle_(ss, orders, period)` - вынесено из `getLongHaulDetail_`, принимает УЖЕ
  загруженный `orders` (не грузит сам).
- `buildLogistView_(orders, logistName, ss, period)` - новые параметры `ss`/`period`; если
  логист - Васин, сразу прикладывает `orders.long_haul = buildLongHaulBundle_(...)`,
  переиспользуя уже посчитанный `orders` - без повторного `getOrdersData`.
- `getLogistView_`/`getLogistViewForPeriod_` прокидывают `ss`/`period`.
- `getLongHaulDetail_` остаётся (для admin-предпросмотра прошлого периода, см. ниже), но тоже
  использует `buildLongHaulBundle_`.

### Фронтенд - убрать лишний round-trip
- `renderMyPageVasin` становится СИНХРОННОЙ (как renderMyPageManager/renderMyPageLogist), без
  своего кэша/асинхронной загрузки:
  - роль `logist` (сам Васин) - читает `D.orders.long_haul` (уже пришёл с логином/
    `my_page_period`, ничего сверх обычного цикла страницы качать не нужно);
  - роль `admin`, текущий месяц - собирает бандл КЛИЕНТСКИ из уже загруженных `D.orders`
    (`long_funnel`/`by_driver_no_waybill_long`/`all_long_deals`/`summary.long_*` - там же, где
    и company-wide данные) + `D.vehicles` (уже загружены на дашборде, фильтр по типу "Борт") +
    `D.summary.profit_long` - ноль дополнительных запросов;
  - роль `admin`, прошлый месяц - `setMyPagePeriod` при выборе Васина ДОПОЛНИТЕЛЬНО дёргает
    уже существующий `action=vehicles_period` (используется "Техникой", не новый код) для
    машин за диапазон дат, кэширует вместе с `orders_period`; диспетчер `renderMyPage()`
    подменяет `D.vehicles` на время рендера тем же приёмом, что уже подменяет `D.orders`.
- `vasinDetailCache`/`vasinDetailLoading`/асинхронный `long_haul_detail`-fetch - удалены за
  ненадобностью.

### Прогноз плана ВП
- Новый широкий блок "Выполнение плана ВП (длинномеры)" (тот же визуальный компонент
  `planProgressBar`, что у менеджера) - факт/план берутся суммой по той же таблице машин, что
  уже выводится ниже (Σv.profit / Σv.plan) - гарантированно совпадает с таблицей, без
  рассинхрона источников. Прогноз - через `calcPaceRatio_(D.orders.period)`, тот же приём, что
  везде в дашборде.

## Критерии готовности

- [ ] Страница Васина (роль logist, реальный вход) грузится ОДНИМ запросом, без второго
      "Загрузка данных по длинномерам…".
- [ ] Admin-предпросмотр текущего месяца - без единого доп. запроса.
- [ ] Цифры не изменились (сверка со старой версией на тех же синтетических данных).
- [ ] Прогноз плана ВП показывает факт/план/прогноз, согласован с таблицей машин.

## Итог

- **Реализовано целиком:** да.
- **Что сделано:**
  - Бэкенд: `buildLongHaulBundle_` принимает уже загруженный `orders`, `buildLogistView_`
    прикладывает `orders.long_haul` для Васина без повторного `getOrdersData`.
  - Фронтенд: `renderMyPageVasin` стала синхронной (как остальные личные страницы) - роль
    `logist` читает `D.orders.long_haul` (уже пришёл с логином/`my_page_period`), роль `admin`
    на текущем месяце собирает бандл из уже загруженных `D.orders`/`D.vehicles`/`D.summary`
    (ноль запросов), на прошлом - `setMyPagePeriod` донагружает машины через существующий
    `action=vehicles_period` только когда выбран Васин.
  - `vasinDetailCache`/`vasinDetailLoading`/асинхронная загрузка - удалены.
  - Прогноз "Выполнение плана ВП (длинномеры)" - `planProgressBar`, факт/план суммой по той же
    таблице машин, что на странице, прогноз через `calcPaceRatio_`.
  - Проверено в браузере на синтетике с явным перехватом `apiFetchJson` (кидает ошибку на
    неожиданный вызов) - подтверждено: admin+Васин+текущий месяц = 0 запросов (было 2, включая
    полный повторный пересчёт заказов), admin+Васин+прошлый месяц = 2 запроса параллельно
    (`orders_period`+`vehicles_period`, было тоже 2, но последовательно и с лишним пересчётом),
    logist-роль (сам Васин)+текущий = 0, +прошлый = 1 (было 2). Регрессия: Прус (1 запрос,
    без vehicles_period) и обычный менеджер - не задеты.
- **Что не сделано и почему:** не покрыт редкий edge-case - admin переключил период на
  НЕ-Васине, потом в дропдауне выбрал Васина (машины для того периода не подгружены) - показывает
  пустую таблицу машин вместо дозагрузки; сознательно не стал усложнять ради редкого
  admin-тестового сценария, реального Васина (роль logist) это не касается.
- **Что добавить в бэклог:** нет.
- **Уроки:** "два похожих personal-page запроса" - явный сигнал искать переиспользование уже
  загруженных данных вместо второго прогона тяжёлой агрегации; стоило спроектировать так
  сразу в прошлой итерации, не дожидаясь жалобы на скорость.
