# План: Живые поступления/списания с банковского счёта (Oplata BULDOG)

**Дата:** 2026-08-28
**Автор:** Клод
**Статус:** в работе (Фазы 1-2 готовы, Фаза 3 - настройка телефона Владом)

## Цель

Банковские уведомления СберБизнеса (сейчас летят через телефон в Telegram-группы
«Поступления БУЛЬДОГ» / «Списания БУЛЬДОГ») должны в реальном времени попадать на
дашборд: живая лента движения по счёту, «Поступления сегодня» считаются из банка
(быстрее 1С), уведомление звук+плашка при новой операции.

## Контекст

- 1С-отчёт по поступлениям приходит на сервер ~раз в час - Влад видит деньги в
  Telegram раньше, чем на дашборде.
- Правило источников (Влад, 2026-08-28): **сегодняшние поступления считать из
  банковских СМС, всё, что старше 1 дня - только из 1С.** Банковская лента не
  заменяет 1С-историю, это «живой верхний слой» на сегодня.
- Отправитель - приложение-пересыльщик СМС на телефоне с банковской симкой (бот
  Oplata BULDOG - собственный, настраивал Влад). Ключевое ограничение Telegram:
  бот не видит сообщения других ботов в группе, поэтому читать группу нашим ботом
  нельзя. Путь: приложение шлёт то же сообщение ВТОРЫМ получателем - HTTP POST на
  `api.yardhub.ru` (webhook). Telegram-канал не трогаем вообще.
- Формат сообщения (пример, поступление):
  `СберБизнес. Поступление 75000,00р на р/с*31367 с р/с*00110 по документу №2208
  от 28.08.2026 от ООО "НОВОТЭК" . Баланс 205040,12р 28.08.2026 10:58:28
  (Входящее - 0321 Банк клиент Бульдог (Мобильный))`
  Списание - тот же шаблон со словом «Списание». В сообщении есть Баланс -
  показываем живой остаток по счёту.
- Уведомления: на дашборде (звук + плашка), по ГОСТу DESIGN_SYSTEM.md раздел 8.
  Web-push - отложено (инфраструктура VAPID уже есть с CRM, включим потом).

## Фазы

### Фаза 1. Сервер: приём и хранение (~1 час)
- [x] Таблица `bank_operations`: id, direction (in/out), amount, counterparty,
      doc_number, account_own, account_from, balance_after, occurred_at,
      received_at, raw_text, parsed (0/1), dedup_hash UNIQUE.
- [x] `POST /api/bank/sms` - приём от телефонного приложения. Авторизация отдельным
      секретом `BANK_SMS_KEY` (header ИЛИ `?key=` - многие приложения не умеют
      заголовки). Принимает JSON/форму/сырой текст, поле с текстом ищем по
      типовым ключам (text/message/body/sms/content).
- [x] Парсер СберБизнес-формата (регэксп). Нераспознанное - тоже сохраняем
      (parsed=0), чтобы не терять и дообучить парсер.
- [x] Дедупликация: hash(текст без хвоста времени доставки) UNIQUE - повторная
      доставка от приложения не создаёт дубль.
- [x] `GET /api/bank/operations` (checkSession): операции за сегодня/вчера +
      сводка (сумма in/out за сегодня, последний известный баланс, время
      последней операции).
- [x] Бэкап server.js перед правкой, `node --check`, рестарт, смоук-тест curl,
      запись в `/root/yard-dashboard/README.md`.

### Фаза 4. Опознание менеджера по контрагенту + личные страницы (Влад, 29.08)

Обсуждение (2026-08-28, "Дай обратную связь") и решение Влада 29.08: "Запускаем и
сразу делаем на личные странички менеджеров". Механизм опознания уже год работает
для 1С-поступлений (`resolveManager`/`managerByKey`/`normalizeClientName` в
`api/server.js`, "последняя сделка выигрывает") - переносим на банковский контрагент,
не изобретаем заново. Эмпирически проверено (28.08): между 1С-поступлениями и
1С-заказами совпадение 96.8% (181/187), но один из промахов - "НОВОТЭК" - из-за
формы собственности В КОНЦЕ названия ("НОВОТЭК ООО" в заказах против "ООО
"НОВОТЭК"" в банке) - это и есть главный ожидаемый источник промахов на банковском
канале, не кавычки (кавычки есть и в 1С-данных, туда матчинг попадает нормально).

- [ ] Сервер: `normalizeClientNameForBankMatch_` - как `normalizeClientName`, ПЛЮС
      допускает форму собственности и в начале, и в конце названия. Отдельная
      функция, не трогаем существующий `normalizeClientName` (96.8% не рисковать).
      Проверить на тех же 187 именах перед деплоем - не должно стать хуже.
- [ ] Кэш `managerByKey` в памяти сервера (TTL ~15 мин, не пересчитывать 3-табличный
      UNION на каждую входящую СМС) - переиспользовать между `/api/bank/sms` и
      будущими вызовами.
- [ ] `bank_operations.matched_manager` (новая колонка) - резолвится ОДИН РАЗ при
      приёме СМС (`POST /api/bank/sms`), не на каждом опросе `/api/bank/operations`.
      Только для `direction='in'` (списания опознавать незачем).
- [ ] `GET /api/bank/operations` - отдаёт `matched_manager` в каждой строке `ops`.
- [ ] Новый клиент (нет в базе) - НЕ опознаётся, поле пустое, это ожидаемо и не
      требует отдельной обработки (та же конвенция, что "Не определён" в 1С-таблицах).

- [ ] Личные страницы менеджеров: вкладка «Поступления» (уже существует, показывает
      1С-историю ЭТОГО менеджера) - добавить СВЕРХУ новую живую карточку "Поступления
      по компании сегодня": ВСЕ входящие по компании (не отфильтровано по менеджеру -
      "все менеджеры видят все поступления"), БЕЗ списаний, БЕЗ остатка по счёту (не
      просили, решил не показывать - более чувствительная цифра, чем поток входящих).
      В каждой строке - фамилия/имя менеджера, если контрагент опознан.
- [ ] Поллинг банковской ленты запускается и для роли `manager` (не только `admin`).
- [ ] Победная сцена (ГОСТ 1.3/1.4, та же градация по сумме) летит в KPI этой новой
      карточки, когда менеджер реально на вкладке «Поступления» - иначе (другая
      вкладка/страница) как и у админа: фанфара+тост без хореографии, без анимации.
      Списания у менеджеров вообще не озвучиваются и не толкают тост (только `in`).
- [ ] Тост (админский и менеджерский) - добавить фамилию менеджера рядом с
      контрагентом, когда опознан.
- [ ] Прогнать чек-лист приёмки DESIGN_SYSTEM.md раздел 10 для новой карточки.

## Критерии готовности

- [ ] Реальная операция с телефона появляется на дашборде без обновления страницы
      (в пределах минуты поллинга).
- [ ] «Поступления сегодня» на дашборде = сумма банковских поступлений за сегодня.
- [ ] Дубль-доставка не задваивает сумму.
- [ ] Звук+плашка срабатывают при новой операции, по ГОСТу.
- [ ] Данные старше сегодня нигде не изменились (1С-канал не тронут).
- [ ] Запись в README сервера и DEPLOY_LOG.

## Риски

- Приложение на телефоне не умеет webhook - есть запасной путь (канал+бот-админ
  или userbot), контракт эндпоинта не меняется.
- Формат СМС банка изменится - нераспознанные сообщения сохраняются с parsed=0,
  видно в БД, парсер дообновляем.
- Телефон выключен/без интернета - лента молчит, «Поступления сегодня» должны
  тихо падать обратно на 1С-цифру, если банковских данных за сегодня нет.
- Секрет в query-string - допустимо для машинного webhook, но в инструкции
  предпочесть заголовок, если приложение умеет.
