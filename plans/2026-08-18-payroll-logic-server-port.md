# Перенос расчётной (зарплатной) логики заказов на сервер

**Статус:** в работе
**Одобрено:** Влад, 2026-08-18 - "перенести расчёт на сервер... глобально мы переходим на
работу на сервере а не на гугл таблицах". См. `../ai-clone` память
`project_server_migration_strategy.md` и статус в `CLAUDE.md` ("Архитектура данных").

## Зачем и почему осторожно

Замер (см. `DEPLOY_LOG.md`, запись 227/229-230) показал: смена периода на "Обзор заказов"
занимает ~26 сек, из них ~15 сек - НЕ чтение данных (сервер уже отдаёт сырые заказы за
0.6 сек), а сама сборка (`aggregateOrdersRows`) внутри Apps Script - CPU, не I/O. Перенос
данных на сервер это не ускорит; ускорит только перенос самого РАСЧЁТА туда же (Node.js
на VPS быстрее V8-песочницы Apps Script на порядок для такой нагрузки).

Это САМАЯ рискованная часть всего переезда - от неё зависит зарплата людей. Прецеденты:
- Суркова дважды выпадала из `TRAL_LOGISTS` при малейшей правке списков → реальные потери
  в зарплате логиста.
- Порог "23%" (квалификация бонуса по марже найма) регрессировал дважды.

**Правило этого плана: НИКАКОГО "с виду работает - переключаю".** Каждая фаза - построчная
сверка нового расчёта против старого (уже проверенного, живого) на РЕАЛЬНЫХ данных, для
МНОГИХ периодов, не только одного месяца. Расхождение больше пары свежих заказов (как было
с сырыми данными) = стоп, разбираться, не переключать.

## Что переносим (Фаза 1 - заказы: зарплаты/планы/воронка менеджеров и логистов)

Функции в `scripts/full_script_final.js`, переносим 1-в-1 (без "улучшений" по дороге -
это отдельная и более поздняя задача, если вообще нужна):
- `aggregateOrdersRows(rows)` - ядро, ~350 строк, вся структура ответа (by_manager,
  by_logist, by_day, doc_status, funnel, lost_customers-заглушка и т.д.)
- `joinManagerPlans_(ss, result, monthKey)` + `getManagerPlans_(ss, monthKey)` - подтяжка
  плана из листа "Планы_менеджеров" (маленький, 796мс - НЕ бутылочное горлышко, но нужен
  для полноты ответа)
- `computeSalesFaktPlan_(periodOrders)` - факт/план продаж для верхней полосы
- `computeLostCustomers_(ss, currentRows, monthKey)` - использует АРХИВНЫЙ лист предыдущего
  месяца (`Заказы_YYYY-MM`) - для месяцев, где такого листа нет (январь-май, будущие после
  отключения старого канала) нужен эквивалент через `orders_archive`/`orders_normalized` на
  сервере, ищущий предыдущий месяц там же

НЕ переносим в этой фазе (сознательно, отдельная задача/не сейчас):
- `getGrossProfitForPeriod`/`getStaffData`/`aggregateFinHistoryForRange` (Штатка/История_
  финансов - "Валовая прибыль", "Маржа") - тоже в очереди по стратегии, но другой источник
  данных (не заказы), другой риск-профиль, отдельная фаза плана или отдельный план.
- Любые "улучшения" логики по дороге - если что-то выглядит как баг в текущей логике,
  фиксируем находку, но НЕ чиним попутно - меняем только площадку исполнения.

## Константы, которые должны остаться идентичными

`TRAL_MANAGERS`, `TRAL_LOGISTS`, `INTERNAL_CLIENTS` - уже скопированы в
`import-orders-raw.js`/`import-orders-jan-may.js` на сервере (с явным предупреждением о
регрессиях в комментарии). Для aggregateOrdersRows понадобятся ЕЩЁ константы изнутри неё
(пороги бонусов, `WAYBILL_SKIP_IF_REALIZ`, `FUNNEL_EXCLUDE_OTHER_PAYMENT_VARIANT`,
`FUNNEL_EXCLUDE_CASH_PAYMENTS`, любые проценты/пороги) - переносить ВМЕСТЕ с функцией,
одним диффом, не по памяти.

## Фазы

### Фаза 1a. Портирование (Node.js, без прод-трафика)
- [ ] Скопировать `aggregateOrdersRows`, `joinManagerPlans_`, `getManagerPlans_`,
      `computeSalesFaktPlan_`, `computeLostCustomers_` в новый файл на сервере
      (`/root/yard-dashboard/api/lib/orders-calc.js` или как модуль `server.js`) - максимально
      дословно, только синтаксис `Utilities.formatDate`/`ss.getSheetByName` заменить на JS-
      эквиваленты (даты - через уже проверенный `toDateStr`/дневной формат, планы - через
      SQL-таблицу-зеркало листа "Планы_менеджеров", см. Фазу 1b).
- [ ] Планы_менеджеров - новый одноразовый + затем регулярный (раз в день? Влад вносит
      руками раз в месяц, не нужен FTP) импорт листа в MySQL-таблицу `manager_plans`
      (month_key, manager, plan) - простой формат, низкий риск (просто SUM-таблица).

### Фаза 1b. Новый эндпоинт `/api/orders_computed?period=YYYY-MM`
- [ ] Использует уже существующий `/api/orders_raw` внутри себя (тот же источник, что и
      сейчас - normalized/archive автоматически), прогоняет через портированный расчёт,
      отдаёт JSON в ТОЧНО том же формате, что `action=orders_period`/`getOrdersData()`.

### Фаза 1c. Сверка (ОБЯЗАТЕЛЬНА до переключения хоть одного пользователя)
- [ ] Для каждого доступного периода (июнь, июль, август, январь-май - 8 месяцев) сравнить
      ПОЛНЫЙ JSON старого (`action=orders_period`/живой расчёт Apps Script) и нового
      (`/api/orders_computed`) - не только общие суммы, а КАЖДОЕ поле в `by_manager`/
      `by_logist`/`funnel_*`/пороговые флаги (`hired_margin_qualifies` и подобные).
- [ ] Отдельно - проверка на "сегодняшний" текущий месяц несколько раз в течение дня (чтобы
      поймать не только статичные архивы, но и живые донасчитывающиеся данные).
- [ ] Любое расхождение - записать в `DEPLOY_LOG.md`, разобрать причину, не считать
      "видимо, погрешность" без объяснения (см. `[[no-conclusions-without-row-level-
      verification]]`).

### Фаза 1d. Включение (постепенно, с мгновенным откатом)
- [ ] Тот же приём, что и для `orders_raw` - фронтенд/Apps Script сначала пробует сервер,
      тихий фолбэк на старый путь при любой ошибке/расхождении. Механизм включения -
      Script Property (как `YARD_API_KEY`), можно выключить одной командой без редеплоя
      фронтенда.
- [ ] Первую неделю - держать ОБА расчёта живыми параллельно, логировать оба результата
      (не показывать пользователю, только для последующей сверки), прежде чем доверять
      серверу единолично.

## Риски и как их снижаем

- **Денежный риск (зарплата/бонусы)** → построчная сверка Фазы 1c обязательна, никаких
  исключений "и так похоже".
- **Расхождение списков менеджеров/логистов между копиями** → уже есть прецедент (Суркова).
  Хранить константы только В ОДНОМ месте после переноса - как только серверный расчёт
  становится основным, Apps Script-копию списков можно считать вторичной (но не удалять,
  пока не отключим старый канал полностью).
- **`computeLostCustomers_` для месяцев без архивного листа** (январь-май, будущее без
  старого канала) → отдельная разработка эквивалента через MySQL до включения для этих
  периодов; для июня-августа архивные листы есть, там не блокирует.
- **Даты/instanceof Date** → уже наступали на эти грабли в этом переезде (см.
  `project_apps_script_date_instanceof_gotcha`) - `orders_raw` уже отдаёт чистые
  YYYY-MM-DD строки, портированный код должен ожидать СТРОКИ, не Date, с самого начала
  (не копировать `instanceof Date` проверки без надобности).
