# Структура коммерческого отдела - из данных, не из хардкода

Влад, 22.09: "Я хочу что бы фундаментально у нас все правильно работало а не хардкор в
коде. Допустим у нас не 10 сотрудников а 30 пришло. Мы приняли их и они были встроены в
структуру не хардкором а выбором где они находятся у какого руководителя в команде. Сделай
пока структурно коммерческий отдел. Да и добавим Гуцу к Айнур а Сергея к Лиане.
Соответственно все логики например видеть в задании своих или видеть зп своих и т.п. должны
качественно сработать."

Повод: искал, к кому прикреплены новые менеджеры (Гуцу, Кимличенко) - оказалось, они нигде
не прописаны, потому что состав команд Ахтамовой/Гусейновой захардкожен фамилиями в коде.

## Что нашлось при разборе - ЧЕТЫРЕ копии одного и того же списка, не три

1. `api/server.js` (VPS) - `COMMERCIAL_HEAD_TEAMS_` (константа, строка ~10118).
2. `api/server.js` (VPS), **тот же файл** - `CRM_HEAD_TEAMS_` (строка ~4014) - ОТДЕЛЬНАЯ,
   независимая копия того же состава для видимости заявок CRM (`crmScope_`). Уже расходится
   потенциально при правке одной, но не другой - классический
   `project_orders_calc_vps_sync_gotcha`, только про людей, не про заказы.
3. `scripts/full_script_final.js` (Apps Script) - `COMMERCIAL_HEAD_TEAMS_`.
4. `files/index.html` (фронтенд) - `DEPT_CFG` (несёт ещё цвет/имя/`solo`, не только состав).

## Решение - тот же паттерн, что уже есть для техники

`sprav_assets.department` уже решает ровно такую же задачу для машин (пусто = Тралы, любое
значение - другой отдел, правится в Справочники → Материальные средства, без деплоя кода).
Делаем зеркально для людей.

### 1. Схема (VPS MySQL)

`ALTER TABLE sprav_people ADD COLUMN commercial_head VARCHAR(60) NULL` - фамилия
руководителя группы, нижним регистром (`'ахтамова'`/`'гусейнова'`) или NULL (нет команды).
Сама Ахтамова/Гусейнова - самореференс (`commercial_head='ахтамова'` у неё же) - так её
фамилия автоматически входит в собственную команду, без спецкейса в коде.

Миграция данных - ОДИН SQL, переносит ТЕКУЩИЙ состав `COMMERCIAL_HEAD_TEAMS_` 1-в-1 (никто
не должен "потеряться" при переходе):
```sql
UPDATE sprav_people SET commercial_head='ахтамова'
  WHERE full_name REGEXP '^(Ахтамова|Цегельников|Гуштюк|Дербенцева|Шейко)';
UPDATE sprav_people SET commercial_head='гусейнова'
  WHERE full_name REGEXP '^(Гусейнова|Савиток|Филипчук|Котельников|Гуляева|Коньшина|Володин)';
```
Сверка после миграции: количество затронутых строк должно точно совпасть с числом фамилий
в старых списках (5+7=12).

### 2. Бэкенд (`api/server.js`) - минимальный по риску рефактор

`COMMERCIAL_HEAD_TEAMS_` остаётся ТЕМ ЖЕ идентификатором и той же формой
(`{ахтамова: [...surs], гусейнова: [...surs]}`) - меняется только ОТКУДА берётся значение,
не как её читают. Все существующие потребители (`commercialHeadTeam_`,
`receiptsPlanCallerHead_`, `/api/receipts_plan/summary`, `buildManagerPayload_`) продолжают
работать без изменений.

```js
let COMMERCIAL_HEAD_TEAMS_ = {};
async function refreshCommercialHeadTeams_() {
  const [rows] = await pool.query(
    "SELECT full_name FROM sprav_people WHERE employment_status='active' " +
    "AND commercial_head=? AND deleted_at IS NULL", [head]); // группируем по каждой голове
  ...
  COMMERCIAL_HEAD_TEAMS_ = map;
}
```
Вызывается: (а) один раз при старте сервера (await до `app.listen`), (б) раз в 5 минут
таймером - страховка, (в) СРАЗУ после успешного `POST /api/sprav/person`, если
`commercial_head` изменился - изменение видно без ожидания таймера (тот же принцип, что
`accessCache_.set(...)` сразу после входа в `/api/auth/google`).

`CRM_HEAD_TEAMS_` - удаляется целиком, `crmScope_` читает `COMMERCIAL_HEAD_TEAMS_` напрямую
(убирает саму возможность второй копии разойтись с первой).

`/api/sprav/person` (`GET`/`POST`) - добавить `commercial_head` в `peopleCols` (список) и в
`INSERT`/`UPDATE`/`ON DUPLICATE KEY UPDATE` (сохранение), с проверкой - либо пусто, либо
фамилия существующего действующего менеджера (не любая строка).

Новый лёгкий эндпоинт `GET /api/commercial_head_teams` (`checkSession`, без ограничения по
роли - список фамилий не ПДн) - фронтенд использует его для построения `DEPT_CFG.members`
и для самого выпадающего списка "к какому руководителю" в форме Справочников.

### 3. Фронтенд (`files/index.html`)

`DEPT_CFG` перестаёт быть плоским литералом - состав (`members`) строится из
`D.orders.commercial_head_teams` (или отдельного вызова `/api/commercial_head_teams`, если
проще не раздувать `/api/main_payload`), цвет/отображаемое имя головы остаются маленьким
статическим стилевым конфигом (`HEAD_STYLE_`) - это НЕ орг.структура, а дизайн-решение
("какого цвета плитка Ахтамовой"), трогается только когда заводят СОВСЕМ новую голову
группы (событие редкое и всё равно требует решения о цвете/названии от Влада, не то же
самое, что "куда прикрепить Гуцу"). Тихий фолбэк на старый литерал, если сервер почему-то
не прислал новое поле (тот же приём "тихий фолбэк", что у всей остальной миграции на
сервер).

Затронутые места (17 использований `DEPT_CFG`) - все продолжают работать НЕИЗМЕННО, т.к.
меняется только откуда берутся `members`, не форма/интерфейс `DEPT_CFG`:
`renderSalesMgrLegacy_`/`renderSalesMgrGost_` ("По менеджерам"), `currentCommercialHeadCfg_`
(личная страница руководителя группы - зарплата 0.8% с выручки группы, ДЗ, план
поступлений), видимость меню/court/менюTierKey_.

### 4. Справочники - UI выбора (вместо хардкода)

Форма "Добавить/Править сотрудника" (`drv-reg-*`) - новый блок `drv-reg-manager-fields`,
видимый только когда включена роль "Менеджер" (тот же приём, что `drv-reg-driver-fields`
для роли "Водитель"): `<select id="drv-reg-commercial-head">` с опциями "— нет команды —" /
"Ахтамова Лиана" / "Гусейнова Айнур" (список голов - из `/api/commercial_head_teams` или
статики `HEAD_STYLE_`, их всего 2, пересчитывать динамически пока не нужно). Значение -
`commercial_head` в `params` при сохранении (`drvRegSave_`), прочитано при открытии формы
(`drvRegOpenForm_`).

### 5. Apps Script (`scripts/full_script_final.js`) - ОСОЗНАННО не переводим на БД

Тот же принцип, что уже применялся 15-16.09 (Дьячков/тралы, таймаут входа): Apps Script -
редкий фолбэк (сервер отдаёт `by_manager`/main_payload первым для всех ролей, включая
manager, с 11.09). Полный перевод на динамический запрос к MySQL из Apps Script
непропорционально дорог для fallback-пути. Компромисс - ОДНОЙ строкой добавить Гуцу/
Кимличенко в существующий хардкод-список ТАМ (чтобы фолбэк не был откровенно НЕВЕРНЫМ для
них конкретно), не строить динамику. Если/когда Apps Script полностью выключат
(`plans/2026-09-01-apps-script-elimination.md`) - вопрос закрывается сам.

## Проверка

- Миграция: количество строк с новым `commercial_head` после UPDATE = 12 (5+7), имена
  совпадают построчно со старыми списками.
- `GET /api/commercial_head_teams` - тот же состав, что раньше был в
  `COMMERCIAL_HEAD_TEAMS_` литерале (сверка построчно, "не сдвинулось").
- Живой тест (форджед токен) - Ахтамова/Гусейнова видят СВОЮ команду (Отдел Тралы, ДЗ,
  зарплата 0.8%, "Задание") без изменений в цифрах ДО и ПОСЛЕ миграции - если разошлось,
  где-то забыт консьюмер.
- Через UI Справочники добавить Гуцу → Гусейнова, Кимличенко → Ахтамова - НЕ прямым SQL,
  чтобы заодно проверить сам механизм (форма → `/api/sprav/person` → кэш обновился →
  видно в `/api/commercial_head_teams` без перезапуска сервера).
- После добавления - живой запрос под Гусейновой/Ахтамовой: Гуцу/Кимличенко видны в составе
  группы («Отдел Тралы», «По менеджерам», ДЗ команды).
- `node --check` на все 3 script-блока `files/index.html`, синтаксис `api/server.js` на
  VPS перед restart.
