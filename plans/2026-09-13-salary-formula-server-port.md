# Перенос формулы зарплаты (окладByRev/calcMgr/calcLogist/calcRyschanow/calcVasin) на сервер

**Статус:** в работе
**Одобрено:** Влад, 13.09 - находка аудита безопасности (5 параллельных агентов): точные формулы
и проценты зарплат КОНКРЕТНЫХ ПОИМЕНОВАННЫХ сотрудников лежат открытым текстом в публичном
`files/index.html` (2% vs 1.5% у Цегельникова/Савитка, пороги окладов, все бонусы) - доступно
любому анонимному `curl` без логина. Тот же класс проблемы, что калькулятор (`plans/2026-09-11-
calculator-server-migration.md`), но серьёзнее - персональные данные о зарплате людей, не
коммерческая тайна компании.

## Почему это ОСОБЕННО осторожно, отдельно от общей осторожности переноса

CLAUDE.md прямо называет зарплатную логику "самой рискованной частью всего переезда" (см.
`plans/2026-08-18-payroll-logic-server-port.md` - тот перенос был про АГРЕГАЦИЮ заказов на
сервер, этот - про уже отдельный слой: РАСЧЁТ САМОЙ ЗАРПЛАТЫ из уже агрегированных данных).
Прецеденты из той же категории риска: Суркова дважды выпадала из списков менеджеров при мелкой
правке, порог "23%" регрессировал дважды. **Правило то же: НИКАКОГО "с виду работает -
переключаю". Построчная сверка на реальных данных для многих месяцев, не одного.**

## Важный нюанс, отличающий это от калькулятора

Сырые числа по каждому менеджеру/логисту (`amount`, `own_profit`, `hired_margin_qualified` и
т.д.) УЖЕ приходят авторизованному пользователю через API (`D.orders.by_manager`/`by_logist`) -
это не новая утечка данных, доступ к ним и так требует логина. Проблема именно в том, что САМА
ФОРМУЛА (кто на каком проценте, все пороги) видна БЕЗ логина, любому анонимному посетителю
сайта, через статический файл. Значит после переноса: авторизованный сотрудник по-прежнему
видит СВОЙ посчитанный результат (и, если админ - результаты всех), но саму методику расчёта
(проценты, пороги, кто на какой ставке) браузер получать не должен вообще - только готовое
число и разбивку по компонентам (оклад/комиссия/бонус - это можно отдавать, не выдавая формулу,
которой они посчитаны).

## Что переносим

Из `files/index.html`, район строк 18201-18380 (сверять по факту, могло сдвинуться):
- `okladByRev(rev)`, `mgrRate(sur)`, `splitRev(m, isPrus)`, `isNewRulesPeriod(period)`,
  `calcMgr(sur, includeOklad, getM, getL, useNewRules)`, `calcLogist(sur, getL, useNewRules)`,
  `calcRyschanow(grossProfit, qualMarginAllLogists, useNewRules, specialTralsProfit)`,
  `calcVasin(profitLong)`.
- Связанные константы: `NEW_RULES_FROM='2026-07'`, ставки 0.02/0.015 (Цегельников/Савиток
  vs остальные), пороги оклада 2М/5М/8М/10М -> 30к/50к/100к/150к, бонус 100к при обороте
  ≥15М, 8% квалифицирующей маржи найма, пороги Прус-Роскошного 10%/7% при марже >1М,
  логисты 500₽/заказ + оклад 20к + премия 30к при марже >1М, Рыщанов 100к + ступени по 50к/5М
  + 2% маржи логистов + 1% ВП спецтралов, Васин 2.5% ВП длинномеров компании.

Точки вызова в клиенте (все нужно переключить, не только одну):
- `calcMgr()` - строки ~8915 (личная страница менеджера, факт), ~8954 (прогноз), ~18616/18621
  (вкладка "Зарплата"/карточка отдела).
- `calcLogist()` - ~9797 (факт), ~9936 (прогноз).
- `calcVasin()` - ~10510 (личная страница).
- `calcRyschanow()` - внутри `renderRyschanowDeptCardHtml_` (карточка отдела, используется и
  вкладкой "Зарплата", и личной страницей Рыщанова/Сильчева).

**Не переносим в этой задаче:** саму агрегацию заказов (`by_manager`/`by_logist` - уже на
сервере, `api/lib/orders-calc.js`) - трогаем только слой "уже агрегированные числа -> итоговая
