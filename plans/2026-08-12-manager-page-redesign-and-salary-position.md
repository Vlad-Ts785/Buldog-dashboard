# План: расчёт зарплаты сразу после KPI-блоков + новая личная страница менеджера (Савиток)

**Дата:** 2026-08-12
**Автор:** Клод
**Статус:** реализовано, ждёт деплоя

## Цель

1. Общий принцип для всех личных страниц (сделанных и будущих): блок расчёта зарплаты сразу
   после блоков с информацией, не в самом низу.
2. Полная переработка личной страницы МЕНЕДЖЕРА (на примере Савитка) - новая структура и
   новый функционал.

## Контекст

Влад, дословно (сжато): расчёт зарплаты - сразу после KPI-блоков. Начинаем разработку
страницы менеджера на примере Савитка:
- Первым - выполнение плана, с добавкой: сколько нужно делать в рабочий/выходной день, чтобы
  догнать план (в выходной объём падает - т.е. не поровну).
- Дальше - отдельный блок с расчётом ЗП, "такой же длинный", прямо с вкладки "Зарплата".
- 4 старых блока (Заработал/Документы/Дебиторка/Заказы по технике) - не нужны.
- Вместо них - один большой блок с вкладками (как "Обзор заказов"): Топ заказчиков /
  Пропавшие клиенты (все, кто заказывал за 3 месяца и не заказывал 2+ недели, сортировка по
  выручке) / Дебиторская задолженность (тот же блок, что общий ДЗ, но только по этому
  менеджеру, с фильтрами по дням/объёму, общее ядро с ДЗ) / Воронка документов.

## Критерии готовности

- [ ] У Савитка на личной странице: план (с рабочий/выходной таргетом) → зарплата (детально)
      → вкладки (топ/пропавшие/ДЗ/воронка), 4 старых блока отсутствуют.
- [ ] "Пропавшие клиенты" - 3 месяца, >14 дней тишины, сортировка по выручке.
      Сверено на синтетике вручную.
- [ ] ДЗ-вкладка даёт те же суммы, что глобальная ДЗ, отфильтрованная по этому менеджеру
      (сверка тотала).
- [ ] Зарплата на новом блоке = зарплата на вкладке "Зарплата" для того же человека/периода.

## Риски

- ДЗ per-manager - реальный "общее ядро" достигается переиспользованием
  `computeDebtAggregates_`/`debtDeadAndStatus_`, а не копией всего рендера global ДЗ (там же
  график истории/тренды/"что изменилось", это не имеет смысла для одного человека) - вкладка
  будет проще визуально, чем глобальная ДЗ, но с той же логикой сумм/дней.
- Соотношение будни/выходные для расчёта таргета - эвристика (из company-wide `by_day`),
  не точная формула - будет скорректирована, если Влад увидит нереалистичные цифры.
