# План: импорт заказов - слияние по номеру заказа вместо перезаписи

**Дата:** 2026-08-06
**Автор:** Влад (постановка) / Клод (реализация)
**Статус:** в работе

## Цель

Заказ, который наш импорт хоть раз увидел, больше никогда не должен молча исчезнуть из
`Заказы_данные`/архивов, даже если следующий отчёт 1С его почему-то не содержит.

## Контекст

Найдено при разборе расхождения 40 000₽ в выручке Савиток за июль (`diagnoseSavitokJuly`,
`findMissingSavitokOrders`): заказ №468973 (40 000₽) отсутствует ВЕЗДЕ - ни в
`Заказы_2026-07`, ни в других листах. Влад открыл заказ в 1С: создан 30.06.2026 10:24, а
"Начало работ" - 01.07.2026 (перевозка на стыке месяцев).

**Механизм потери.** Комментарий в `importOrdersReport()` (`scripts/full_script_final.js`)
подтверждает: "с 1С теперь может приходить сразу несколько месяцев в одном файле (прошлый +
текущий - окно для коррекций до 5-6 числа)". То есть 1С сама уже умеет присылать заказы
"на стыке" - НО только узкое окно в начале месяца. Если наш `runAll()` не подхватил этот заказ
именно в те несколько дней, пока 1С ещё включала июнь в файл вместе с июлем - после закрытия
окна коррекции заказ, созданный 30.06, больше никогда не попадёт ни в один отчёт (1С фильтрует
по дате создания, "Начало работ" тут не при чём).

**Но даже если бы мы его поймали** - весь пайплайн построен на замене, не накоплении:
- `importOrdersReport()`: `raw.clear()` → пишет ТОЛЬКО то, что в сегодняшнем файле от 1С.
- `normalizeOrders()`: `norm.clear()` → пишет ТОЛЬКО то, что распознано из raw сегодня.
- `writeArchiveSheet()`: `archive.clear()` → пишет ТОЛЬКО то, что передано сегодня.

Ни один из этих шагов не сверяется с тем, что уже было записано раньше. Если 1С хоть один
день не включит ранее видимый заказ в отчёт (не только из-за окна коррекции - мало ли какая
причина на стороне 1С) - при следующей перезаписи этот заказ исчезнет из дашборда навсегда,
даже если мы его уже видели и сохраняли.

## Фазы

### Фаза 1. Функция слияния по ключу "Номер заказа" (~20 мин)
- [ ] `mergeOrderRowsById_(existingRows, newRows, idColIndex)` - чистая функция: берёт уже
      сохранённые строки + новые из свежего отчёта, объединяет по id (колонка "Номер"/
      "Номер заказа", индекс 0 в нормализованном формате). Для id, что уже был - берёт СВЕЖИЕ
      данные (1С может дозаполнить прибыль/путёвку/оплату задним числом - это не отменяем).
      Для id, что пропал из нового отчёта, но был раньше - СОХРАНЯЕТ прежнюю строку как есть.
      Новые id - просто добавляются.

### Фаза 2. Подключить слияние в normalizeOrders() (~15 мин)
- [ ] Перед `norm.clear()` - прочитать текущие строки `Заказы_данные` (если лист уже есть).
- [ ] `parsed.rows` пропустить через `mergeOrderRowsById_` вместе с прочитанными старыми
      строками, записать результат вместо голого `parsed.rows`.
- [ ] Не ломает уже работающую защиту "0 строк - не трогаем лист" (правка 2026-07-24,
      см. комментарий в коде) - она остаётся первой проверкой.

### Фаза 3. Подключить слияние в writeArchiveSheet() (~15 мин)
- [ ] Перед `archive.clear()` - прочитать текущие строки архива (если лист уже есть).
- [ ] Слияние тем же способом, что и в Фазе 2.
- [ ] Используется и в `importOrdersReport()` (многомесячный случай), и в
      `archiveOrdersIfNeeded()` (обычный переход на новый месяц + поздняя коррекция) - оба
      вызова получают защиту от потери автоматически, без отдельных правок в них.

### Фаза 4. Ручной бэкфилл заказа №468973 (и №469551) (~10 мин)
- [ ] Слияние решает проблему НА БУДУЩЕЕ, но не восстанавливает задним числом заказ, который
      мы вообще ни разу не видели (1С уже закрыла окно коррекции для июня) - нужно дописать
      руками. Данные по заказу есть из выгрузки Влада + скриншота 1С (см. переписку).
      Отдельное подтверждение перед записью в архив (правки реальных финансовых данных).

## Критерии готовности

- [ ] `mergeOrderRowsById_` - чистая функция, без побочных эффектов, легко тестируется.
- [ ] Повторный запуск `runAll()` с ЛЮБЫМ отчётом 1С (даже без заказа №468973) не стирает
      уже сохранённые данные ни в `Заказы_данные`, ни в архивах.
- [ ] Заказ №468973 (и №469551) появляется в `Заказы_2026-07` после ручного бэкфилла -
      выручка Савиток за июль = 10 596 690₽, совпадает с 1С.
- [ ] Задеплоено (backend через clasp, с pull+diff протоколом).

## Риски

- Слияние может "законсервировать" реально удалённый в 1С заказ (сторнирован/ошибочно
  создан) - раньше такой заказ пропадал бы из отчёта и корректно исчезал у нас тоже, теперь
  останется навсегда, если 1С прямо не пришлёт признак отмены. Смягчение: 1С обычно помечает
  такие заказы, а не просто убирает из выборки - но если окажется проблемой, нужен отдельный
  сигнал "заказ отменён" для явного удаления из слияния (не реализовано в этом плане - если
  всплывёт, разбираться отдельно).
- Дополнительное чтение текущего листа перед каждой записью - на объёмах ~1000-2000 строк
  не должно быть заметно медленнее, но стоит последить за временем выполнения `runAll()`
  после деплоя (уже была история таймаутов, версия 136).
