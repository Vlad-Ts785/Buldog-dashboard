# Мост «Справочники → Планировка/отчёты» для типа техники

## Проблема

Влад изменил Сектор прицепа УУ 4383 77 в Справочниках (Материальные
средства) с К-3 на КР-3. Планировка (бейдж на плитке тягача Е 623 ЕТ 797)
и все финансовые отчёты (Тралы/Длинномеры) продолжали показывать старое
значение из Штатки.

Причина: `vehicle_types` (мост, построенный 01.09 - `plans/2026-09-01-*`,
не сохранился отдельным файлом на тот момент) - ОДНОСТОРОННИЙ канал.
Апп Скрипт (`syncVehicleTypesToServer_()`) пишет туда узкую карту
"госномер тягача -> тип" из Штатки каждые 3 часа. Ничего и никогда не
читало `sprav_assets.trailer_type` (Справочники, ручной ввод, живой)
обратно в эту таблицу - мост существовал только в одну сторону.

Влад, подтверждение: "Сделай сразу по уму. Логика должна быть и связи."

## Решение

Новый VIEW `vehicle_types_effective` (MySQL, вычисляется на лету, без
дополнительной синхронизации):

```sql
CREATE OR REPLACE VIEW vehicle_types_effective AS
SELECT
  vt.gos_number,
  COALESCE(sa.trailer_type, vt.vehicle_type) AS vehicle_type,
  vt.updated_at
FROM vehicle_types vt
LEFT JOIN fleet_assignments fa
  ON fa.tractor_gos COLLATE utf8mb4_unicode_ci = vt.gos_number
  AND fa.kind = 'trailer' AND fa.valid_to IS NULL
LEFT JOIN sprav_assets sa
  ON sa.id COLLATE utf8mb4_unicode_ci = fa.resource_key
  AND sa.deleted_at IS NULL;
```

Логика по тягачу: если сейчас сцеплен прицеп (`fleet_assignments`,
`valid_to IS NULL`) и у него в Справочниках заполнен Сектор - берём ЕГО;
иначе честный fallback на старый Штатка-тип из `vehicle_types`. Прицеп
без заполненного Сектора или отсутствие прицепа вообще (в т.ч. Длинномеры/
Борт - у них тоже есть запись в `fleet_assignments kind='trailer'`,
проверено живьём) не ломает классификацию - просто держит прежнее
значение, пока Влад не заполнит Сектор сам.

## Что переведено на view (все читающие места `vehicle_types` в `api/server.js`)

1. `/api/park_summary` - разбивка Тралы/Длинномеры для денег.
2. `/api/vehicle_status_history` - история статусов ("Динамика").
3. `buildFleetSummary_()` - общая функция, кормит `/api/fleet_summary`,
   `/api/mechanic/fleet` И, что важнее всего, `/api/main_payload.vehicles[].type`
   - именно отсюда Планировка берёт бейдж типа на плитке тягача.
4. `/api/driver_payroll` - разбивка трал/длинномер по водителю за месяц.
5. `main_payload` history (Динамика 30 дней, отдельный inline-запрос).

Сама таблица `vehicle_types` НЕ переименована и НЕ удалена - остаётся
каналом ЗАПИСИ (Апп Скрипт продолжает слать туда Штатку без изменений) и
fallback-слоем ВНУТРИ view. Ни на одном из 5 мест не читается напрямую
больше нигде в коде.

## Проверено живьём (09.09)

- `main_payload.vehicles[Е 623 ЕТ 797].type` = `КР-3` (было `К-3`) сразу
  после правки в Справочниках, без задержки/кэша.
- `park_summary?month=2026-09`: `profit_tral + profit_long` == `profit`
  один в один, `types_known=56` == `COUNT(*) FROM vehicle_types_effective`
  == `COUNT(*) FROM vehicle_types` (0 потерянных/задвоенных строк).
- Все 19 активных Длинномёров (Борт) проверены поимённо - у их прицепов
  Сектор в Справочниках уже стоит "Борт" (совпадает со Штаткой), COALESCE
  безопасен без спецкейса для этого типа.

## Не сделано (сознательно, не требовалось)

- Обратная синхронизация НЕ строилась (Штатка не пишет обратно в
  Справочники) - направление моста строго одностороннее: Справочники
  первичны, Штатка - только fallback для того, что ещё не заведено.
- UI-подсказка "тип взят из прицепа vs из Штатки" на Планировке не
  добавлена - если понадобится диагностика расхождений, можно добавить
  отдельным полем.
