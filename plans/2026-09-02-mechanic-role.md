# Роль «механик»

## Запрос Влада (дословно, 2026-09-02)

«Нам нужно ввести отдельную роль механик. У нас есть логист менеджер и должен быть
механик» → уточнено (AskUserQuestion):
- Доступы заводит сам Влад (роль `mechanic` в листе «Доступ»), список людей не хардкодим.
- На странице - только доступ к «Планировке» (как у логистов).
- Расчёт зарплаты сейчас не нужен.

## Почему НЕ как с Барыльченко (хардкод-фамилия в Apps Script)

При проектировании обнаружено: с 01.09.2026 идёт миграция с Apps Script на сервер
(`plans/2026-09-01-apps-script-elimination.md`), первый инвариант плана - «с 1 сентября в
Apps Script не добавляется НИЧЕГО нового». Роль «механик» по этой причине реализована
**целиком через сервер**, без единой новой строки бизнес-логики в `doGet`.

Это оказалось возможным, потому что Этап 1 плана («Вход и роли на сервере») уже закрыт -
`/api/auth/google` уже отдаёт `role` из `access_users` (живое зеркало листа «Доступ»,
cron раз в 5 мин) прямо при входе, а `/api/fleet_summary` (Этап 2.2) уже отдаёт весь состав
парка без ограничения по роли (`checkSessionOrServerKey`, без `requireRole_`).

## Найдена и закрыта дыра безопасности (независимо от роли механика)

`doGet` разбирал только `access.role === 'manager'`/`'logist'` явно - **любая другая роль
(опечатка, будущая роль) молча проваливалась в общий блок и получала ПОЛНЫЙ admin-payload**
(все финансы/зарплаты компании). Добавлен явный запрет-по-умолчанию перед этим блоком:
`if (access.role !== 'admin') return {error}`. Это защита на случай, если механик всё же
дойдёт до doGet через резервный путь входа (Apps Script - «вторая дверь» на переходный
год, независимая от кэша роли на фронте).

## Реализация

**Бэкенд (`scripts/full_script_final.js`):** только security-фикс выше, никакой новой
бизнес-логики для механика.

**Фронтенд (`files/index.html`):**
- `handleCredentialResponse` - кэширует `role`/`name` из ответа `/api/auth/google` в
  `localStorage` (`user_role`/`user_name`) - id_token живёт ~час, на обычной перезагрузке
  его уже не перепроверить, поэтому роль нужно помнить сразу после входа.
- `clearAuthTokens_` - чистит эти два ключа при выходе.
- `loadMechanicData_()` (новая функция) - единственный источник данных механика,
  `/api/fleet_summary`, приводит ответ к формату `{gos, marka, type, trailer, driver,
  status}`, который уже читает `buildVehicles()` в модуле Планировки. Собирает `D` САМА,
  `doGet` не дёргается вообще.
- `loadData()` - если `localStorage.user_role === 'mechanic'`, вызывает
  `loadMechanicData_()` и выходит, не долетая до `apiUrl({})`.
- `applyRoleUI()` - отдельная ранняя ветка для `D.role === 'mechanic'`: сайдбар сужен до
  `calculator`+`logistics-plan`, дефолтная страница - Планировка (не Личная страница -
  её у механика нет, `D` не содержит `D.orders`, `renderMyPage()` на этом упал бы).

## Проверено

Изолированный Node-тест `loadMechanicData_()` (маппинг полей `/api/fleet_summary` ->
формат `D.vehicles`, включая пустые trailer/driver) - все поля совпали. Синтаксис всех
трёх реальных `<script>`-блоков файла - `node --check` без ошибок. `render()`/
`checkStaleFallbacks_()`/`p2DataSoundCheck_()`/`updateViewAsButton_()` - вручную сверены,
все безопасно обрабатывают `D` без `orders`/`debt`/`receipts` (ранние guard'ы уже были).
