# Убрать блокирующие экраны загрузки

**Создан:** 2026-08-28 по запросу Влада: «я бы хотел, чтобы у нас не было загрузок вообще.
При первом старте пусть будет, но если какие-то данные обновляются, пусть они на каждом
участке обновляются по мере поступления информации... я также могу работать с интерфейсом,
пока идёт тихая загрузка».

**Статус:** план, к реализации не приступал.

---

## Что происходит сейчас (проверено по коду, не по памяти)

`loadData()` (`files/index.html:3480`) — один блокирующий цикл:

1. Показывает полноэкранный лоадер («Прогреваем дизель…»), гасит весь интерфейс.
2. Делает ОДИН запрос за ВСЕМ сразу (`apiUrl({})` → `doGet` → `getMainPayloadCacheOrLive_`).
3. Дожидается полного ответа.
4. Вызывает `render()` — линейно перерисовывает все ~11 секций подряд.
5. Гасит лоадер.

Кнопка «Обновить данные» (`files/index.html:1041`) зовёт ту же `loadData()` — отсюда и
претензия Влада: принудительное обновление гасит весь экран, хотя обновиться должна была
пара цифр.

**Из чего состоит ответ** (`getMainPayloadCacheOrLive_`, `scripts/full_script_final.js`):
- `Object.assign({}, cached, freshFinancials)`
- `cached` — Штатка/техника/водители/история/периоды, кэш на 3 часа (медленное, но и не
  меняется внутри часа).
- `freshFinancials` — `summary`/`orders`/`debt`/`receipts`, каждый раз живьём с VPS.

## Главное открытие: нужный паттерн УЖЕ работает в бою

`files/index.html:3495-3498` — «Поступления» уже обновляются ровно так, как Влад хочет
видеть везде:

```
render();                                  // сначала показали, что есть
fetchReceiptsFromServer_().then(function(r) {   // потом в фоне подменили свежим
  if (r && !r.error && D) { D.receipts = r; renderReceipts(); }
}).catch(function() {});                   // не ответил - молча остались на старом
```

Никакого лоадера, интерфейс живой, секция перерисовалась сама. **Задача — не изобрести
подход, а распространить этот на остальные секции.** Это сильно снижает риск: паттерн уже
проверен на проде.

## Что играет в нашу пользу

- **Секции уже разделены на функции.** `render()` — просто оркестратор из 11 вызовов
  (`renderKPI`, `renderMain`, `renderDebt`, `renderReceipts`, `renderVehiclesTable`…).
  Не нужно распутывать монолит — нужно перестать звать их скопом.
- **На сервере уже есть отдельные эндпоинты по секциям**: `/api/orders_computed`,
  `/api/debt_computed`, `/api/receipts`, `/api/orders_period`, `/api/import_status`.
  Разбивать бэкенд с нуля не надо.
- **Данные уже быстрые.** Финансы идут с VPS живьём (0.3 сек), не из Google Таблиц. Долгая
  часть — это Apps Script как посредник и медленная Штатка.

## Что играет против (честно, до начала работ)

- **81 функция `render*`, все читают глобальный `D`.** Сейчас каждая исходит из того, что
  `D` заполнен целиком. При частичной загрузке `D.orders` может ещё не приехать, а
  `renderKPI()` уже вызвана — получим пустой экран или ошибку в консоли вместо цифр. Это
  главный риск, и он требует аккуратности, а не смелости.
- **Гонки при повторных нажатиях.** Влад жмёт «Обновить» дважды — два набора ответов могут
  прийти вперемешку и перезаписать друг друга старыми данными. Нужен счётчик поколений
  запроса (ответ от устаревшего запроса игнорируется).
- **Показ устаревших данных без предупреждения** — если убрать лоадер, но не показать, что
  идёт обновление, Влад может принять старую цифру за свежую. Нужен ненавязчивый индикатор.

---

## Этап 1. Обновление без гашения экрана (главная боль, наименьший риск)

**Цель:** «Обновить данные» больше не гасит интерфейс. Можно продолжать работать.

- Разделить `loadData()` на две: `loadDataInitial()` (с лоадером, только первый вход) и
  `refreshDataSilent()` (без лоадера).
- Кнопка «Обновить данные» зовёт `refreshDataSilent()`.
- Индикатор вместо лоадера: кнопка «Обновить данные» показывает состояние (крутится/
  «Обновляю…»), интерфейс остаётся полностью рабочим.
- Счётчик поколений запроса — ответ устаревшего запроса отбрасывается.
- Ошибка при тихом обновлении НЕ должна ронять уже показанные данные: остаёмся на старом
  + короткое ненавязчивое сообщение (тот же принцип, что уже у `fetchReceiptsFromServer_`).

**Риск:** низкий. `render()` вызывается с полным `D`, как и раньше — просто без лоадера.
**Уже закрывает** основную претензию Влада про «нажал обновить и сижу смотрю на экран».

## Этап 2. Мгновенный старт из локального кэша

**Цель:** при повторном заходе интерфейс появляется сразу, без «Прогреваем дизель…».

- После каждой успешной загрузки складывать `D` в `localStorage` (последнее известное
  хорошее состояние).
- При открытии страницы: если кэш есть — сразу отрисовать из него (мгновенно, без лоадера),
  и тут же запустить тихое обновление фоном (Этап 1).
- Лоадер остаётся ТОЛЬКО для самого первого входа, когда кэша ещё нет — как Влад и просил.
- Обязательно: видимая пометка «данные от HH:MM, обновляются» пока не приехали свежие,
  чтобы устаревшая цифра не выдавалась за текущую.
- Ограничение по возрасту: кэш старше N часов не показываем (лучше лоадер, чем вчерашние
  деньги на экране).

**Риск:** средний. Главное — не показать вчерашнее как сегодняшнее. Индикатор обязателен,
не опционален.

## Этап 3. Секции грузятся и появляются независимо

**Цель:** то, что Влад описал буквально — «на каждом участке обновляются по мере поступления».

- Вместо одного запроса за всем — параллельные запросы по секциям (эндпоинты на VPS уже
  есть).
- Каждая секция перерисовывается, как только приехали ЕЁ данные, не дожидаясь остальных.
- Перед этим — сделать все `render*` устойчивыми к отсутствию своих данных (показывать
  скелет/«загружается» вместо ошибки). **Это основная работа этапа, не сама параллельность.**
- Делать по одной секции за раз, начиная с самых заметных (KPI сверху, Поступления, ДЗ),
  проверяя каждую. Не переписывать все 11 разом.

**Риск:** выше остальных — трогает все секции. Именно поэтому идёт последним и по одной.

## Этап 4. После 1 сентября — убрать Apps Script из цепочки

**Контекст от Влада:** «с 1 сентября переключу их... всё, что приходило на почту и
обрабатывалось скриптом, добьём, чтобы это было в серверных функциях».

Когда последние email-каналы 1С переедут на сервер, Apps Script перестанет быть посредником
для данных, и фронтенд сможет ходить прямо на VPS. Это само по себе уберёт заметную часть
задержки (сейчас Apps Script — самое медленное и самое нестабильное звено, см. запись про
`/exec` в CLAUDE.md). Отдельная задача, но она усилит эффект этого плана.

---

## Порядок и принцип

Этапы 1 → 2 → 3 — по возрастанию риска и убыванию отдачи на единицу риска. Этап 1 сам по
себе снимает большую часть боли и почти ничем не рискует; Этап 3 самый красивый, но и самый
инвазивный, поэтому последний.

**Правило перехода:** следующий этап не начинается, пока предыдущий не поработал на живом
дашборде и Влад не подтвердил, что стало лучше, а не «просто по-другому».
