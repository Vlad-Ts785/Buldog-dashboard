При первом старте пусть будет, но если какие-то данные обновляются, пусть они на каждом
участке обновляются по мере поступления информации... я также могу работать с интерфейсом,

повторить.

**Статус:** Этап 0 реализован и задеплоен 29.08 (Apps Script v305, files/index.html
коммит 8982a99, лог - scripts/DEPLOY_LOG.md). Этапы 1-5 - не начаты.

## Что показали замеры (29.08, живой прод)

Полная загрузка дашборда через Apps Script: **медиана 14 секунд**, лучший результат 9.6 с,
при частых запросах Google троттлит до 40-87 с. Примерно 1 запрос из 10 возвращает HTML
вместо JSON (задокументированная нестабильность /exec) - фронтенд его ретраит, для
пользователя это +30 с молчаливого ожидания под лоадером.

Куда уходят типичные 12 секунд:

| Слой | Секунд | Доля |
|---|---|---|
| Пол Apps Script (dispatch Google + openById) - неустраним, пока он посредник | ~2.8 | 23% |
| Работа с Google Sheets внутри Apps Script (см. горячую точку ниже) | ~7.0 | 58% |
| Сам VPS (все три финансовых эндпоинта) | ~1.2 | 10% |
| Сериализация и отдача 784 КБ | ~1.0 | 8% |

**Горячая точка номер один: `getRevenueDateComparison_`** (`full_script_final.js:~7098`) -
при КАЖДОМ заходе на дашборд читает полный лист архива `Заказы_2026-07` (~1000 строк x 44
колонки) ради одной цифры «выручка на ту же дату прошлого месяца». Кэша нет - хотя
соседний блок prev_year в той же функции закэширован на 6 часов. Это ~4-5 секунд из
каждых 12. Одна маленькая правка бэкенда срезает треть времени загрузки.

VPS сам по себе быстрый: orders_computed 0.17 с, debt_computed 0.17 с, receipts 0.86 с.
76% байт ответа - это три блока, уже посчитанные на VPS, которые Apps Script просто
переупаковывает.

## Три ошибки первой версии плана (признаны, исправлены в v2)

1. **«Этап 1 - низкий риск» был неправдой.** Тихий вызов render() имеет два побочных
   эффекта: (а) `applyRoleUI()` для менеджера/логиста принудительно вызывает
   `showPage('my-page')` - тихое обновление выкидывало бы человека с открытой вкладки
   («План задания», «Калькулятор») обратно на личную страницу, на телефоне ещё и
   закрывало бы меню; (б) `p2DataSoundCheck_()` - фанфары и одометр начали бы срабатывать
   на автоматических обновлениях. Оба лечатся, но должны быть явными пунктами.

2. **«Данные от 14:03» - на этом поле нельзя строить.** `D.updated` ставится в момент
   сборки ответа (`new Date()` в doGet) - это время ЗАПРОСА, а не данных. Оно всегда
   «сейчас» и физически не может предупредить об устаревании - ровно та слепота, из-за
   которой авария 19.08 висела 8 часов. Честный источник уже есть и уже дёргается:
   `/api/import_status` с minutes_since_run + готовый форматтер fmtAgo_.

3. **Старый Этап 3 (параллельные запросы по секциям) сделал бы дашборд МЕДЛЕННЕЕ.**
   Каждый отдельный запрос к Apps Script платит пол 2.8-3.5 с (dispatch + openById) и
   несёт ~10% шанс поймать HTML-вместо-JSON. Пять запросов вместо одного - пять полов и
   впятеро больше лотереи. Параллелить можно только прямые VPS-запросы. Взамен есть ход
   лучше и дешевле - ленивый рендер по вкладкам (см. Этап 2).

## Что оказалось ЛУЧШЕ, чем ожидалось

- Из 84 render-функций при частичных данных падают только **2** (а не «81 посыпется»):
  `renderMgrList` (реальная бомба на пути render(), ~строка 8102) и `renderMyPageManager`
  (сегодня прикрыта guard'ом выше по стеку). Починка обеих - 2-4 строки.
- Графики Chart.js все аккуратно уничтожаются перед пересозданием (11 из 11), слушатели
  не дублируются - утечек при повторном рендере нет вообще.
- Фильтры и сортировки живут в JS-глобалях, а не в DOM - перерисовка их НЕ сбрасывает.
  Реально теряются только: скролл внутри контейнеров с overflow (чат CRM), открытая
  модалка, анимация графика, выделение текста мышью. Конечный список, записан.
- Из 11 секций render() на стартовом экране видны только 3 (KPI, сводка поступлений,
  панель) - остальные 8 рисуются в скрытые display:none вкладки. Лоадер в основном ждёт
  отрисовку, которую никто не видит.
- В коде уже ~10 образцов тихого обновления. Самый чистый - поллинг банковских операций:
  отдельный глобал (не трогает D), точечная перерисовка, visibilitychange, дельта по
  max-seen-id. Язык проекта уже задан, изобретать не надо.

## Известные мины (найдены аудитом, чинить обязательно в любом случае)

- **`renderSalesTabsForPeriod` подменяет глобальный D без try/finally** (~7151-7180).
  Исключение в любом из 4 внутренних рендеров - и весь дашборд навсегда остаётся на
  цифрах чужого месяца. У соседнего renderMyPage try/finally есть. Фикс 3-4 строки.
- **Двойной клик по «Обновить данные» ничем не защищён** - две записи в D в произвольном
  порядке.
- **`fetchReceiptsFromServer_` перерисовывает только страницу «Поступления», но не
  сводку на Панели** - две секции читают один D.receipts, но нарисованы из разных его
  версий до следующего события.
- Скрытая связка звука: `p2CurDebtTotal_` пишется внутри renderKPI (не renderDebt!) и
  читается табло/звуком - при независимой перерисовке пропуск renderKPI глушит метрику ДЗ.
- Кто-то бьёт /exec каждые 30-40 секунд фоном (видно в access.log даже без наших
  запросов) - забытая вкладка или чужая сессия. Возможная часть причины троттлинга до
  40-87 с. Стоит найти источник.

# План v2

Гранулярность - НЕ 11 визуальных секций, а **3 пакета данных по источнику** (эта нарезка
уже существует на бэкенде, мы её просто признаём):

1. **Живые финансы** - summary + orders + debt + receipts. Неделимый пакет: summary
   считается ИЗ orders на бэкенде, разнести их = гарантированный разъезд цифр на Панели
   (нарушение принципа project_data_consistency_principle).
2. **Медленный парк** - vehicles + drivers + history + periods + driverOrderCounts.
   Google Sheets, кэш 3 часа, ~26 КБ, денег в моменте нет. Кандидат в localStorage.
3. **Живая Штатка** - fleet + repairs + staffMarkas + access_log. Дешёвое, но физически
   только в Google Sheets (лист правят руками), никуда не переезжает.

Личные страницы, Клиенты, CRM, План задания - не пакеты, они уже ленивые по требованию.

## Этап 0. Честность и быстрые победы (ничего не ломают, делать первыми)

- **0.1 Честный таймстемп.** `nav-updated` в сайдбаре перестаёт врать: вместо «Обновлено:
  14:03» (время запроса) - «Данные 1С: 12 мин назад» из /api/import_status (уже
  опрашивается, форматтер fmtAgo_ уже есть). Убрать или починить тем же источником
  «· данные 1С HH:MM» в шапке - два места со свежестью, оба неверные, хуже одного верного.
- **0.2 Кэш getRevenueDateComparison_** (CacheService 6 ч, как у соседнего prev_year в
  той же функции). Минус ~4-5 с с КАЖДОЙ загрузки. Одна правка бэкенда. Цифра меняется
  раз в день (архив прошлого месяца) - кэш безопасен.
- **0.3 Обязательные фиксы из аудита:** try/finally в renderSalesTabsForPeriod, guard в
  renderMgrList и renderMain, защита кнопки от двойного клика (disabled на время
  запроса - заодно готовый индикатор «Обновляю...»).
- **0.4 Фикс fetchReceiptsFromServer_:** дёргать обе перерисовки поступлений, не одну.

Ожидаемый эффект Этапа 0: загрузка с ~14 до ~9-10 с, свежесть перестаёт врать, три
известные мины сняты. Пользовательских изменений почти не видно - это фундамент.

## Этап 1. Тихое обновление (переработанный)

- **applyData(patch)** - единая точка записи в D (~30 строк): через неё идут первая
  загрузка, кнопка, будущий поллинг, восстановление снапшота. Каждый следующий
  параллельный чат добавляет вызов, а не переписывает loadData - под наше ограничение
  «маленькие диффы при параллельных сессиях».
- **Хэш-сравнение по пакетам** (~15 строк): JSON.stringify куска сравнивается с прошлым,
  совпало - секция не перерисовывается. Бесплатно снимает мигание графиков, потерю
  скролла, лишние анимации. Замерить стоимость на ДЗ-массиве на телефоне.
- **Вынос showPage из applyRoleUI**: переключать страницу только если текущая активная
  НЕ разрешена роли - тихое обновление больше не выкидывает человека с вкладки.
- **Звук на тихом обновлении**: p2DataSoundCheck_ уже имеет guard на document.hidden и
  порог 10 000 ₽. Решение: оставить как канал «данные изменились» при видимой вкладке -
  это и есть механизм доверия (цифра прокрутится сама, тишина = «проверил, всё то же»).
  Если Владу будет шумно - отключим одним флагом.
- Кнопка «Обновить данные»: спиннер + disabled + «Обновляю...» (частично уже сделано в
  0.3). Ошибка тихого обновления - остаёмся на старых данных + p2Toast, экран не гасим.
- Лоадер остаётся только на самый первый вход (пустой D).

## Этап 2. Ленивый рендер по вкладкам (замена старого «параллельного» Этапа 3)

- render() рисует только активную страницу; остальные помечаются «грязными» и
  дорисовываются в showPage при переключении. ~20 строк, не трогает внутренности ни
  одной render-функции.
- Прецедент уже в коде: clients / crm / global-stats / order-plan так и работают.
- Выигрыш времени до первого экрана больше, чем у параллельных запросов, при кратно
  меньшем риске.
- Сюда же: ~16 B-блоков получают честные состояния «загружается» вместо тихих нулей
  (32-64 строки). Скелетоны - новый визуальный паттерн: сначала одобрение Влада, потом
  запись в DESIGN_SYSTEM.md, потом код (правило ГОСТа).

## Этап 3. Поллинг горячих цифр (бывшая «кнопка» умирает как необходимость)

- Раз в 10 минут (1С кладёт файлы ~раз в час - чаще опрашивать бессмысленно, только
  нагрузка), ТОЛЬКО при видимой вкладке (document.hidden - не бьём; возврат во вкладку -
  один запрос, если прошло > N минут), ТОЛЬКО по прямым VPS-эндпоинтам (дешёвые), НЕ по
  Apps Script (квота общая на аккаунт - project_apps_script_quota_gotcha).
- Сейчас напрямую с VPS доступны: receipts, import_status, client_analytics,
  orders_period (архив), bank/operations, вся CRM. Этого хватает для поступлений и
  свежести. Полный финансовый пакет - см. Этап 5.

## Этап 4. Снапшот холодной части в localStorage (бывший Этап 2, урезан)

- В снапшот кладётся ТОЛЬКО пакет «медленный парк» (~26 КБ, не деньги) - не весь D
  (784 КБ, микрофриз на записи + квота + деньги на диске браузера).
- Обязательно: константа версии схемы рядом с API_URL_DEFAULT (поднимать руками при
  несовместимой правке рендера); рендер из снапшота в try/catch с автоочисткой ключа
  (иначе один битый снапшот = вечно белый экран, чинить по телефону); чистить снапшот в
  clearAuthTokens_/logoutUser.
- Показ устаревшего: показывать всегда (директору полезнее вчерашние цифры мгновенно,
  чем пустой экран), но при возрасте > 30 мин приглушать (opacity ~0.5) до прихода
  свежих. Приглушение - новый паттерн, через ГОСТ.
- Мобильный: nav-updated в закрытом сайдбаре не виден - нужен компактный дубль строки
  свежести в шапке страницы (тоже через ГОСТ).

## Этап 5. Прямой путь браузер -> VPS для финансового пакета (после 1 сентября)

Когда последние email-каналы 1С переедут на сервер, Apps Script перестаёт быть
обязательным посредником для данных. Но открыть orders_computed/debt_computed браузеру
нельзя, пока на VPS нет ролей:

- **Блокер: orders_computed содержит зарплатную логику.** Сейчас эти эндпоинты закрыты
  SERVER_KEY. session_token несёт только email, без роли - открой их по checkSession, и
  любой менеджер с валидным входом достанет зарплаты всех. Обязательное условие прямого
  пути: роль на VPS (зеркало листа «Доступ» в MySQL, синк раз в N минут, ИЛИ роль в
  payload токена - второе меняет формат, которым пользуется весь Apps Script, осторожно).
- Прочие разрывы, найденные замером: отзыв доступа на VPS не мгновенный (токен живёт до
  48 ч против перечитывания «Доступа» на каждый запрос в doGet); скользящее продление
  сессии есть только в doGet; счётчик входов ведёт только doGet.
- Что при этом остаётся за Apps Script навсегда (или до отдельного решения): вход и
  выдача токена, Штатка/fleet/repairs, История_финансов (ВП), «Доступ», «Логи_входов»,
  Планы_менеджеров (мостик на VPS убран - manager_plans в MySQL не синхронизируется),
  План задания, ИИ-задачи, marketing.

## Порядок и правило перехода

0 -> 1 -> 2 -> 3 -> 4 -> 5. Каждый следующий этап - после того как предыдущий пожил на
проде и Влад подтвердил, что стало лучше. Этапы 3 и 4 можно менять местами по желанию.

## Что соглашаемся терять при перерисовке (зафиксировано, чтобы не бояться абстрактно)

Скролл внутри контейнеров с собственным overflow (чат CRM), открытые модалки, анимацию
графика в момент обновления, выделение текста мышью. Хэш-сравнение (Этап 1) сводит это
к случаям, когда данные реально изменились.
