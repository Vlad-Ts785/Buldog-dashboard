# Дашборд ЯРД - навигация

Карта проекта. Читай в начале каждой сессии.

## Что это за проект

**Дашборд ЯРД** - внутренняя BI-система для директора ООО «Бульдог» (группа ЯРД Империал).
Сводит данные из 1С, Google Sheets, Роснефть и телефонии в одно окно.
Влад открывает ноутбук - за 2 минуты видит состояние бизнеса без звонков сотрудникам.

Подробности - `.business/INDEX.md`.

## Порядок чтения в начале любой сессии

1. `../ai-clone/INDEX.md` - кто такой Влад и как он думает
2. `.business/INDEX.md` - контекст компании, команда, сегменты ЦА
3. `CLAUDE.md` (этот файл) - стек, правила, навигация
4. Зона задачи: нужный файл из `.business/`, `plans/<актуальный план>`, или код

**Стратегия (Влад, 2026-08-18): ГЛОБАЛЬНО переходим на работу с сервера, не с Google Таблиц.**
Это не разовая фича - конечная цель всего переезда. Раньше "расчётная логика (зарплаты/
планы/воронка) сознательно НЕ переносится" было постоянным правилом; теперь это следующий
этап того же переезда, просто самый рискованный - делать МЕДЛЕННО и с построчной сверкой на
каждом шаге (см. `plans/2026-08-18-payroll-logic-server-port.md`), не вместо осторожности,
а из-за неё. Google Таблицы остаются источником для 1С-каналов, которые физически шлют туда
данные (email/FTP-приёмники) - меняется КУДА дашборд идёт ЗА расчётом, не как данные попадают
от 1С в систему.

С 2026-08-17 идёт постепенный переезд на свой сервер (VPS Beget, `api.yardhub.ru`) - ДВА
параллельных канала для одних и тех же отчётов 1С, пока не отключим старый:

```

       |                                          |
  Apps Script (парсит Gmail)              Node.js import-скрипты (VPS, cron)
       |                                          |
  Google Sheets (20+ листов)              MySQL (VPS)
       |                                          |
  doGet() JSON API                        Express API (api.yardhub.ru)

Дашборд      Telegram-бот                 Дашборд (files/index.html) -
(GitHub)     (3 сообщения)                пробует сервер первым, при ошибке -
```

## Свежесть данных - три РАЗНЫХ слоя задержки, не путать

**Записано 25.08.2026 после того, как в разгар инцидента (приостановка VPS у хостера)
диагноз был поставлен неверно** - расхождение выручки с 1С списали на "часовой кэш главной
страницы", хотя такого кэша не существует. Причина путаницы: в системе реально есть ТРИ
разных места, где что-то может "не обновляться", и они легко смешиваются, если не
проверять код, а рассуждать по памяти.

**1. Выручка/ДЗ/поступления на дашборде - ВСЕГДА живьём, кэша Apps Script здесь нет.**
`getOrdersData()`/`getDebtData()`/`getReceiptsData()` при КАЖДОМ заходе на дашборд сначала
бьют на сервер (`fetchOrdersComputedFromServer_`/`fetchDebtComputedFromServer_`/
`fetchReceiptsComputedFromServer_`) и только при недоступности сервера тихо откатываются на
лист. Если цифра "не обновилась" - ищи причину НЕ здесь, а в звене ниже или в самом сервере
(жив ли он - см. "Деплой на VPS-сервер").

**2. Реальный предел свежести - расписание самой 1С, не сервера.** Сервер проверяет папку
FTP гораздо чаще, чем 1С физически кладёт туда новый файл - запас сделан специально, чтобы
не упустить момент прихода. Замерено эмпирически 25.08 (стат по `mtime` файлов + журнал
`import_runs`):

| Отчёт | 1С реально кладёт файл | Сервер проверяет | Итоговый потолок задержки |
|---|---|---|---|
| Заказы | ~раз в час | каждые 3 мин | до часа - упирается в 1С |
| Поступления | ~раз в час | раз в час | до часа - упирается в 1С |
| ДЗ (дебиторка) | нерегулярно, видел разрывы >15 часов | каждые 5 мин | до часа-полутора - упирается в 1С |

**3. Кэш Штатки/техники (состав парка, статусы машин) - раз в 3 часа, это реальный кэш.**
`saveMainPayloadCache_` пишется триггером `runAll` 6 раз в сутки (6:00, 9:00, 12:00, 15:00,
18:00, 21:00 - см. `setupTrigger()`, комментарий в коде "подогнано под расписание 1С"
устарел, это привязка к СТАРОМУ email-каналу, не к текущему FTP). Уместно для медленных
полей (состав парка не скачет внутри часа), но НЕ путать с финансовыми показателями из
пункта 1 - `getMainPayloadCacheOrLive_` берёт этот кэш как базу и ПЕРЕЗАПИСЫВАЕТ поверх
свежими `summary`/`orders`/`debt`/`receipts` (`Object.assign({}, cached, freshFinancials)`).

**Отдельно, четвёртое - но это уже не про данные, а про КОД страницы:** `yardhub.ru`
кэшируется прокси на 10 минут (`Cache-Control: max-age=600`) + свой кэш браузера
пользователя поверх. После любого деплоя `files/index.html`, если у Влада "сайт не грузит"
на одном устройстве, а на другом всё в порядке - в первую очередь `Ctrl+Shift+R`
(жёсткое обновление), не подозревать сервер, пока это не исключено.

**Ключевые листы (старый канал, Google Sheets):** Штатка (ЖИВОЙ документ - статусы машин),
Нормализованные_данные, Менеджеры_данные, История_показателей, История_финансов,
Заказы_данные (+ архивы Заказы_YYYY-MM), Планы_менеджеров, ДЗ_данные + История_ДЗ
(дебиторка, отчёт 1С раз в день в 15:00, см. `plans/2026-07-08-debt-receivables-tab.md`).

**Штатка - критические колонки:** A=тип, C=госномер, AF=статус машины,
AG2/3/4=тралы, AH2/3/4=длинномеры, AJ2/AK2=без заказа.

## 8 правил репо

1. **Не хардкодить** токены, ID, константы. Всё в `.env` или конфиге.
2. **Не деплоить без явной команды.** Push в main = автодеплой на GitHub Pages.
3. **Удалять одноразовый код** после использования.
4. **`.env` только через `grep "^VAR=" .env`** - никогда не читать целиком.
5. **Большая фича = план в `plans/`.** Граница: задача больше часа - пишем план.
6. **Цикл после каждой фичи:** найди ошибки -> что упустили -> security review.
7. **`git add` поимённо.** Никогда `git add .` - параллельно работают другие чаты.
8. **Ретроспектива в конце сессии** - `retrospectives/YYYY-MM-DD_HH-MM_название.md`.

## Цикл после каждой фичи (обязательно перед закрытием задачи)

1. Найди ошибки в написанном коде - исправь
2. Что упустили (граничный кейс, валидация, ошибки) - исправь
3. Это реально решает нашу задачу? Сверь с `.business/` и `plans/`
4. Security review: ПДн, внешние запросы, токены в коде
5. Менялся UI - прогони чек-лист приёмки из `DESIGN_SYSTEM.md` (раздел 10). Не
   прошёл пункт - не сдаём. Нового паттерна нет в ГОСТе - сначала одобрение Влада,
   потом дописать в ГОСТ, потом использовать

**Код на сервере НЕ под git.** Значит нет `clasp pull`+`diff`-протокола, как у Apps Script -
только ручной бэкап (`cp server.js server.js.bak-...`) перед перезаписью и осторожность при
параллельной работе (см. координацию ниже). Ежедневный автобэкап данных+кода настроен
(`import/backup-db.js`, `/root/backups/`), но это не замена git-синхронизации для правок в
моменте.

**Координация между сессиями (ОБЯЗАТЕЛЬНО)** - параллельно могут работать другие чаты и
деплоить туда напрямую, минуя git. Уже дважды приводило к тихому откату чужого фикса
(версии 90-92, см. `scripts/DEPLOY_LOG.md`). Перед КАЖДЫМ `clasp push`:
1. `clasp pull` в `Дашборд_Apps_Script`.
2. `diff --strip-trailing-cr` с `scripts/full_script_final.js` из git HEAD.
3. Если diff непустой - в живом файле есть чужая недокоммiченная работа, сначала перенеси
   её в репозиторий отдельным sync-коммитом, и только потом свои правки.
4. После `push`+`create-version`+`redeploy` - добавь строку в `scripts/DEPLOY_LOG.md`.

**То же самое касается `files/index.html` и вообще любого push в `main`, не только Apps
Script** (подтверждено 2026-08-17: Влад параллельно в ДРУГОМ чате того же проекта вкатил
фичу "калькулятор стоимости перевозки" прямо в `main`, пока эта сессия работала над
"Клиенты"/сервером - совпало без предупреждения). Перед push в `main`:
1. `git fetch origin main`, сравни с тем, от чего реально ответвлялась твоя работа
   (`git merge-base HEAD origin/main`) - если `origin/main` уехал вперёд, там чужая работа.
2. Не пытайся угадать различия руками на больших файлах - `git merge-file <mine> <base>
   <theirs>` (3-way merge) отработал чисто в этом случае, используй тот же приём.
3. Коммить чужую работу и свою РАЗНЫМИ коммитами (или явно описывай слияние в одном, как
   сделано здесь), не тихо перезаписывай.
4. Влад ведёт несколько чатов по этому проекту одновременно как норму, а не исключение -
   не удивляться, ожидать это перед каждым крупным push.

**То же самое (плюс отдельный риск) для VPS-сервера** - код там НЕ под git, только ручные
`.bak`-копии, значит нет способа автоматически увидеть чужие правки перед `scp`. Перед тем
как заливать `api/server.js` или любой файл в `import/` на сервер:
1. Сначала `scp` файл С сервера к себе и посмотри, не разошёлся ли он с тем, что редактируешь
   локально - если да, перенеси чужие правки в свою копию вручную, не перезаписывай их.
2. После деплоя - строка в `/root/yard-dashboard/README.md` (см. раздел "Деплой на VPS-сервер"
   выше), не только в `scripts/DEPLOY_LOG.md`.
3. Если знаешь, что другая сессия сейчас тоже правит `server.js` - договоритесь через
   `SendMessage` (см. `ListAgents`), кто деплоит первым (подтверждено 2026-08-21: ровно эта
   ситуация - два чата одновременно правили `server.js` под разные задачи).
