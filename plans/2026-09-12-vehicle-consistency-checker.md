# Инструмент проверки согласованности данных по машине

## Проблема

Влад поймал живьём: тягач М 844 ЕА 797 в Планировке (сейчас, 12.09) показывает
живого водителя Смирнова, а на странице "Техника" за произвольный период
(01.08-31.08) - "Без водителя"/"вакант". Спросил: "откуда тянутся статусы
техники в технике?" и попросил общий инструмент - собрать по одной машине
данные из ВСЕХ источников рядом и подсветить расхождения, не разбирать
каждый случай вручную.

## Найденный корень (именно этого случая)

Две РАЗНЫЕ ветки кода за словом "Техника":
- **"Текущий месяц" (по умолчанию)** - `D.vehicles` из `/api/main_payload`,
  `buildFleetSummary_()` на VPS - живой `fleet_assignments` + живой
  `computeLiveVehicleStatus_()`. Тот же источник, что и Планировка - здесь
  расхождений быть не должно.
- **Произвольный период ("Показать" с датами)** - `action=vehicles_period`
  в Apps Script (`scripts/full_script_final.js:5573`) - вызывает
  `getStaffData(ss)` + `aggregateFinHistoryForRange(...)` - это **Штатка**
  (Google-лист), которую "больше никто не ведёт" (Влад, 02.09, тот же факт,
  что уже увёл computeLiveVehicleStatus_ с vehicle_status_daily). У Штатки
  нет исторической версионности - при ЛЮБОМ периоде отдаётся ТЕКУЩЕЕ
  (замороженное) состояние листа, не "как было на самом деле в августе".
  М 844 ЕА 797 в самой Штатке годами висит вакантным - ровно это и
  показалось за август, независимо от даты.

Это НЕ баг рассинхронизации в моменте - это структурная особенность старого
источника: Планировка/"Текущий месяц" уже мигрировали на VPS, а Штатка
для ЛЮБОГО прошлого периода - нет (та же незаконченная миграция типа/
статуса техники, упомянутая в CLAUDE.md).

## Решение - не полная миграция периода (отдельная большая задача), а честный
## диагностический инструмент прямо сейчас

Influenced Владом дословно: "инструмент проверки логики... собирает
информацию по машине: что у нас по строчкам, по машине, что у нас в парке
техники, по машине, что у нас в планировке. Показывает, где у нас идут
нестыковки."

### Новый эндпоинт `GET /api/vehicle_check?gos=` (admin)

Собирает по ОДНОМУ гос.номеру, за один запрос:
- **Справочники** (`sprav_assets`) - тип, сектор, отдел, юрлицо.
- **Планировка/живая сцепка** (`fleet_assignments`, valid_to IS NULL) -
  текущий водитель + с какого момента + кто посадил; текущий прицеп.
- **Живой статус** - `computeLiveVehicleStatus_()`, тот же расчёт, что уже
  кормит "Текущий месяц" - "В работе"/"Ремонт"/"Без водителя"/"Без заказа".
- **Текущая запись Планировки** (`plan_segs`, покрывающая "сейчас") - kind,
  причина (repair_reason/reason), с/до.
- **Последние 15 событий истории** (тот же запрос, что у кнопки "История" в
  Планировке, `/api/plan/activity?gos=`) - кто и что менял недавно.

### Фронтенд - новая карточка в Справочники

"Проверка техники" - поле ввода гос.номера (с автодополнением по
sprav_assets), кнопка "Проверить". Показывает 4 блока (Справочники / Живая
сцепка / Статус сейчас / Последние действия) СТРОГО как есть, без
причёсывания - и отдельно **Штатку за сегодня**, догруженную тем же
`action=vehicles_period` (уже существующий Apps Script путь, узкий период -
сегодня-сегодня, БЕЗ нового кода в Apps Script), найдя нужную строку по
гос.номеру на фронтенде.

**Расхождения** - простое сравнение "живой водитель (VPS) vs водитель по
Штатке" и "живой статус (VPS) vs статус по Штатке" - если различаются,
красная строка сверху с явной формулировкой (не гадание, оба значения
рядом).

## Сознательно НЕ делаем сейчас

- НЕ чиним саму Штатку и НЕ мигрируем `vehicles_period` на VPS для
  произвольных периодов - это отдельная, более крупная задача (тип/статус
  техники "мигрирует отдельно", по CLAUDE.md), инструмент только
  ДИАГНОСТИРУЕТ, не лечит корень.
- НЕ строим "пробег по всему парку" автоматически в этой версии - ручная
  проверка по одному гос.номеру. Массовый прогон (по всем 50+ машинам разом)
  - следующий шаг, если этот инструмент окажется полезным.
