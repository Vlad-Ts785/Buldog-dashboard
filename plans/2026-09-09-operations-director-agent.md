# ИИ-агент «Операционный директор»: каждый день отвечает, что сделать, чтобы больше заработать

**Дата:** 2026-09-09
**Статус:** Фаза 1 СДЕЛАНА 09.09 (сервер на бою, крон 07:00 МСК, первый бриф собран за 97 с; фронт в ветке `claude/operations-director-agent-b029b3`, ждёт решения Влада о публикации в main). Фазы 2+ - по отдельным «да».

## Зачем

Влад: «Нужно вырастить агента руководителя (операционного директора), который анализирует
все показатели бизнеса ежедневно и начинает учиться управлять бизнесом. Пока - в качестве
моего ассистента, пока учится. Данных полно, и они будут только прибавляться.
Каждый день он должен начинать с вопроса: а какие нам нужно сделать действия, чтобы больше
зарабатывать».

**Как выглядит успех MVP:** утром на странице «Операционный директор» лежит свежий бриф
за сегодня: главный вывод дня, состояние ключевых показателей (что в норме, что требует
внимания), 3-5 действий с оценкой в рублях, ответственным и метрикой для проверки
завтра, и отчёт по вчерашним действиям (что изменилось). Влад отвечает на каждое действие
одной кнопкой: «Согласен» / «Не согласен» (с комментарием) / «Сделано». На следующий день
агент видит эти ответы и свои прошлые заметки - и его советы становятся точнее. Это и
есть «учится»: не дообучение модели, а накопленная память о бизнесе + обратная связь
руководителя, которые подмешиваются в каждый следующий запуск.

## Что НЕ делаем в v1

- **Агент ничего не делает сам.** Ни задач сотрудникам, ни сообщений, ни правок данных.
  Только текст для Влада. Полномочия - Фазы 3-4, каждая по отдельному «да».
- **Не дообучаем модель (fine-tuning)** - на объёме «один бриф в день» бесполезно. Тот же
  вывод, что в плане агента продаж (`plans/2026-09-09-sales-agent-learning-from-history.md`):
  контекстный подход + один живой документ-память. Память агента = обычный текст в БД,
  который он сам переписывает каждый день (как плейбук продаж), не embeddings.
- **Не строим отдельный ИИ-слой с доступом к SQL («tool use»).** Контекст собирается
  детерминированно из тех же эндпоинтов, что кормят Панель (`/api/orders_computed`,
  `/api/debt_computed`, `/api/park_summary`, `/api/fleet_summary`, `month_summary`,
  `debt_history`) - агент видит ровно те же цифры, что Влад на экране (принцип «цифры
  бьются везде», `project_data_consistency_principle`). Свободный SQL - Фаза 5.
- **Не шлём в Телеграм.** На сервере нет токена бота (он в Script Properties Apps Script).
  Фаза 2, копейки работы, но требует переноса секрета - отдельный шаг с Владом.
- **Не делаем красивую страницу с графиками.** Бриф - текст и список действий в
  стандартной карточке ГОСТа (клон «Проверка контрагента»). Спарклайны, табло - потом.
- **Не анализируем CRM/звонки/Авито.** v1 - деньги, парк, долги, документы, найм,
  план продаж. CRM-воронка, плейбук продаж, телематика - Фаза 2+ (по одному источнику
  за раз, каждый - проверка «стало ли полезнее»).

## Пре-мортем и совет (09.09, поздно вечером) - что изменилось в плане

«Око Саурона» (10 причин смерти) и совет из 7 голосов - см. лог решений в
`.business/execution/sovet-log.md`. Позиция Влада: **только советник с его кнопкой**, никакой
автономии до доказанного качества; в ближайший месяц важнее **точность советов**, руки потом.
Вердикт совета принял позицию и уточнил: «точность» разбить на три измеримые вещи и делать
по порядку, а «год качества» заменить счётчиком доказательств (30 отзывов Влада + 10 брифов
подряд без ошибок в цифрах), не календарём.

**Три инварианта (нельзя нарушать ни на одной фазе):**
1. Одна цифра - один источник, тот же, что на Панели. Расхождение с экраном - стоп.
2. Ни одно действие к клиенту не уходит без человека. Автономия (если когда-нибудь) только
   для внутренних действий, стоп-лист клиентов/тем ведёт Влад, отзыв автономии - одна кнопка.
3. Правила Влада и гипотезы агента живут раздельно: правила пишутся только из его ответов с
   датой, агент их не редактирует; гипотезы агент переписывает свободно.

## Фазы 2+ - Рост (каждая по отдельному «да» Влада, порядок по совету)

- **Фаза 2 - канал доставки.** Телеграм-сообщение с брифом в 07:05 (перенести
  `TELEGRAM_TOKEN` в `.env` сервера, чат - `CONFIG.TELEGRAM_CHAT_ID`). Условие из вердикта:
  если через 2 недели отзывов меньше 5, Телеграм идёт ПЕРВЫМ, раньше всего остального -
  проблема будет в подаче, не в агенте. До Фазы 2 - письменное решение по данным у kie.ai
  (псевдонимизация или принятие риска; причина смерти №10).
- **Фаза 3 - руки, от имени Влада.** Открывается по счётчику: >= 30 отзывов Влада И 10 брифов
  подряд с пустым `unverified`. «Согласен» кладёт задачу на личную страницу сотрудника
  (`ai_tasks_cache`) **от имени Влада, в форме просьбы с фактами**, без пометки «ИИ»
  (Макиавелли, Карнеги). Только внутренние действия (документы, техника, план менеджеру
  на день). Оценки людей из памяти агента людям не показываются никогда.
- **Фаза 4 - автономия по радиусу, НЕ по счётчику согласий.** Переписано после пре-мортема
  (причина смерти №6): автомат открывается по ТИПУ действия и радиусу (только внутреннее,
  никогда к клиенту), стоп-лист клиентов/тем ведёт Влад, недельный отчёт «что агент сделал
  сам», отзыв - одна кнопка. Перед Фазой 4 - ещё один пре-мортем на живых данных Фазы 3.
- **Фаза 5 - больше источников** (CRM-воронка, плейбук продаж, банковские СМС, телематика) -
  по одному, каждый проверяется «стали ли советы точнее» по `unverified` и отзывам.
- **Фаза 6 - самооценка.** Раз в неделю агент сверяет свои `check_metric` с фактом по
  снимкам и пишет в гипотезы «в чём ошибался». Плюс учёт вызовов ИИ (`ai_calls_log`, причина
  смерти №7) и 5 «золотых» контекстов для проверки правок промпта (причина смерти №8).
- **Слепое пятно совета (держать в голове):** возможно, главная ценность агента не советы,
  а ежедневный сверенный снимок бизнеса с историей - через полгода он ответит «что реально
  сработало». Поэтому чистота цифр и хранение каждого дня - инвестиция, а не побочка.
