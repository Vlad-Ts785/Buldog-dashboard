# План: своя CRM на сервере вместо Битрикс24

**Дата:** 2026-08-26
**Автор:** Клод
**Статус:** Фаза 1 (приём звонков) и Фаза 2 (канбан сделок) готовы, задеплоены,
подтверждены живыми звонками 27.08.2026. Дальше - Фаза 3 (уведомления), Фаза 4
(Авито), Фаза 5 (судьба истории Битрикса).

## Цель

Заменить Битрикс24 своей CRM на `api.yardhub.ru`: приём звонков (и позже Авито),
карточка клиента с одним ответственным, воронка сделок с канбаном - без чужого
интерфейса, без платных пакетов Манго, без бага "ответственный в сделке ≠
ответственный у клиента".

## Контекст

Три недели настройки Битрикс24 (`plans/2026-07-12-bitrix24-crm-integration.md` -
лежит в отдельном неслитом воркчате `nice-hofstadter-73c6dc`, в `main` его нет)
упёрлись в структурную проблему: Битрикс хранит контакт и сделку как ДВЕ разные
сущности с разными ответственными, и правило маршрутизации Манго при повторном звонке
шлёт вызов ответственному ЗА КОНТАКТ, а не тому, кто реально ведёт сделку - плюс само
правило маршрутизации заперто за платной услугой "Расширенные возможности интеграции".
Живой пример бага - сделка 7 999 988-14-56 (22.07): звонок принял Котельников,
сделку вручную переназначили на Гуляеву (она продала и везёт), а контакт клиента
остался на Котельникове. Разбор - `reference/mango-office-bitrix-integration.md`.

Влад (26.08): "Битрикс в итоге мне надоел... давай сделаем свой битрикс в дашборде
нашем. Тем более у нас есть сейчас свой сервер." Направление совпадает с общим планом
переезда на `api.yardhub.ru` (см. [[project_server_migration_strategy]]).

**Решение по объёму (спросил явно, ответы Влада 26.08):**
- Охват: **полная замена Битрикса** (канбан, стадии, причины отказа, своя интеграция
  Авито) - конечная цель, не только звонки.
- Переход: **сразу переключаемся**, без длинного параллельного прогона - но по
  каналам: телефония переезжает первой, Авито продолжает через Битрикс, пока не
  готова Фаза 4.
- Авторизация новых данных: **сделать по уму сразу** - НЕ переиспользовать общий
  ключ, отдельный секрет как везде на сервере.

**Важное уточнение архитектуры (Влад, 26.08, второй заход):** CRM - совершенно новая
сущность, у неё НЕТ наследия в Google Таблицах/Apps Script - значит фронтенд должен
ходить НАПРЯМУЮ на `api.yardhub.ru` (через `checkSession`, уже готовый паттерн для
браузера), БЕЗ Apps Script посередине. Это отличается от остальных вкладок дашборда
(заказы/ДЗ/клиенты), которые всё ещё идут через Apps Script как переходный слой из-за
исторических Google Sheets корней - у CRM таких корней просто нет, поэтому не нужно
повторять этот паттерн. Полностью убирает риск деплоя живого Apps Script (11553
строк, считает зарплаты) ради фичи телефонии.

**Интерфейс - НЕ изобретаем заново, копируем проверенную воронку Битрикса** (Влад,
26.08): название вкладки на дашборде - **"CRM"**. Канбан-доска, визуально похожая на
Битрикс (см. многочисленные скриншоты в этом чате). Стадии те же, что были настроены
и проверены в Битриксе: **Новые заявки → В работе → Сделан расчёт/Отправлено КП →
Переговоры/Отложено → В процессе исполнения → Отказ / Сделка успешна**. Новый клиент
(первый звонок) - карточка сразу падает в "Новые заявки", дальше менеджер
(например, Савиток) звонит и разбирает по канбану вручную. Причина отказа -
ОБЯЗАТЕЛЬНОЕ поле при переносе в "Отказ" (это была главная победа всей битриксовской
истории - причины отказа стали впервые анализируемы 21.07, терять этот выигрыш при
переезде нельзя).

**Почему это реализуемо технически** (проверено по `MangoOffice_VPBX_API.pdf` и
`MangoOffice_VPBX_API_v1.9.pdf`, `Реклама_ЯРД_Apps_Script/`): у Манго есть отдельный
VPBX Integration API - можно зарегистрировать СВОЙ URL, Манго шлёт туда события звонка
(`call_state`: Appeared/Connected/OnHold/Disconnected, `from.number` - телефон
клиента, `to.extension` - внутренний номер сотрудника, который ответил), подписанные
`sign = sha256(vpbx_api_key + json + vpbx_api_salt)`. Формат идентичен между "Версия
событий 1" и "Версия 2" (Версия 2 - те же поля + дополнительные, подтверждено
подсказкой в интерфейсе Манго). Внутренние номера сотрудников известны и загружены
в `crm_employees` (см. раздел "Найдено 26.08" ниже).

**Архитектура сервера** (полная карта - [[project_server_architecture]]): SSH-доступ
есть, авторизация (`checkSession`/`checkServerKey`/`checkWriteKey`) уже готова как
паттерн, конвенции деплоя (бэкап файла перед правкой, `systemctl restart yard-api`
после правки `api/lib/`, таблицы создаются вручную SQL, не авто-DDL) - следовать им.

## Ключевое архитектурное решение v1

**Один клиент = одна запись с одним ответственным.** Не контакт+сделка раздельно, как
в Битриксе - структурно убирает класс бага "разъехались ответственные". Ответственный
назначается первым звонком и НЕ меняется автоматически при повторных звонках другого
сотрудника. Сделки (`crm_deals`) привязаны к клиенту через `client_phone` - у сделки
НЕТ своего отдельного поля "ответственный", он всегда читается через клиента.

- **Два типа OAuth2, не путать:** `ClientCredentials` (доступ к СВОЕЙ учётке, без
  Redirect URL - это то, что нужно нам) и `AuthorizationCode` (доступ от имени ЧУЖИХ
  аккаунтов, требует Redirect URL - НЕ нужно нам, Влад по ошибке начал создавать
  именно такое приложение). «Приложение персональной авторизации» на странице
  Client_id/Secret в кабинете Авито (ЛК → Настройки → Avito API) выдаётся
  автоматически - это и есть ClientCredentials, ничего создавать не требуется.
- Токен живёт 24 часа (`POST https://api.avito.ru/token`).
- `POST /messenger/v3/webhook {url}` - ОДИН URL на весь аккаунт, все чаты сразу.
  Авито после регистрации сразу же дёргает URL тестовым POST, ждёт 200 за 2 секунды.
- **Вебхуки БЕЗ подписи** (в отличие от Mango) - в спецификации НЕТ HMAC/signature
  механизма вообще. Значит секретность обеспечиваем сами: непредсказуемый путь в
  самом URL (`/api/avito/webhook/<случайный токен>`), не короткий/публичный адрес.
- Payload вебхука: `{payload:{type:"message", value:{chat_id, author_id, chat_type,
  content}}, timestamp, version}`. `chat_type`: u2i (по объявлению) / u2u (по
  профилю) / a2u (диалог с самим Авито). `content.call.status:"missed"` - **звонки
  внутри Авито идут через ТОТ ЖЕ вебхук**, отдельного канала для них нет.
- `GET /messenger/v2/accounts/{user_id}/chats` - список чатов (есть `context.value` -
  объявление: title/price_string/url/image).
- `GET /messenger/v3/.../messages/` - история сообщений (НЕ помечает прочитанным
  автоматически - для этого отдельно `POST .../read`).
- `POST /messenger/v1/.../messages {type:"text", message:{text}}` - отправка (только
  текст, до 1000 символов, на 27.08).
- **⚠️ Ключевая архитектурная развилка:** у авито-чата НЕТ номера телефона напрямую,
  только `author_id` (внутренний ID Авито). Вся CRM построена вокруг
  `crm_clients.phone` как первичного ключа ("один клиент = один телефон"). Решение:
  для авито-клиентов ключ = `avito:<author_id>` (синтетический "телефон") - тот же
  принцип "один клиент = одна запись с одним ответственным" сохраняется, просто
  другой тип идентификатора в том же поле. Отдельный эндпоинт `phonesInfoFromChats`
  существует, но требует продукта CPA (лидогенерация, другой тариф) - не в этом
  заходе.
