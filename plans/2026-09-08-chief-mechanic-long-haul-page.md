## 3. Уроки прошлых страниц, которые прямо применимы

1. **«Информационная -> инструментальная»** (ретро 30.08, «Техника» до сих пор не начата):
   экран, который только показывает строку Штатки и ничего не позволяет изменить, Влад
   называет «информационным» и считает недоделанным. Страница механика обязана давать
   ДЕЙСТВИЕ, а не только цифры - иначе это второй «Техника».
2. **«Убери с этой страницы» (25.08, Рыщанов) / «отдельная и единственная» (26.08):**
   тяжёлые самостоятельные разделы - отдельным пунктом меню, а не вкладкой внутри личной
   страницы.
3. **«С позиции руководить, а не делать самому» (26.08):** если это страница РУКОВОДИТЕЛЯ
   (главный механик над линейными механиками и слесарями), каждая рекомендация должна иметь
   адресата-подчинённого. Корень той ошибки был не в тексте, а в данных: не было связи
   «объект -> ответственный». У нас сейчас **нет закрепления механик -> машины/слесари** -
   значит ИИ-задачи «руководительского» типа для механика пока строить не на чём.
4. **«Цифры настоящие или их нет» (29.08):** никаких синтетических значений. Пробег, ТО «по
   регламенту», «следующее ТО через N км» - НЕ показываем, пока нет источника.
5. **«Показывает чушь, все данные есть» (01.09):** два виджета статуса парка на разных
   страницах Влад сверяет глазами немедленно. Статусы на странице механика обязаны
   совпадать с шапкой Планировки один в один - тот же `plan/segs` + `fleet/state`, тот же
   приоритет `computeFleetGroupLive_`, тот же фильтр `Борт`. Не свой расчёт.
6. **«Машины с нулевой выручкой в задачи не попадают - и так понятно, что случилось» (11.08):**
   не писать очевидное.
7. **Таблицы:** только клик по заголовку = сортировка; категориальный фильтр - `<select>` над
   таблицей; никаких input-фильтров под заголовком (04.09, запрет в ГОСТе); tfoot-итог;
   «формула видна, не только результат».
8. **Превью = контракт** (ГОСТ 0.6): сначала превью Владу, потом перенос 1:1.
9. **Google Таблица / 1С остаются** - страница ДОБАВЛЯЕТ способ, не отменяет учёт ремонтов
   в 1С транспортной.

## 5. Проект страницы (v1 - к обсуждению, не контракт)

### 5.1 Принцип
Не «вторая Техника», а **рабочее место человека, который отвечает за то, чтобы 20 бортов
ездили**. Три вопроса, на которые страница отвечает за 10 секунд: *что стоит и почему*,
*что стоит ДОЛГО*, *что сломается следующим*. И одно действие без ухода в другой раздел -
поставить/снять Ремонт или ТО.

Что здесь НЕТ и почему:
- **Зарплаты/выручки/плана** - механик за них не отвечает, и Влад 02.09 сказал «зарплату
  не считаем». Деньги на странице - только ЗАТРАТНЫЕ статьи (запчасти/топливо/штрафы/
  проходные), потому что именно они - его зона (`.business/products/overview.md`).
- **ИИ-задач** - в v1 нет: нет данных «кто за какую машину/слесаря отвечает», без них
  задачи будут либо «сделай сам», либо очевидные («у Х ремонт» - и так видно). Фаза 3,
  если Влад захочет и появится закрепление.
- **Пробега/ТО по регламенту** - источника нет (Omnicomm без одометра).

### 5.3 Данные и права - что придётся сделать на сервере
- Новый `GET /api/mechanic/long_haul` (checkSession, роли `mechanic` + `admin` для
  «Смотреть как»): один ответ = `fleet_summary`(Борт) + `plan/segs`(repair/maint по этим
  гос) + `park_reports` текущего месяца по этим гос (parts/fuel/fines/tolls) +
  `omnicomm_vehicle_locations` (voltage/fuel_volume/actual_date) + документы. Всё это уже
  лежит в MySQL - эндпоинт только собирает и фильтрует по `Борт`, новой логики не считает.
  Сегмент - параметром, чтобы завтра тот же эндпоинт отдал тралы.
- `loadMechanicData_()` -> дёргает его вместо голого `fleet_summary`; `applyRoleUI()` -
  добавить `my-page` в `mechAllowed_`; `render()` - пустить механика в `renderMyPage()`
  новой веткой `renderMyPageMechanic_`.
- Статусы - **ничего нового**: те же `POST /api/plan/seg` / `seg_delete`, что Планировка,
  механику уже разрешены (02.09).
- Определение «главного по длинномерам» - см. вопрос 1 ниже (в коде сейчас ни роли, ни
  признака сегмента у механика нет).

### 5.4 Мобильная версия
Если механик реально в боксе с телефоном - НЕ адаптировать десктоп медиа-запросами, а
сделать по прецеденту `plan-m.html`: отдельная страница, вертикальный список «что стоит»,
одна главная кнопка внизу, вибрация, `--vvh`. Это удвоение работы, поэтому решаем по
ответу на вопрос 3, а не по умолчанию.

1. **Кто.** «У нас часто меняется. Давай делаем интерфейс главного механика, где и тралы, и
   длинномеры, а там решим, кто из них будет видеть полный интерфейс, а кто часть». И
   следом: «надо строить интерфейс главного механика с возможностью потом отключать куски
   информации для линейных механиков. Допустим Велиев видит всю картину, а Самошкин видит
   только длинномерную часть. Но начинать надо с полной версии, чтобы сразу сделать всё, а
   уже потом решить, кто какие блоки информации видит».
   => Страница ОДНА, на ВЕСЬ парк (56 тягачей), с разбивкой Тралы / Длинномеры внутри
   каждого блока (как шапка Планировки и «Статус парка»). Видимость блоков и сегментов по
   человеку - настройка ПОСЛЕ полной версии (Фаза 3), по образцу уже существующего
   `menu_config` с ключом `mechanic:фамилия` (тот же ключ, что у кастомизации меню -
   инфраструктура ключа и admin-настройки через «Смотреть как» уже есть). Название файла
   плана оставлено историческим; сама страница - «Главный механик», не «по длинномерам».
2. **Действия v1** - ставить/снимать Ремонт и ТО (переиспользуем функции Планировки).
   Журнал ремонтов - не сейчас.
3. **Устройство** - «и так, и так»: сначала десктоп, мобильная версия по канону
   `plan-m.html` - следующей фазой, после того как десктоп приживётся.
4. **Зона ответственности** - затраты по парку (запчасти/топливо) из отчёта 1С. НЕ выбраны:
   сроки документов, штрафы ГИБДД, телематика (АКБ/топливо/связь) - в v1 их НЕТ, не
   навязываем. Телематику держим в уме как готовый блок на потом, только если Влад сам
   попросит.

## 7-бис. Следствия для проекта (правки к разделу 5)
- Вердикт-полоса - по всему парку: «В РЕМОНТЕ N ИЗ 56 · тралы A · борта B», справа
  «ГОТОВНОСТЬ ПАРКА XX%» (доля машин НЕ в ремонте/ТО среди всех, без «без водителя» - это
  не зона механика; формула пишется под цифрой, «формула видна»).
- Каждый блок - две колонки/группы «Тралы» и «Длинномеры» (или одна таблица с `<select>`
  «Все / Тралы / Длинномеры» над ней - канон Техники). В превью показать ОБА варианта? Нет -
  берём канон Техники (select), он уже утверждён Владом, лишних вариантов не плодим.
- Блок «Тревоги телематики» - УБРАН из v1.
- Новый эндпоинт - `GET /api/mechanic/fleet` (без сегмента в имени), параметр `segment=`
  опциональный, чтобы Фаза 3 (частичная видимость) отдавала Самошкину только борта на
  сервере, а не прятала на клиенте.

## 8. Риски (пре-мортем, коротко)

- **Второй «информационный экран».** Предохранитель: в v1 обязательно хотя бы одно действие
  (Ремонт/ТО прямо из шторки машины), иначе не сдаём.
- **Расхождение статусов с Планировкой.** Предохранитель: один источник, один расчёт,
  сверка в приёмке «шапка Планировки = плашки страницы» число в число.
- **Устаревший `.business` про механиков.** Предохранитель: не выводить структуру по
  аналогии, спросить (вопрос 1) и обновить `org-structure.md` по ответу.
- **Соблазн показать «ТО через N км».** Предохранитель: правило «цифры настоящие или их нет»
  - без одометра этого блока нет.
- **Мобильная версия вдвое дороже.** Предохранитель: решение только по ответу на вопрос 3.
