# Calltouch + сквозная аналитика в CRM

**Дата:** 2026-09-09
**Статус:** MVP-план (навык «Зодчий»). Фаза 1 - можно строить сразу. Фаза 2+ - ждёт
входа трёх экспертных агентов (маркетолог/эргономист/РОП), см. низ файла.

## Зачем

Влад: «полагаю мы так можем отследить трафик что откуда к нам идёт» + «нужно строить
источники звонков в дашборд» + «сделай страницу сквозной аналитики в CRM - третья
вкладка после Чатов - откуда что, кто взял, кто продал, кто не продал и почему».

**Как выглядит успех MVP (Фаза 1):** на CRM-доске виден блок «Откуда звонят» с реальной
разбивкой по источникам ТОЛЬКО нашего бизнеса (негабарит, arenda-tral.ru), без чужих
номеров (экскаваторы/yard-imperial.ru), данные обновляются из Calltouch автоматически,
не руками.

## Что НЕ делаем в v1

- Не считаем стоимость лида/CPL/ROI - расходов на рекламу в системе ещё нет (Влад
  сказал «в будущем добавим затраты»).
- Не связываем звонок Calltouch со сделкой CRM 1:1 (join по телефону) - это лежит в
  основе Фазы 2, но само по себе отдельная работа с граничными случаями (один клиент
  разными номерами и т.д.) - не рискуем сделать её наспех ради Фазы 1.
- Не трогаем заявки с формы сайта - подтверждено, что форма НЕ шлёт данные в Calltouch
  (0 записей за 5+ недель по `orders-diary`). Это отдельная задача (спросить у того, кто
  ставил форму), не часть этого плана.
- Не выносим общий бюджет предупреждений/квоты Calltouch API в мониторинг - подключение
  новое, простой polling с кэшем в БД достаточен, не отдельный сервис.

## Фаза 1 - MVP (строим сейчас)

- [ ] **VPS: таблица `calltouch_calls`** (своя БД, не Google Sheets - по стратегии
      переезда на сервер) - `call_id` (PK), `call_date`, `phone_number`,
      `caller_number`, `source`, `medium`, `keyword`, `url`, `city`, `device`,
      `duration`, `target_call`, `raw_json`. Наполняется ТОЛЬКО звонками из «наших» 8
      номеров - остальное не сохраняем вообще (не только не показываем - решение принято
      здесь, чтобы не тащить чужие ПДн понапрасну, см. security-review ниже).
- [ ] **VPS: `import/calltouch-calls.js`** - cron-скрипт (аналог существующих
      `import/*.js`), каждые ~15-20 мин тянет `calls-diary/calls` за сегодня и вчера
      (ловит дозапись задним числом), фильтрует по списку наших номеров, upsert по
      `call_id`. Логирование - как у остальных cron (`import/*.log`).
- [ ] **VPS: `GET /api/crm/traffic_sources`** (`checkSession`, доступ - как у остального
      CRM, не завязан на `crmScope_`, т.к. это агрегат по компании, не по клиенту) -
      считает из `calltouch_calls` за период (по умолчанию 30 дней, параметр `days`):
      разбивка по `source`/`medium`, всего звонков, целевых звонков.
- [ ] **Фронт: карточка «Откуда звонят»** на CRM-доске (`#crm-view-board`, рядом с
      `#crm-kpis`/`#crm-leaders` - тот же визуальный ряд) - переиспользует
      `.crm-chip`/цвета источников (`SOURCE_LABELS_`, уже есть в `cardHtml()`),
      расширить палитру для `yandex`/`google`/`direct`. Без graphs/canvas - просто
      список «источник - N звонков (M целевых)», в духе текущего ГОСТа.
- [ ] Проверить вживую (реальный клик, не синтетика - см. прошлые уроки сессии),
      сверить цифры карточки с ручным SQL-запросом.
- [ ] Запись в `README.md` VPS + `DESIGN_SYSTEM.md` (новый визуальный паттерн карточки
      источников - сначала одобрение Влада на скриншоте, если это правда новый паттерн,
      а не переиспользование `crm-chip`).

*4 вопроса:* Решает проблему - да, ровно то, что попросил Влад («строй источники в
дашборд»). Не код ради кода - переиспользуем cron-паттерн и визуальный язык, которые уже
есть. Не усложняет - без join со сделками, без денег, без графиков. Лишнее выкинуто -
не делаем прямого live-запроса к Calltouch с фронта на каждую загрузку страницы (были
бы задержки/лимиты API) - только через свою БД, как и все остальные внешние источники в
проекте.

## Фазы 2+ - Рост (сквозная аналитика, третья вкладка CRM)

Влад: третья вкладка после «Чаты» - «вся инфа откуда что, кто взял, кто продал, кто не
продал почему». Плюс явный запрос - подключить экспертный взгляд (маркетолог,
эргономист, опытный РОП), чтобы страница вышла «супер понятной и информативной», не
просто набором цифр.

**Статус на 09.09:** три параллельных экспертных агента запущены (маркетолог -
метрики/формулы, эргономист - структура страницы и как не превратить в простыню,
РОП - что реально нужно для управления командой) с полным контекстом проекта (модель
данных CRM, причины отказа, объём данных, факты о Calltouch выше). Этот раздел плана
ДОПОЛНЯЕТСЯ их выводами перед началом реализации - не начинаем кодить Фазу 2 вслепую.

Уже понятно заранее (не ждёт экспертов):
- Данные: `crm_deals` (стадии/причины отказа/сумма/ответственный через клиента),
  `crm_messages`/`crm_calls` (канал = Авито чат/звонок, обычный звонок),
  `calltouch_calls` (трафик сайта, после Фазы 1) - три источника лидов, у каждого свой
  охват достоверности (Calltouch - только звонки с сайта; Авито - свой канал целиком;
  прямые звонки - Mango).
- «Кто взял / кто продал / не продал почему» - уже есть как данные (ответственный на
  клиенте, `stage='won'/'lost'`, `loss_reason`) - не хватает СВОДНОЙ страницы, а не
  самих данных.
- Место под будущий блок затрат на рекламу - зарезервировать в композиции страницы
  (директива эргономисту), не строить сейчас.

*4 вопроса (предварительно, уточнить после экспертов):* Решает проблему - да (прямой
запрос директора). Не оверинжиниринг - есть риск скатиться в BI-систему для контента,
которого физически мало (десятки сделок в месяц) - экспертам явно поставлена задача
не строить статистику на маленьких выборках. Не усложняет v1 - будет ОТДЕЛЬНАЯ фаза
от Фазы 1 трафика, не блокирует её. Лишнее - решится после отчётов экспертов.
