## 2. Архитектурное решение (рекомендация)

### 2.1 Форма: PWA, две точки входа, один сервер

```
files/index.html  (TS HUB, как сейчас)      files/driver.html  (НОВЫЙ, тонкий)
  admin / manager / logist / mechanic          driver
  PWA: manifest.json + sw.js                   PWA: driver.webmanifest + тот же sw.js
        \                                         /
         \---------  api.yardhub.ru  ------------/
                 (вся логика, все данные)
```

- **Офисные роли** (менеджеры, логисты, руководители, механик, Влад) - тот же `index.html`,
  установленный на телефон как PWA. Их экраны уже есть, Планировка уже мобильная, push уже
  работает. Дорабатываем точечно (раздел 4, Фаза 4).
- **Водители** - отдельная страница `files/driver.html`: экран из одной карточки и 4-5 кнопок,
  ~50 КБ вместо 2,6 МБ. Причины: (а) водителю не нужен BI-дашборд, ему нужен "мой рейс сейчас";
  (б) 4G на объекте - 2,6 МБ с 820 КБ шрифтов для КП неприемлемы; (в) отдельный файл =
  отдельный кэш и отдельный ритм деплоя, не ломаем 24 тысячи строк офисного монолита;
  (г) принцип ГОСТа "не дублировать бизнес-логику" соблюдён - логики на фронте водителя нет
  вообще, только вызовы `/api/driver/*`.
- **НЕ делаем:** Capacitor/нативную обёртку (Google-логин офисных ролей ломается во встроенном
  WebView - `disallowed_useragent`; две кодовые базы навсегда). TWA для Google Play - только
  если появится конкретная причина (Фаза 7).
- **iPhone** - тем же кодом: Safari -> "На экран Домой". Push на iOS работает с 16.4+ только у
  установленной PWA - это ограничение Apple, не наше.

### 2.2 Вход водителя - развилка (решает Влад, раздел 3, вопрос 1)

Рекомендация: **персональная ссылка-приглашение с долгоживущим токеном устройства.** Логист
(или Влад) в карточке водителя в Справочниках нажимает "Выдать доступ" -> получает ссылку/QR
-> отправляет водителю в WhatsApp/Telegram -> водитель открывает, телефон "запомнен" на год.
Тот же HMAC-формат, что у `session_token` и break-glass, с `role=driver` + `person_id`
(`sprav_people.id`). Отзыв - кнопкой в той же карточке (таблица `driver_devices`). Ни Google,
ни SMS-провайдера, ни нового пароля. Риск "переслал ссылку другому" - смягчается тем, что
токен одноразово привязывается к первому устройству и виден в карточке ("вошёл 03.09 с
Android"), отзыв за секунду.

### 2.3 Модель данных (сервер, MySQL) - минимальные добавления

```
plan_segs           + driver_person_id  (снимок в момент назначения/создания, backfill из
                      fleet_assignments для открытых рейсов)
                    + order_number      (nullable; автоподсказка из orders_normalized по
                      заказчику+дате - закрывает и Фазу 4 плана Планировки "стыковка с
                      План заданием")
                    + stage             (planned/enroute/at_load/loaded/at_unload/unloaded/done)
                    + stage_updated_at

trip_events         id, seg_id, driver_person_id, event, at, lat, lng, speed, note,
                    source (driver/logist/auto), created_at
                    -- lat/lng сервер берёт САМ из omnicomm_vehicle_locations по госномеру
                       в момент события: доказательство места без запроса геолокации у
                       телефона водителя (и без его разрешения на неё)

trip_photos         id, seg_id, event_id, stored_name, mime, size_bytes, uploaded_by,
                    uploaded_at  -- по образцу sprav_asset_documents, папка uploads/trip_photos

driver_devices      id, person_id, token_hash, label (модель телефона), issued_by,
                    issued_at, first_seen_at, last_seen_at, revoked_at

push_subscriptions  = crm_push_subscriptions + колонка person_id/role + topic;
                    crmSendPush_ -> sendPushTo_(emails|person_ids, payload)

payroll_1c (Фаза 5) person_key, period (YYYY-MM), lines JSON, total, imported_at
```

### 2.4 Эндпоинты

```
Водитель (checkSession с role=driver, данные ТОЛЬКО свои):
  GET  /api/driver/me            карточка + машина (открытая сцепка) + сегодняшний/следующий рейс
  GET  /api/driver/trips?days=7  история моих рейсов со стадиями
  POST /api/driver/trip_event    {seg_id, event, note}  -> сервер штампует точку Omnicomm
  POST /api/driver/trip_photo    multipart, {seg_id, event_id}
  POST /api/driver/push/subscribe
  GET  /api/driver/payroll       (Фаза 5)

Офис (существующие + поля):
  GET  /api/plan/segs            + driver_person_id, stage, stage_updated_at, order_number
  GET  /api/plan/activity        + события trip_events (загрузился/выгрузился/фото)
  GET  /api/plan/trip_photos?seg_id=
  POST /api/sprav/driver_invite  {person_id} -> ссылка; POST /api/sprav/driver_revoke
```

Уведомления (адресные): водителю - "назначен рейс", "рейс изменён/отбой"; логисту - "водитель
загрузился/выгрузился", "стоит на погрузке > N часов"; менеджеру - "водитель назначен" (данные
на пропуск - закрывает бэклог из плана Планировки "менеджеры дёргают логистов по каждому
пропуску"), "груз выгружен" (можно звонить заказчику про документы/оплату).

### 2.5 Зарплата - развилка (раздел 3, вопрос 3)

Формул зарплаты водителей в системе нет и придумывать их на фронте НЕ надо (инвариант
проекта "цифры настоящие или их нет"). Правильный источник - отчёт 1С по начислениям, тем же
FTP-каналом, что заказы/ДЗ/парк, в таблицу-снимок `payroll_1c`. Это одновременно закрывает
пробел "истории зарплат нет" и для менеджеров/логистов: расчётный блок на личной странице
остаётся как "прогноз", а строка из 1С - как "начислено". Что именно 1С умеет выгружать
(ЗУП? начисления по сотрудникам? сдельно по рейсам?) - вопрос Владу к бухгалтерии, без
ответа Фаза 5 не планируется в деталях.

## 3. Развилки - РЕШЕНО Владом 2026-09-03

1. **Вход водителя: ссылка-приглашение** (раздел 2.2). Telegram/SMS/Google - отвергнуты
   для v1; SMS-код возможен позже как апгрейд поверх той же таблицы `driver_devices`.
2. **Пилот: колонна длинномеров, Барыльченко** (18 водителей, 2 недели), затем тралы
   (Дьячков, 36). Список водителей колонны - `.business/company/org-structure.md`, раздел 4;
   в `sprav_people` их надо будет пометить (колонна = отдельное поле или роль-тег - решить
   в Фазе 1, в справочнике сейчас колонны нет).
3. **Зарплата из 1С: есть готовый отчёт по начислениям по сотрудникам.** Значит Фаза 5 -
   тот же приём, что для заказов/ДЗ/парка: рассылка 1С на FTP-приёмник + импорт-скрипт +
   таблица-снимок. Формат файла (колонки, период, идентификатор сотрудника - ФИО или
   табельный номер) - запросить у бухгалтерии ДО написания импорта; ключ сопоставления с
   `sprav_people` - по ФИО с нормализацией `ordCleanName()`-стиля, как везде в проекте
   (ИНН/СНИЛС в справочнике есть - надёжнее ФИО, если 1С отдаёт).
4. **Стадии: 5 + "Проблема"** - Выехал / На погрузке / Загрузился (+фото) / На выгрузке /
   Выгрузился (+фото); "Проблема" = текст + фото + push логисту немедленно. Активна только
   следующая по порядку кнопка, назад - через логиста (не давать водителю "откатить" стадию,
   иначе история недостоверна; исправление - действие логиста, пишется в `trip_events` с
   `source=logist`).

## 5. Пре-мортем (где это провалится, если не заложить сейчас)

1. **Водители не нажимают.** Приложение должно давать ИМ пользу с первого дня: свой рейс
   с адресом и контактом (вместо звонка логисту), потом - зарплата. Логист видит "не нажал"
   и звонит - через 2 недели привычка. Пилот на одной колонне, не на всех.
2. **Нет связи на объекте.** Офлайн-очередь и сжатие фото - не "потом", а Фаза 2.
3. **Двойной ввод.** "План задание" (Google Таблица менеджеров) остаётся навсегда (память
   `feedback_gradual_transition_sheets_to_dashboard`) - чекбоксы "подтверждение водителя"
   там не трогаем и не заставляем; приложение - параллельный ход.
4. **ПДн и фото.** Телефоны/паспорта водителей во фронт не идут (правило Планировки). Фото
   могут содержать документы и номера - хранение только за `checkSession`, не публично,
   ротация через 12 месяцев, объём ~15 ГБ/год при 50 рейсах/день (диск 38 ГБ - следить).
5. **Сервер - единая точка отказа без Sheets-фолбэка.** У водителей его нет и не будет.
   Есть ежедневный бэкап и `/api/health`; нужен внешний uptime-пинг (бесплатный сервис) с
   алертом в Telegram - добавить в Фазу 1.
6. **Стадии без номера заказа = красивая, но бесполезная для денег история.** Поле
   `order_number` в заявке - обязательная часть Фазы 1, иначе зарплата по рейсам не свяжется.
7. **Кэш.** Без `VERSION` водитель может неделю сидеть на старом `driver.html` - Фаза 0.
8. **Параллельные сессии.** Планировка и миграция с Apps Script правят тот же `server.js`
   и `plan_segs` прямо сейчас - координация через SendMessage до каждого `scp`, git на VPS
   уже есть (инвариант 2 плана миграции).

## 6. Что сознательно НЕ делаем

- Не переписываем `index.html` "под мобильный" целиком - только личные страницы и Планировка.
- Не считаем зарплату водителей формулами на фронте - только из 1С.
- Не заводим водителям Google-аккаунты и не строим SMS-логин, пока не отвергнута ссылка-
  приглашение.
- Не трогаем Apps Script вообще.
- Не публикуем в сторы.
