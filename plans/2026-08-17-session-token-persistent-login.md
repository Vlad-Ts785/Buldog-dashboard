# План: сессия на 1-2 дня вместо перелогина через Google каждый час

**Дата:** 2026-08-17
**Автор:** Клод (с Владом)
**Статус:** в работе (код готов, ждёт деплоя)

## Цель

Один раз войти через Google - и дашборд не спрашивает логин снова минимум 1-2 суток, вместо
текущего ~1 часа.

## Контекст

Повод (Влад, 2026-08-17): "постоянно раз в час или раз в полчаса требует перезахода. Это
неудобно. Можно сделать так, чтобы один раз через Google залогинились, и там день-два никто не
трогает тебя".

Текущий механизм ([files/index.html:1163-1196](../files/index.html#L1163)): фронтенд получает
Google `id_token` (JWT) через Google Identity Services (кнопка "Войти через Google"), хранит
его в `localStorage`, шлёт на КАЖДЫЙ запрос к `doGet()`. Backend
([scripts/full_script_final.js:3600-3606](../scripts/full_script_final.js#L3600)) на каждый
запрос ходит в `https://oauth2.googleapis.com/tokeninfo` и проверяет токен - тот живёт ~1 час
(это срок жизни, который выдаёт сам Google, мы его не контролируем). Как только токен протухает,
следующий запрос получает `needLogin`, фронтенд стирает токен и показывает экран входа.

**Рассмотренная и отклонённая альтернатива**: тихое обновление через
`google.accounts.id.prompt()` (silent One Tap). Не выбрано - поведение зависит от браузера/
FedCM/cookie-политики, не гарантирует именно "день-два", может продолжать спрашивать
подтверждение мимо нашего контроля.

**Выбранное решение**: свой подписанный токен сессии поверх Google-логина. Google остаётся
единственным источником проверки личности при ПЕРВОМ входе; после этого backend сам выдаёт
токен на 48 часов (HMAC-подпись, секрет в Script Properties, генерируется автоматически при
первом обращении - без ручного шага для Влада). Фронтенд дальше ходит по этому токену,
Google трогаем заново только когда токен истёк.

**Что НЕ меняется**: авторизация (роль/имя по листу "Доступ") по-прежнему проверяется на
КАЖДЫЙ запрос через `getAccessRole_` - длинная сессия влияет только на то, что не нужно
повторно подтверждать личность через Google. Отзыв доступа (удалить строку из "Доступ")
сработает мгновенно и с длинной сессией - следующий же запрос получит `access.role` пустым.

## Фазы

### Фаза 1. Backend: выпуск и проверка токена сессии (~30 мин)
- [x] `getSessionSecret_()` - секрет в Script Properties (`SESSION_SECRET`), генерируется
      автоматически при первом вызове, если его ещё нет (не нужно вручную заводить, как
      `TELEGRAM_TOKEN`).
- [x] `issueSessionToken_(email)` - `{email, exp: now + 48ч}` -> base64url + HMAC-SHA256 подпись.
- [x] `verifySessionToken_(token)` - проверка подписи (constant-time сравнение, не через `===`
      с ранним выходом - защита от timing-атаки на HMAC) + срок годности, возвращает email
      или `null`.

### Фаза 2. Backend: подключить к doGet() (~20 мин)
- [x] Наверху `doGet()` - сначала пробуем `session_token` из параметров, если его нет/истёк -
      падаем на существующую проверку `id_token` через Google (как сейчас).
- [x] После успешной проверки доступа - выпускаем свежий `session_token` (скользящее окно:
      каждый заход при валидной сессии продлевает её ещё на 48ч от текущего момента, поэтому
      если Влад открывает дашборд хотя бы раз в 1-2 дня, сессия не обрывается никогда).
- [x] Кладём `session_token` в ответ только у трёх "полных" загрузок страницы (admin по
      умолчанию, `getManagerView_`, `getLogistView_`) - не в каждый мелкий `action=...` запрос,
      этого достаточно (фронтенд читает его один раз при загрузке страницы).

### Фаза 3. Фронтенд: использовать токен сессии (~20 мин)
- [x] `apiUrl()` - шлёт оба токена, если есть (`id_token` и `session_token`), backend сам
      разбирается, какой использовать.
- [x] `loadData()` - если ответ содержит `session_token`, сохраняем в `localStorage`.
- [x] `initGoogleSignIn()` - если есть ЛИБО `id_token`, ЛИБО `session_token` - сразу грузим
      данные, экран входа не показываем.
- [x] Везде, где сейчас чистим `id_token` при `needLogin`/логауте - чистим заодно и
      `session_token`.

### Фаза 4. Проверка и деплой (~20 мин)
- [x] Синтаксис (`node --check`), сравнить структуру ответа до/после для всех трёх ролей.
- [ ] Деплой по протоколу (`clasp pull` -> diff с git HEAD -> sync чужой работы, если есть ->
      `clasp push` + `create-version` + `redeploy`).
- [ ] Влад проверяет вживую: логинится один раз, ждёт пару часов (или переживает истечение
      старого 1-часового `id_token` вручную), убеждается что дашборд НЕ просит войти снова.

## Критерии готовности

- [ ] После первого входа через Google дашборд не просит логин повторно минимум 24 часа при
      обычном использовании (открывать хотя бы раз в этот период).
- [ ] Отзыв доступа (удаление строки из листа "Доступ") продолжает работать мгновенно, даже
      если у человека есть свежий `session_token`.
- [ ] Подделанный/повреждённый `session_token` не даёт доступа (сервер откатывается на
      требование `id_token`/логина, не падает с ошибкой 500).

## Риски

- Новый секрет (`SESSION_SECRET`) в Script Properties - тот же уровень чувствительности, что
  `TELEGRAM_TOKEN` (уже там есть). Компрометация секрета позволила бы подделать токен на
  ЛЮБОЙ email - но `getAccessRole_` всё равно проверяется по листу "Доступ", так что урон
  ограничен тем, что уже разрешено этому листу. Секрет не логируется, не возвращается клиенту.
- Скользящее окno (продление при каждом заходе) означает, что теоретически сессия может жить
  бесконечно долго при регулярном использовании - это осознанный компромисс ради удобства
  (внутренняя система, малое число людей, доступ и так живой список в "Доступ").
- Если позже понадобится инвалидировать ВСЕ сессии разом (не только конкретный email) -
  достаточно сменить `SESSION_SECRET` вручную в Script Properties, все токены разом станут
  невалидными - explicitly не автоматизируем сейчас, это ручной аварийный рубильник.
