# Дьячков - личная страница (тралы) + «Зарплата машинистов» по сегменту у обоих начальников автоколонн

Влад, 15.09: "Мне нужна личная страница для Дьячкова. Всё то же самое как у Барыльченко,
только всё по тралам. И без блока расчёт зарплаты на личной странице. Так же добавить
блок Зарплата машинистов, но у него должны показываться только тральщики. Барыльченко
добавить тоже зарплаты машинистов - у него должны показываться только длинномерщики."

## Блокер

Дьячков (`ЗК-0002152`, sprav_people) - **нет email** (phone/адрес тоже пусты). Без email
нельзя завести `access_users` - он физически не сможет залогиниться. Всё остальное (код,
классификация, "Смотреть как") делаем сейчас; `access_users` INSERT - когда Влад пришлёт
email.

## Найдено при разборе - список мест ШИРЕ памяти `project_avtokolonna_head_role_pattern`

Кроме уже известных 3 списков (`COLUMN_HEAD_SUR_FRONT_`/`MENU_COLUMN_HEAD_SUR_`/VPS
`COLUMN_HEAD_SUR_`), нашёлся **четвёртый смысл** того же списка на VPS
(`isColumnHeadName_`, `api/server.js:8794`) - решает, кому лепить `payload.orders.long_haul`
(бандл машин типа "Борт"/длинномер) при реальном входе. Он **захардкожен на длинномеры**
для ЛЮБОГО, кто в списке - для Дьячкова (тралы) это неверно. Значит просто добавить
фамилию недостаточно - список должен стать **картой фамилия->сегмент**, не плоским
массивом.

`vehicle_bucket` в `/api/driver_payroll` УЖЕ различает три категории на уровне ВОДИТЕЛЯ
(`api/server.js:2731`): `"трал"` / `"длинномер"` / `"файмонвиль"` (через
`fleet_assignments`+`vehicle_types_effective`+`fayDrivers`) - это и есть источник для
нового блока "Зарплата машинистов", `/api/driver_payroll` сейчас `requireRole_("admin")`
ТОЛЬКО - нужен новый доступ для роли logist, СТРОГО ограниченный своим сегментом на
сервере (клиенту не доверяем, тот же принцип, что `mechanicSegmentForName_`).

## План

### VPS (`api/server.js`, отдельный git-репозиторий на сервере)

1. `MENU_COLUMN_HEAD_SUR_` (:417) += `"дьячков"` - тир меню (общий для обоих, не зависит
   от сегмента).
2. Заменить плоский `COLUMN_HEAD_SUR_`/`isColumnHeadName_` (:8794-8795) на
   `COLUMN_HEAD_FLEET_ = { "барыльченко": "long", "дьячков": "tral" }` +
   `columnHeadFleetFor_(name)` -> `"long"|"tral"|null`. Обновить ВСЕ вызовы
   `isColumnHeadName_`/`isVasinName_` в ветке `/api/main_payload` (:8918) - Vasin и
   `fleet==="long"` строят `long_haul` (машины `type==='Борт'`, как сейчас),
   `fleet==="tral"` строит НОВЫЙ `tral_haul` (те же поля, машины `type!=='Борт'`) -
   переиспользовать `buildLongHaulPayload_`, параметризовав фильтр машин снаружи (сама
   функция уже принимает готовый список - только вызывающий код должен фильтровать по
   нужному типу и класть в `payload.orders.long_haul` ИЛИ `payload.orders.tral_haul`
   в зависимости от сегмента - фронт разберёт по имени поля, не по "typeof бандл").
3. `VASIN_FORMULA_SUR_` (:426) - **НЕ трогать**, Дьячкова туда не добавлять (Влад явно
   сказал - без блока расчёта, будущая формула для Дьячкова ещё не решена).
4. Новый эндпоинт `GET /api/my_driver_payroll` (`checkSession`, без `requireRole_` -
   сам решает по роли): admin - 400 (использовать `/api/driver_payroll`); logist -
   резолвит `own` через `access_users` по email сессии (тот же приём, что
   `ownSur_()`/`mechanicSegmentForName_`), смотрит `COLUMN_HEAD_FLEET_[own]` - если нет
   (обычный логист, не начальник автоколонны) - 403; иначе дёргает ТУ ЖЕ логику, что
   `/api/driver_payroll` (переиспользовать функцию сборки строк, не копировать), но
   отдаёт ТОЛЬКО строки с `vehicle_bucket === (fleet==='long' ? 'длинномер' : 'трал')`
   (файмонвиль исключён из ОБОИХ - Влад просил именно "тральщики"/"длинномерщики").
5. `access_users` INSERT для Дьячкова - ПОСЛЕ получения email от Влада.

### Apps Script (`scripts/full_script_final.js`) - фолбэк-путь - ОСОЗНАННО ОТЛОЖЕНО

Живой тест 15.09 подтвердил: `/api/main_payload` (VPS) уже сам обслуживает manager/logist
напрямую (не только admin, как думала устаревшая заметка в CLAUDE.md) - оба сегмента
(long_haul/tral_haul) отдаются корректно БЕЗ обращения к Apps Script вообще. Значит
`COLUMN_HEAD_SUR_`/`buildLongHaulBundle_` в Apps Script - чистый фолбэк на случай
недоступности VPS, вероятность живого срабатывания для Дьячкова низкая.

Там `buildLongHaulBundle_` ТАК ЖЕ захардкожена на длинномеры, как была VPS-версия ДО
фикса (не сегмент-осознанная) - зеркалить её на тралы означало бы повторить весь объём
работы по `orders-calc.js` (funnel/deals/driver_no_waybill для тралов) ЕЩЁ РАЗ в Apps
Script. Решение: `COLUMN_HEAD_SUR_` НЕ трогать (Дьячков туда не добавлен) - если фолбэк
когда-нибудь реально сработает для него, он просто не получит `long_haul` бандл (мягкий
отказ - "нет данных"), а не НЕВЕРНЫЙ (длинномерный) бандл. Осознанный компромисс, не
забытое место - отдельным заходом, если станет реально нужно.
