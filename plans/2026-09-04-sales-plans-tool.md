# Планы продаж - инструмент в Справочниках (уход от Google-листа «Планы_менеджеров»)

**Статус: в работе 04.09.2026.** Закрывает пункт 4.1 плана
`plans/2026-09-01-apps-script-elimination.md`.

## Запрос Влада (дословно, 04.09.2026)

«Нужно, чтобы ты эти планы встроил в дашборд. Но не просто захардкодил. Создал
справочники, планы продаж. Сделал из этого инструмент, где я каждый месяц могу
выставить план сотрудникам. То есть мы уходим от Excel-таблиц. И делаем теперь всё через
наш дашборд и сервер.»

Контекст: перед этим в чате согласован план на сентябрь 2026 (итог 70 млн, см. таблицу
ниже) - его нужно завести первым через новый инструмент, не руками в лист.

## Что было (разведка 04.09)

- Источник истины - Google-лист «Планы_менеджеров» (Месяц | Фамилия | План). Влад правит
  руками раз в месяц.
- На сервере уже есть таблица `manager_plans` (month_key, manager, plan) и её читают
  `/api/orders_computed` и `/api/main_payload` через `orders-calc.js joinManagerPlans`.
  НО каждые 3 часа `runAll()` в Apps Script вызывает `syncManagerPlansToServer_()` -
  `POST /api/manager_plans` (checkServerKey) делает `TRUNCATE` и перезаливает таблицу из
  листа. То есть любая правка в MySQL жила бы до следующего runAll.
- `getOrdersData()` в Apps Script накладывает `joinManagerPlans_` из ЛИСТА поверх
  серверного ответа («всегда берём план свежим из листа», 2026-08-26) - второй путь, по
  которому лист побеждает сервер.
- Найден рассинхрон списков `ACTIVE_PLAN_KEYS`: в Apps Script уже есть `'ратников'`, на
  сервере (`api/lib/orders-calc.js`) - нет (класс бага
  `project_orders_calc_vps_sync_gotcha`). План Ратникова 10 млн на сервере не попадал бы
  в `salesPlan`.

## Решение

Направление данных разворачивается: **сервер = источник истины, лист = read-only
зеркало** (инвариант 3 плана миграции: «привычный Владу аудит глазами сохраняется»).

### Сервер (VPS, `api/server.js`, `api/lib/orders-calc.js`)
- `manager_plans` + колонки `updated_by`, `updated_at` (кто и когда правил).
- `GET /api/manager_plans?month=YYYY-MM` (checkSessionOrServerKey, admin для сессии) -
  строки месяца + список месяцев, по которым есть план. Тот же роут отдаёт Apps
  Script'у (ключ) данные для зеркала и для `getManagerPlans_`.
- `POST /api/manager_plans/set` (checkSession, admin, JSON `{month, plans:[{manager,
  plan}]}`) - транзакция: удалить строки месяца, вставить присланные, запись в
  `sprav_audit_log` (entity_type `manager_plans`, entity_id = месяц).
- Старый мост `POST /api/manager_plans` (TRUNCATE всей таблицы) - ОТКЛЮЧЁН (405 с
  пояснением), чтобы ни один забытый вызов не стёр планы, введённые через UI.
- `ACTIVE_PLAN_KEYS` += `'ратников'` (паритет с Apps Script).

### Apps Script (`scripts/full_script_final.js`) - только разворот существующих мостов,
без новой бизнес-логики (инвариант 1 плана миграции)
- `getManagerPlans_(ss, monthKey)`: сервер первым (`GET /api/manager_plans?month=`),
  лист - тихий фолбэк при недоступности сервера.
- `syncManagerPlansToServer_()` -> `mirrorManagerPlansFromServer_()`: сервер -> лист
  (лист «Планы_менеджеров» переписывается целиком, в шапке пометка «ЗЕРКАЛО сервера,
  правится в дашборде: Справочники -> Планы продаж»). Вызов в `runAll()` заменён.

### Фронтенд (`files/index.html`, раздел «Справочники»)
- Новая вкладка «Планы продаж»: переключатель месяца (← Сентябрь 2026 →), таблица
  Сотрудник | План (₽, ввод с разделителями), строки - менеджеры из Справочников (роль
  «Менеджер») + все ключи, уже присутствующие в плане месяца + служебные строки
  «Внутренние перевозки» и «ВП своего парка (план Рыщанова)». Итоги: по менеджерам и с
  внутренними. Кнопки «Скопировать из прошлого месяца», «Сохранить». После сохранения -
  тост + перезагрузка данных дашборда (план сразу виден на Панели/По менеджерам).
- По ГОСТу: токены, `tbl`/`tab-btn`, без эмодзи и цветных полосок, `autocomplete="off"`,
  уведомления только тостом.

## Риски / что не делается
- Лист «Планы_менеджеров» после разворота править руками БЕССМЫСЛЕННО - зеркало
  перепишет его при следующем runAll. Пометка в шапке листа об этом.
- Прошлые месяцы (июнь-август) остаются в `manager_plans` как были (перенесены мостом
  ранее), редактируемы через тот же инструмент.
- Планы ВП по машинам (`vehicle_plans`, Штатка) - другая сущность, не трогается.
