# План: 5 задач на день от ИИ + совет по плану (личная страница менеджера)

**Дата:** 2026-08-12
**Автор:** Клод
**Статус:** реализовано, ждёт деплоя + ручного шага от Влада (Script Property)

## Цель

Влад: у Васина уже есть 5 задач на день по простому алгоритму (жёсткие правила - см.
`plans/2026-08-11-vasin-per-vehicle-forecast-tasks.md`). Для МЕНЕДЖЕРА хочет то же самое, но
"изгенерированные ИИ через kie.ai" - раз в день модель смотрит на личную ситуацию менеджера
(план/факт/прогноз, топ заказчиков, пропавшие клиенты, дебиторка) и сама формулирует 5 задач +
совет, как выполнить план. Модель - GPT-5 (reasoning) через kie.ai (подтверждено с Владом -
рекомендованный вариант, лучше подходит для бизнес-советов, чем более быстрый/дешёвый Gemini
3.5 Flash).

## Архитектура (ключевое решение)

Весь дашборд общается с Apps Script только через `GET doGet(e)` (query-параметры, без POST) -
см. `apiFetchJson()` во фронтенде. Значит контекст для ИИ нельзя "собрать во фронтенде и
отправить" (слишком много данных для query-строки) - контекст собирается ЦЕЛИКОМ НА БЭКЕНДЕ.

Но часть расчётов (прогноз по `calcPaceRatio_`, агрегаты ДЗ `computeDebtAggregates_`) живут
только во фронтенде (`files/index.html`), в Apps Script их нет. Дублировать всю фронтенд-логику
в бэкенд - лишний риск разъехаться. Решение: НЕ копировать сложную логику 1-в-1, а собрать
на бэкенде упрощённый, но достаточный набор фактов из УЖЕ существующих чистых бэкенд-функций
(`computeLostCustomersForManager_`, `getDebtData`, `by_manager_detail.doc/top_customers`), плюс
маленький честный порт `calcPaceRatioServer_` (10 строк, единственное, что реально нужно
дублировать - для прогноза к концу месяца).

Ключ `KIE_API_KEY` - только в Script Properties (не в коде, не в .env читаем целиком). Влад
должен once вручную добавить Script Property `KIE_API_KEY` в редакторе Apps Script (то же
значение, что в `.env` для других проектов) - Клод не может прочитать `.env` целиком по правилу
репозитория, и не имеет доступа к живому Apps Script редактору напрямую.

## Кэширование - "раз в день", не при каждом открытии страницы

Генерация у reasoning-модели небольшая, но не мгновенная (~5-15 сек) - если звать при каждом
рендере страницы, это и медленно, и дорого (кредиты kie.ai). Решение: новый лист
`ИИ_Задачи_Менеджеров` (Дата | Менеджер | Задачи_JSON | Совет_по_плану | Модель |
Сгенерировано_в). Флоу:

1. Менеджер (или admin-предпросмотр) открывает личную страницу - блок "Задачи на сегодня (ИИ)"
   сразу дёргает `action=generate_ai_tasks`.
2. Бэкенд ищет строку на СЕГОДНЯ (Europe/Moscow) для этого менеджера в кэш-листе - если есть,
   отдаёт её мгновенно, БЕЗ обращения к kie.ai.
3. Если нет - строит контекст, зовёт GPT-5, парсит ответ, сохраняет строку, отдаёт результат.
4. Весь следующий день (и все повторные открытия страницы в этот день, включая
   admin-предпросмотр того же менеджера) - используют этот же кэш. Новый вызов ИИ - только
   на следующий календарный день или если вчерашняя генерация упала с ошибкой (ошибки не
   кэшируются - можно повторить).

Только для ТЕКУЩЕГО (живого) месяца - для прошлого периода блок скрыт целиком (задачи "на
сегодня" не имеют смысла для закрытого месяца).

## Реализация

### Бэкенд (`scripts/full_script_final.js`)
- `AI_TASKS_SHEET = 'ИИ_Задачи_Менеджеров'`, `ensureAiTasksSheet_`, `findAiTasksCacheRow_`,
  `saveAiTasksCache_` - тот же паттерн get-or-create листа, что `ensureDebtStatusSheet_`.
- `calcPaceRatioServer_(period)` - честный порт `calcPaceRatio_` из фронтенда (единственное
  дублирование, простая арифметика день/дней в месяце).
- `buildManagerAiContext_(ss, orders, managerName, period)` - план/факт/% (из `by_manager`),
  прогноз (`calcPaceRatioServer_`), топ-8 заказчиков и воронка документов (из
  `by_manager_detail[name]`), пропавшие клиенты 3 мес. топ-8 по выручке
  (`computeLostCustomersForManager_`), дебиторка - топ-6 должников по балансу + итого баланс +
  кол-во должников (`getDebtData`, отфильтровано на менеджера).
- `buildAiTasksPrompt_(managerName, context)` - инструкция на русском, строго JSON-ответ:
  `{"tasks":[{"title":"...","why":"..."} x5], "plan_advice":"..."}`, без markdown-обёртки, без
  выдуманных фактов вне переданных данных, обращение на "ты", без длинного тире.
- `callKieGpt5_(promptText)` - `POST https://api.kie.ai/codex/v1/responses`, `model:'gpt-5-4'`,
  `reasoning:{effort:'medium'}`, ключ из `PropertiesService.getScriptProperties()`, ответ из
  `output[].content[].text` (см. `docs.kie.ai`, см. reference-память kie.ai).
- `parseAiTasksResponse_(rawText)` - защитный парсинг (снимает возможные ```json fences),
  валидирует, что `tasks` - массив (обрезает/дополняет до 5, не падает на 4 или 6).
- `generateManagerAiTasksCached_(ss, orders, managerName, period)` - оркестратор кэш/генерация.
- `doGet`: `action=generate_ai_tasks` - роль `manager` форсит `access.name` (игнорирует
  параметр `manager` от клиента, тот же паттерн, что `manager_lost_customers`), `admin` может
  указать любого. Роль `logist` - вне охвата v1 (Влад просил именно "у менеджера" - Васин и
  наёмные логисты остаются на старом алгоритмическом блоке, расширение - в бэклог).

### Фронтенд (`files/index.html`)
- Новый блок "🤖 Задачи на сегодня (ИИ)" в `renderMyPageManager` - СРАЗУ после шапки/периода,
  ДО "Выполнение плана продаж" (первое, что менеджер видит, открыв страницу утром).
- Только для текущего месяца (`!myPagePeriod`) - для прошлого периода блок не рендерится.
- Состояния: загрузка ("Генерируется... обычно 5-15 сек"), успех (5 пронумерованных задач +
  абзац совета), ошибка (текст ошибки + кнопка "Повторить" - ошибки не кэшируются на бэкенде,
  повтор безопасен).
- Автозапрос при первом рендере блока (если кэша ещё нет в `aiTasksCache`) - `action=
  generate_ai_tasks`, результат кладётся в module-level `aiTasksCache` (ключ
  `manager::YYYY-MM-DD`), чтобы переключение вкладок/дропдауна admin-предпросмотра не дёргало
  повторный HTTP-запрos (бэкенд и так закэширует, но лишний round-trip ни к чему).

## Проверка

- Синтетика: контекст собирается из тестовых `D.orders`/`D.debt`, промпт получается на выходе
  без исключений, `parseAiTasksResponse_` корректно обрабатывает валидный JSON, JSON в
  ```fences```, и мусор (кидает понятную ошибку).
- **Живой вызов kie.ai проверить НЕ МОГУ** - в этой сессии нет доступа к `KIE_API_KEY` (правило
  репозитория - не читать `.env` целиком, Bash-доступ к `.env` в этой сессии закрыт хуком) и
  нет доступа к живому Apps Script редактору, чтобы прописать Script Property. Точный формат
  ответа `/codex/v1/responses` подтверждён только текстом в reference-памяти (документация
  kie.ai), не живым тестовым запросом. После деплоя Владу нужно: (1) вручную добавить Script
  Property `KIE_API_KEY` в редакторе Apps Script; (2) открыть свою личную страницу под ролью
  admin, выбрать любого менеджера, проверить, что блок сгенерировался; если формат ответа
  kie.ai окажется не таким, как в памяти - пришлёт текст ошибки, поправлю парсинг за один заход.
- Регрессия: остальные личные страницы (Васин, наёмные логисты) не задеты - новый блок только
  в `renderMyPageManager`.

## Риски

- **Стоимость**: reasoning-модель (GPT-5) дороже Gemini Flash. Кэш на день ограничивает расход
  - максимум 1 вызов на менеджера в день (при условии, что admin-предпросмотр не сбрасывает
  кэш - он его как раз переиспользует). Худший случай - Влад в один день пролистает всех ~11
  менеджеров ДО того, как они сами зайдут - 11 вызовов за день, разово, не по кругу.
- **Формат ответа kie.ai не проверен вживую** (см. "Проверка" выше) - главный риск сессии,
  честно записан, чинится за один цикл правок после первого реального теста.
- **Реалистичность советов** ограничена тем, что реально передано в контекст (план/факт/топ
  клиенты/пропавшие/долги) - модель не видит переписку/причины, советует по цифрам, не заменяет
  живое знание менеджера о клиенте.

## Уточнения от 2026-08-12 (тот же день, вторая итерация - первый реальный прогон)

Первая живая генерация (GPT-5 через kie.ai) сработала технически (парсинг/формат ответа -
подтверждён, риск из "Проверки" выше снят), но Влад разобрал каждую из 5 задач построчно -
модель писала общие/местами ошибочные формулировки из-за нехватки деталей в контексте. Плюс
3 доработки UI по скриншоту.

### UI

  страницы (ФИО+должность) уже несёт этот смысл, для ВСЕХ ролей (менеджер/логист/Васин), не
  только менеджера - тот же дубль был везде.
- Компактный виджет плана в шапке, справа от имени (`renderMyPage()`, только для

  раскраской, что и полная шкала. Полная шкала осталась отдельным блоком ниже, без изменений

- Полоса "Выполнение плана продаж" - раньше статус-текст красился ДРУГИМ порогом (95/105,
  фактически бинарно красный/зелёный с "мёртвой зоной" 95-100%), чем факт-заливка (50/80) -
  разные пороги в одном виджете читались нелогично. Теперь ОДИН порог everywhere (0-50 красный,
  50-80 жёлтый, 80-100+ зелёный - Влад: "сделать более дружелюбной") - `planZoneColor_()`,
  общая для факт-бара, статус-текста, отметки прогноза и виджета в шапке.

### Промпт и контекст для ИИ - главная часть правки
Влад построчно разобрал первую генерацию (см. полный текст в истории сессии) - ключевые
претензии и фикс каждой:
1. **"Было бы круто ссылаться на УПД"** - по Геоспецстрою модель могла сослаться только на
   общий баланс, не на конкретный документ. Добавлено `debt.top_debtors[].unpaid_docs` - топ-3
   САМЫХ СТАРЫХ непокрытых документа (дата/юрлицо/описание/сумма к оплате) на должника, из уже
   загруженного `c.unpaidDocs` (тот же источник, что открывающаяся строка на вкладке ДЗ).
2. **"52 отгрузки без ТТН - не зона менеджера, это к логистам; а вот проводить после подгрузки
   путевого - можно ускорять"** - модель перепутала два разных документных статуса. В промпт
   добавлены явные факты: `no_waybill` (нет путевого) - зона ЛОГИСТОВ, не писать менеджеру
   задачу собирать путёвки; `not_posted`/`no_realiz` (путевой есть, но не проведён/нет
   реализации) - менеджер МОЖЕТ ускорить.
3. **"33 непроведённых (не 'неподанных'), и они не 'держат выручку' - просто если документ
   закрыт, вероятность оплаты выше"** - модель придумала неверную причинно-следственную связь.
   В промпт добавлен ПРАВИЛЬНЫЙ факт (документы влияют на вероятность быстрой оплаты, не
   "держат" уже учтённую выручку) - модель теперь должна объяснять именно так, не изобретать.
4. **"Пропавшие клиенты - должно быть 'ты тогда-то работал с тем-то, попробуй связаться,
   узнать как дела', а не сухая статистика"** - в контекст добавлено `last_order_date` (раньше
   терялось при сборке контекста, хотя было в `computeLostCustomersForManager_`), промпт
   инструктирует формулировать как напоминание из истории отношений.
5. **"Активные клиенты с ростом - можно написать, что неплохо идёт работа, может стоит
   увеличить объёмы"** - промпт теперь явно просит позитивную рамку для растущих клиентов, не
   формулировку-претензию.
6. **"Совет по плану" называл сбор ДЗ и проведение документов 'рычагом' для роста ПРОДАЖ -
   сомнительно"** - Влад прав, это разные цели (план считается по факту продаж, не по оплатам).
   Промпт теперь явно разделяет ДВЕ ЦЕЛИ (рост продаж vs деньги/документы) и требует, чтобы
   `plan_advice` касался ТОЛЬКО рычагов роста продаж.
7. **Доп. контекст** - `documents.examples` (топ-5 проблемных заказов этого менеджера, номер/
   дата/клиент/сумма/статус, тот же источник `orders.problem_orders`, что "Воронка документов")
   - чтобы задачи про документы тоже ссылались на конкретные заказы, а не на голые счётчики.
8. **Новое поле `category`** ("выручка"/"дебиторка"/"документы") на каждой задаче - промпт
   просит разумный баланс (минимум 2 задачи про рост продаж, не больше 2 про ДЗ, не больше 1
   про документы), фронтенд показывает маленький бейдж категории у каждой задачи.
9. Краткое исследование по запросу Влада ("посмотри, как решают такую задачу") - "Next Best
   Action" паттерн в CRM (Dynamics 365, HighSpot и др.): ограничивать список 1-3 действиями по
   impact/urgency (у нас фиксировано 5 - осознанно оставлено, Влад просил именно 5), встраивать
   рекомендации в рабочий поток менеджера (уже так - на личной странице), опираться на
   конкретные проверяемые факты, а не общие метрики - это и есть суть правок выше (пункты 1-8).

5. **"Итого по прогнозу"** - новая строка под "Итого" синим цветом (`COL.blue`), зарплата, если
   темп сохранится до конца месяца. Не новая формула - масштабирует числовые поля строки
   менеджера/логиста на `paceRatio` (тот же коэффициент, что уже даёт прогноз плана) и
   прогоняет через ТУ ЖЕ `calcMgr()` - переход на следующую ступень оклада/премия >15М в

6. **Правила эскалации по ДЗ в промпте** (Влад разобрал реальную генерацию: "Гермесавто, долг

## Уточнения от 2026-08-12 (тот же день, пятая итерация)

Влад разобрал ещё одну живую генерацию (МИК-СЕРВИС+ ООО / ТСК-3 ООО) - три содержательных
правки и одна про число-форматирование.

1. **Допродажа без учёта долга - методологическая ошибка, не опечатка.** Рекомендация
   "предложи МИК-СЕРВИС+ увеличить объём" при том, что у клиента уже 600 000 ₽ неоплаченного
   долга - "очень сомнительно... только при условии оплаты по предыдущему объёму". Раньше
   `top_customers`/`lost_customers` в контексте ИИ не пересекались с ДЗ вообще - блок долга
   собирался отдельно. Теперь `buildManagerAiContext_` собирает ДЗ менеджера ПЕРВОЙ (до
   top/lost клиентов) и строит `debtByName` (имя контрагента -> баланс), которым помечает
   каждого клиента в `top_customers`/`lost_customers` полем `unpaid_balance`, если у него есть
   непогашенный остаток (любой, не только "работающий" - для предупреждения важен сам факт
   долга, не взыскиваемость). Промпт получил явное правило: рекомендация "нарастить объём" при
   наличии `unpaid_balance` должна ставить условие (сначала оплата, потом рост), не игнорировать
   долг.
2. **Формулировка "верни клиента" - неестественная.** Влад: "часто читаю слово 'верни', 'не
   верни', а 'возобнови'". В промпт добавлено явное указание - "возобнови работу с..." хорошо,
   "верни клиента" не использовать (клиент не вещь).
3. **Грамматический род под пол сотрудника.** Влад: "если обращение идёт к сотруднику женского
   пола, учитывая род..." - пример из плана (Савиток Олеся Анатольевна) до этой правки получал
   бы "ты работал с..." (мужской род) от модели, хотя менеджер - женщина. Промпт получил
   инструкцию определять пол по отчеству/имени в `context.manager` (окончание "-вна"/"-чна" =
   женский, "-вич"/"-ич" = мужской) и использовать верный род во всех обращениях на "ты".
4. **Разделители тысяч в числах.** "7618250" тяжело читается - модель иногда не форматирует
   суммы внутри собственного текста (JSON-число само по себе не содержит разделителей, а при
   вставке в текст ответа модель должна сама расставить пробелы). Промпт получил явное правило
   с примером - "7 618 250", не "7618250", применяется ко всем суммам в тексте задач и совета.

Проверено: unit-тест `debtByName`/`attachDebtFlag_` на синтетике (МИК-СЕРВИС+ с балансом
600 000 -> получает `unpaid_balance`, клиент без долга -> поле отсутствует) - в точности
воспроизводит сценарий Влада. Полный промпт собран на реальном примере (Савиток, женское
отчество) - все 4 новых правила видны в тексте, читаются понятно.
