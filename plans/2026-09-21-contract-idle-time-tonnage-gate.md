3. Договор нельзя выгрузить, пока менеджер не заполнил наименование/габариты/**массу** груза -

## Формула простоя (Влад, 21.09, два уточняющих вопроса заданы и закрыты)

- **База - стоимость СМЕНЫ по тоннажу из таблицы калькулятора**, не итоговая цена рейса
  `o.price` (та может включать доплаты за маршрут/сопровождение/скидку - Влад явно выбрал
  тоннажную базовую ставку, не `o.price`).
- Смена = 7 оплаченных часов работы → **час простоя = смена_по_тоннажу / 7**.
- Бесплатно: 7 часов работы + 1 час подачи = **8 часов бесплатно НА ВЕСЬ РЕЙС** (Влад выбрал
  ОБЩИЙ лимит, не отдельно на погрузку и отдельно на выгрузку - это меняет старую
  формулировку п.4 «на каждую процедуру»).
- С 9-го часа - почасовой простой до конца первых суток (24 часа с начала = 16 биллингуемых
  часов первого дня - совпадает с числом «16» из сообщения Влада не случайно).
- Свыше суток - **по 16 часов (не 24) за каждые последующие начатые сутки**, не продолжающийся
  почасовой счётчик.

Пример (трал до 20 т, смена 25 000 ₽): час простоя = 25 000/7 ≈ 3 571 ₽. Сутки простоя
(с 2-х суток и далее) = 3 571 × 16 ≈ 57 143 ₽.

## Источник таблицы смен по тоннажу - НЕ дублировать

Таблица `P` (Трал/Длинномер/Панелевоз/Трал под кран/Трал-корыто/Faymonville, ₽ по массе) и
хелперы `tralByMass(w)`/`faymonCatByMass(w)` живут в `api/lib/calculator-calc.js` **на VPS,
не в этом репозитории** (проверено SSH 21.09, файл 318 строк, `module.exports` в конце).
Дублировать эту таблицу в `order-plan-v2.js` - риск разъехаться с сервером при следующей
правке цен (тот же класс проблемы, что [[project_orders_calc_vps_sync_gotcha]]) - тем более
опасно здесь, потому что ошибка попадёт в штрафной пункт ЮРИДИЧЕСКОГО документа.

**Решение:** новая чистая функция `shiftRateFor(vehType, weight)` в `calculator-calc.js`
(переиспользует существующие `P`/`tralByMass`/`faymonCatByMass`, БЕЗ маршрута/сверхгабарита/
дальнего рейса/раздвижения корыта - подтверждено Владом, нужна именно базовая ставка по
массе) + тонкий роут `GET /api/calculator/shift_rate?vehType=&weight=` в `server.js`. Не
трогает `computeQuote()` и вообще ничего в существующей логике - только добавляет экспорт уже
готового кода.

⚠️ **Файл чувствительный** - в памяти есть пометка «не лезть в `calculator-calc.js` без
Влада» (из-за известного MKAD-полигон-бага в отдельной задаче, Фаза 1 ИИ-агента продаж).
Это другая, независимая часть файла - здесь ничего в существующих функциях не меняется,
только добавляется новый маленький экспорт. Но раз файл живёт на проде и связан с деньгами -
**сверить с Владом перед деплоем этого кусочка на VPS**, не просто запушить.

## Шапка заказчика - автозаполнение по ИНН, без пустых полей - СДЕЛАНО 21.09

**Разведка показала: почти вся инфраструктура уже была.** Поле «Заказчик» в форме заявки
(`op2-f-cust`) уже умеет искать по ИНН: `GET /api/orders/inn` - сначала справочник
(`sprav_legal_entities`), если нет - **ДаДата** (не Чеко - в форме используется именно она,
`DADATA_API_KEY`), кнопка «Сохранить в справочник и подставить» (`/api/orders/inn_save`)
пишет найденное в справочник и проставляет `customer_entity_id` на заявке. Ни ДаДата, ни
Чеко НИКОГДА не отдают банковские реквизиты (это не публичные данные ЕГРЮЛ) - подтверждено
чтением обоих интеграций, значит правило «нет банка - не печатать» будет срабатывать
почти всегда для заказчиков (это база, не редкое исключение).

**Ключевая развилка (решено Владом 21.09):** `customer_entity_id` - ОПЦИОНАЛЬНОЕ поле,
менеджер может просто вписать имя заказчика текстом, не проверяя по ИНН. Без него взять
реквизиты неоткуда (ни справочник, ни ДаДата - их вызывают ПО ИНН). Влад выбрал **блокировать
выгрузку договора**, если `customer_entity_id` не проставлен - тот же гейт-паттерн, тост с
причиной («в поле «Заказчик» введи ИНН и подставь из подсказки»).

**Сделано:**
