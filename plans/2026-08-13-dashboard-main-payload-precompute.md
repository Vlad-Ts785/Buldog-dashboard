# План: ускорить главную загрузку дашборда - precompute тяжёлого payload в runAll()

**Дата:** 2026-08-13
**Автор:** Клод (с Владом)
**Статус:** черновик

## Цель

Главная загрузка дашборда (`doGet()` без `action`, роль admin) должна открываться мгновенно
при ЛЮБОМ заходе - включая самый первый после обновления данных 1С, не только повторные
открытия. Сейчас каждый визит пересчитывает всё с нуля.

## Контекст

Повод (Влад, 2026-08-13): "долгие загрузки порой", в рамках разговора про архитектуру 2.0.

Нашли причину: `doGet()` без action ([scripts/full_script_final.js:3974-4011](../scripts/full_script_final.js#L3974))
на КАЖДЫЙ визит пересчитывает: `getSummaryData`, `aggregateFinHistoryForRange` (парк за
месяц), `getOrdersData` (текущий месяц + **весь архив прошлого месяца** ради "потерянных
клиентов" - [scripts/full_script_final.js:7150-7159](../scripts/full_script_final.js#L7150)),
`getHistoryData`, `getDebtData`, `getReceiptsData`, `getDriverOrderCounts_`. Ни один байт не
кэшируется. При этом `runAll()` и так гоняет обновление данных по расписанию 6 раз в день
(6/9/12/15/18/21 МСК, [scripts/full_script_final.js:3279](../scripts/full_script_final.js#L3279))
- то есть данные для этих полей и так не свежее последнего прогона, пересчитывать их заново
при каждом клике "открыть дашборд" смысла нет.

В коде уже есть отработанный паттерн решения этой же задачи - `action=global_stats`
(см. [2026-08-04-global-stats-page.md](2026-08-04-global-stats-page.md)): не считает текущий
месяц на лету, а читает готовое из листа `История_месяцев`, который заполняет `runAll()`.
Делаем то же самое для главной страницы.

**Важный нюанс** - не всё в главном payload одинаково "дорого" и не всё можно кэшировать с
лагом:
- **Дорогое** (тяжёлый парсинг больших листов, источник обновляется только `runAll()`):
  `summary`, `vehicles`, `orders`, `debt`, `receipts`, `history`, `driverOrderCounts`. Можно и
  нужно кэшировать - свежее последнего `runAll()` эти данные всё равно не бывают.
- **Дешёвое, но должно быть ЖИВЫМ**: `fleet`, `repairs`, `staffMarkas` - берутся из Штатки,
  которая в CLAUDE.md прямо названа "ЖИВОЙ документ (статусы машин)" - её редактируют руками
  вне расписания `runAll()`. Если закэшировать эти поля на 3 часа, правки статуса машины будут
  "зависать" - это регресс, а не ускорение. `access_log` - активность сотрудников, тоже должна
  быть свежей. Штатка маленькая (~55 строк) - расчёт по ней и так быстрый, кэшировать незачем.

## Фазы

### Фаза 1. Выделить дорогой блок в отдельную функцию (~20 мин)
- [ ] `buildHeavyMainPayload_(ss)` - переносим туда ровно то, что сейчас дорого считается в
      `doGet()`: `summary`, `vehicles`, `drivers` (производное от vehicles), `orders`, `debt`,
      `receipts`, `history`, `driverOrderCounts`, `periods`. Чистая функция, без побочных
      эффектов, как `computeMonthSummary_` в прошлом плане.
- [ ] `doGet()` пока продолжает звать её напрямую (behavior не меняется) - промежуточный шаг,
      чтобы не сломать всё одним большим диффом.

### Фаза 2. Хранилище precomputed payload (~40 мин)
- [ ] Решить формат хранения. Рекомендация - **скрытый лист** `Кэш_главной_страницы` (не
      `CacheService`): CacheService ограничен 100KB на ключ и TTL максимум 6 часов, а этот
      payload заведомо больше 100KB (для сравнения - `client_analytics`/`manager_profile`
      уже упираются в лимит на **урезанных** данных, см. `if (caJson.length < 95000)`).
      Лист же не имеет TTL-сюрпризов (не исчезнет молча, если `runAll()` разок не отработал -
      останется последнее хорошее значение) и уже привычный паттерн в этом проекте
      (`История_месяцев`). Cell-лимит Sheets ~50000 символов - пишем JSON в несколько ячеек
      подряд (chunks), склеиваем при чтении.
- [ ] `saveMainPayloadCache_(ss)` - зовёт `buildHeavyMainPayload_`, режет JSON на чанки,
      пишет в лист (одна строка, перезаписывается каждый раз, не копится история).
      Версия в первой ячейке (`v1`) - на случай будущей смены структуры payload, чтобы старый
      кэш от прошлой версии кода не подсунулся молча после деплоя (тот же приём, что
      `client_analytics_v7_`).
- [ ] `readMainPayloadCache_(ss)` - читает и склеивает чанки, проверяет версию, возвращает
      `null` если кэша нет / версия не совпадает (fallback ниже).

### Фаза 3. Подключить к runAll() и к doGet() (~30 мин)
- [ ] В `runAll()` - вызов `saveMainPayloadCache_(ss)` в конце, после `importReceiptsReport()`
      (все источники к этому моменту свежие за этот прогон).
- [ ] `doGet()` без action, admin: `readMainPayloadCache_(ss)` - если есть, используем как
      основу; если `null` (первый запуск после деплоя, до первого `runAll()`, или порча кэша) -
      считаем `buildHeavyMainPayload_(ss)` на лету как раньше (safety net, никогда не отдаём
      ошибку из-за отсутствия кэша).
- [ ] Поверх кэша (или live-расчёта) **всегда** доклеиваем живые поля: `fleet`, `repairs`,
      `staffMarkas`, `access_log`, `updated` (текущее время запроса, не время кэша).

### Фаза 4. Проверка и деплой (~30 мин)
- [ ] Сравнить JSON старого пути и нового (кэш) на реальных данных - поля идентичны.
- [ ] Замерить время ответа `doGet()` до/после (лог в Apps Script executions).
- [ ] Влад открывает дашборд несколько раз подряд, проверяет: цифры совпадают с тем, что было
      раньше; правка статуса машины в Штатке видна сразу, без ожидания `runAll()`.
- [ ] Деплой по протоколу (`clasp push` + `create-version` + `redeploy`), строка в
      `scripts/DEPLOY_LOG.md`.

## Критерии готовности

- [ ] Первое открытие дашборда после обновления данных 1С загружается так же быстро, как
      повторное (не только повторные визиты).
- [ ] Правки в Штатке (статус машины) видны на дашборде без задержки в 3 часа.
- [ ] Если кэш почему-то пуст/битый - страница всё равно грузится (медленнее, но без ошибки).
- [ ] Цифры на всех вкладках главной страницы совпадают с тем, что было до изменения.

## Риски

- Payload может отставать от факта на длину одного цикла `runAll()` (до ~3 часов для
  парка/заказов, до суток для ДЗ - но ДЗ и так обновляется 1С раз в сутки, тут ничего не
  меняется относительно текущего поведения).
- Если структуру `buildHeavyMainPayload_` поменяем в будущем и забудем поднять версию кэша -
  фронт получит старые поля вперемешку с новыми. Митигация - версия в первой ячейке,
  проверяется при чтении.
- Гонка: `runAll()` пишет кэш, пока `doGet()` его читает. Митигация - пишем кэш одной
  операцией (весь лист целиком за один `setValues()`), не по частям построчно.
- Штатка не единственное "живое" исключение - если позже появится ещё один источник, который
  редактируют руками вне `runAll()`, его тоже нельзя молча заворачивать в этот кэш. Проверять
  при каждом будущем добавлении нового поля в главный payload.

## Открытые вопросы

- Ничего не блокирует старт - формат хранения (лист vs chunked cache) решаем сами, Влад уже
  выбрал направление ("Б: правильное решение").
