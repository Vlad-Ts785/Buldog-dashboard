- **Скрытый баг:** роль живёт в токене сессии, `main_payload` перевыпускает токен с той же ролью. Смена роли в листе не доходит до человека, который заходит чаще раза в 48 ч.
- Копии уже разошлись: `plan-m.html` без Феськова; Apps Script: колонны только Барыльченко, руководитель логистики = Рыщанов (на сервере - Сильчев).

## Как это сделал бы профессиональный архитектор

**Модель - RBAC (Role-Based Access Control, управление доступом на основе ролей):**
- `roles` - справочник ролей: ключ, название, базовая роль для совместимости (`admin/manager/logist/mechanic`), какие страницы видит (матрица роль × страница - правится галочками в Справочниках).
- `user_access` - кто есть кто: email, сотрудник из `sprav_people` (по id, не по фамилии), роль, активен, с какой даты. Заменяет `access_users` и лист «Доступ».
- Охват данных (свои / команда / все) - свойство роли, команда = сотрудники, у которых руководитель - этот человек (`head_person_id` в `sprav_people` вместо фамилий-строк).
- Редкие исключения (ГПБ, Прус с двойной ролью) - отдельная таблица исключений с причиной, а не `if` по фамилии.

**Варианты:**
1. **RBAC поэтапно, «душителем» (рекомендую).** Сначала Справочники становятся источником истины и появляются новые роли, но в токен и старый код пишется базовая роль - ни одного отказа 403. Потом по одной заменяем проверки фамилий на проверки роли/права. Плюс: польза видна сразу, ничего не ломается. Минус: 1-2 недели до полного конца.
2. Только перенести лист в Справочники, роли не трогать. Плюс: 1 день. Минус: главное (старшие, механики, страницы по ролям) не решено, фамилии в коде остаются.
3. Переписать всё разом на права. Плюс: чисто. Минус: 92 места с ролями одним заходом - гарантированные поломки у живых пользователей.

**Какие «палки» не ставим:**
- новую роль строкой в токен сразу (`fleet_head` не входит ни в один из 92 списков - будет 403 почти везде);
- связь людей по фамилии (однофамилец или смена фамилии ломают всё);
- матрицу страниц в коде (`if role === ... показать`) - только в данных, правится в Справочниках без программиста;
- ещё одну копию состава ролей в мобильных страницах - они читают тот же ответ сервера.

**Риски и как проверяем:** режим «только лог» перед включением новых проверок (сервер пишет, кому было бы отказано, и мы сверяем с текущим поведением); лист «Доступ» остаётся зеркалом только для чтения, пока Apps Script жив (так уже сделано с планами продаж 04.09); запасной вход (break-glass токен) не трогаем.

**Термины:** *RBAC* - доступ по ролям, а не по людям; *матрица доступа* - таблица «роль × страница/действие»; *принцип наименьших привилегий* - каждая роль видит только то, что ей нужно для работы.

**Безопасность вкладки «Доступ и роли» (Влад, 23.09: «только мне, только мне»):**
- Право `access.manage` - ТОЛЬКО у роли `director`; роль `director` - только у Цуцурина. Не у базовой роли admin: будущий второй admin эту вкладку не получит.
- Проверка на сервере на КАЖДОМ эндпоинте вкладки (чтение списка тоже) - не только скрытая кнопка на фронте.
- «Смотреть как» - вкладка не показывается и её API не отвечает (даже когда смотрит сам Влад от имени другого).
- Журнал изменений доступа: кто, когда, кому, было -> стало.
- Нельзя снять `director` с последнего директора и нельзя отключить доступ самому себе (защита от самоблокировки). Запасной вход (break-glass) не трогаем.
**Лист «Доступ»** - зеркало только для чтения, правки только в Справочниках.
