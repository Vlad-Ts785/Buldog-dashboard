# Планировка - отмена действия из истории (только admin)

## Запрос

Влад, 17.09: "Нужна чисто админская функция делать отмену действий в
истории. Например Кан снял Бурханова с 318, я считаю это неправильным и
отменяю действие - и всё должно вернуться в то же состояние, что и было
до смены статуса."

Панель "История" (`/api/plan/activity`, кнопка у лампочек присутствия и в
меню ПКМ по машине) уже показывает ленту событий - кто, когда, что сделал.
Не хватает кнопки "Отменить" у каждой строки.

## Что уже есть (источники событий в ленте)

Два независимых источника, слитых в одну ленту по времени:

1. **`plan_segs_history`** - create/overwrite/delete записей на ленте
   (рейс/ремонт/ТО/без заказа/без водителя). У каждой строки `hist_id` +
   `snapshot` (JSON-снимок записи в МОМЕНТ действия).
2. **`fleet_assignments` (`source='planirovka'`)** - посадка/высадка
   водителя, сцепка/расцепка прицепа. События `fleet_couple`/`fleet_uncouple`
   СИНТЕЗИРУЮТСЯ из текущего состояния строки (created_at/updated_at), не
   имеют отдельной истории снимков.

## Ключевой принцип безопасности - отмена ТОЛЬКО последнего шага

Отменять можно только САМОЕ ПОСЛЕДНЕЕ действие над конкретной записью/слотом
- не произвольную точку в прошлом. Если после интересующего события уже было
что-то ещё (новая правка того же рейса, новая посадка на тот же слот) -
кнопка "Отменить" не предлагается вообще (не блокируется тостом по клику -
её просто нет), чтобы не создавать иллюзию отмены, которая на самом деле
тихо затрёт чужую более свежую работу. Это тот же принцип, что уже
предотвращает 2 машины в одном открытом слоте (`fleet/couple`, шаг 1-2).

## V1 - что отменяем

- **`seg_create`** → удалить запись (если ещё существует и это последнее
  событие по её `seg_id`).
- **`seg_overwrite`** → вернуть запись к состоянию из `snapshot` (если это
  последнее событие по её `seg_id`).
- **`seg_delete`** → воссоздать запись из `snapshot` (тем же `id`, если он
  не занят заново).
- **`fleet_uncouple`** (снял водителя/отцепил прицеп) → переоткрыть ТУ ЖЕ
  строку `fleet_assignments` (`valid_to = NULL`), если после нейс никто
  другой не садился/цеплялся на этот же слот (tractor_gos+kind+slot).

## Сознательно НЕ в V1

- **`fleet_couple`** (посадка/сцепка) - отмена сложнее: могла закрыть ДРУГУЮ
  открытую запись (пересадка) и урезать driveroff-полосу (авто-truncate,
  `fleet/couple` шаг 4) - откатывать нужно ВСЁ это одним действием, риск
  тихо испортить состояние выше, чем у остальных четырёх. Кнопка "Отменить"
  для этого типа события не показывается вообще - явная граница, не забыто.
- **`seg_cancel`** (отбой заказа) - отдельная кнопка "Отменить" в контекстном
  меню плитки уже покрывает похожий сценарий по-другому; не смешиваем.

## План реализации

1. `GET /api/plan/activity` - добавить `id`/`slot`/`hist_id` в события, где
   их сейчас нет (нужны для точного таргетинга при отмене), и флаг
   `undoable: true/false` посчитанный на сервере (проверка "это последнее
   действие" делается там же, одним запросом, не гадаем на фронте).
2. Новый `POST /api/plan/activity/undo` (`requireRole_("admin")` СТРОГО, не
   admin+manager+logist, как у остального Планировка-API) - принимает тип
   события + идентификаторы, делает ту же проверку "ничего свежее не было"
   ещё раз атомарно (транзакция, `FOR UPDATE`) прямо перед записью - не
   доверяем `undoable`, посчитанному чуть раньше на GET, гонка возможна.
   Само действие отмены ТОЖЕ пишет запись в соответствующую history-таблицу
   (`action:'undo'`) - отмена отменяемого действия остаётся в истории, не
   исчезает бесследно.
3. Фронт (`files/index.html`, панель "История") - кнопка "Отменить" рядом со
   строкой, только когда `ev.undoable && STATE.role==='admin'`. Клик →
   `showConfirmDialog_` (канон, уже используется в этом же модуле) с текстом
   события → на "Да" зовёт `/plan/activity/undo` → тост + перерисовка ленты
   истории И самой доски (`renderRows`/`renderKpis`, состояние изменилось).
4. Мобильная `plan-m.html` - НЕ трогаем в V1 (кнопки истории с отменой там
   нет вообще, admin ей на телефоне не пользуется по роли).

## Проверка перед сдачей

- Живой тест на реальных исторических событиях (не выдуманных) - минимум по
  одному случаю на каждый из 4 типов V1, включая ОТКАЗ (когда undoable
  корректно false из-за более позднего действия).
- `git diff` по `api/server.js` (VPS) и `files/index.html` - без нового
  `git status` мусора, координация с параллельными сессиями по правилам
  CLAUDE.md перед заливкой на сервер.
